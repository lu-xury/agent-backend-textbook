单机程序的难点主要是算法、数据库和进程内并发；系统一旦跨机器，**网络会延迟、重复、乱序，也会在你不知道结果时失败**。一次写请求可能已经在远端成功，只是响应在路上丢了；两个副本可能暂时看到不同数据；一台机器的缓慢还可能借由重试扩散成全站拥塞。分布式系统不是“服务拆得多”，而是让多个独立进程在这些条件下仍能提供可解释的结果。

本章的目标不是记住 CAP、Raft 或某个中间件名词，而是能为一次业务操作写清四件事：**唯一事实存在哪里；读写经过哪些节点；失败后允许用户看到什么；靠什么把错误限制在局部。**这些问题先有答案，组件才有选择依据。

## 12.1 从状态归属开始划分边界

**服务边界**不是按技术层把“用户服务、订单服务、数据库服务”机械分开，而是按业务能力、数据所有权和变化频率划分。订单服务若负责创建订单、取消订单和订单状态机，就应是订单记录的唯一写入者；库存服务负责可售数量与预占规则；支付服务只保存支付意图和渠道结果。其他服务需要订单信息时，可以调用订单服务，或消费它发布的事件来维护自己的只读视图，但不应绕过边界直接更新订单表。

“谁拥有数据”比“表在哪台数据库”更重要。若商品、订单、支付三个服务共享一张可随意修改的数据库表，代码虽然拆开了，schema 变更、锁竞争和权限仍把它们绑成一个整体。这种系统往往同时拥有远程调用的失败模式和共享数据库的耦合，称为**分布式单体**。相反，早期单体只要模块边界和表的访问约束清楚，仍然可以是很好的架构：一个事务就能维护订单和库存的局部不变量，排查与发布也更简单。

判断是否拆服务时，先问：该能力是否需要独立扩缩容、独立可靠性目标、独立安全边界或独立团队节奏？如果答案只是“代码目录已经很大”，先模块化、明确接口、补测试和观测通常更划算。拆分后每一次跨服务调用都引入超时、版本兼容、权限、重试和数据同步成本；它不是把复杂度删除，而是把复杂度移到网络上。

### 高频辨析：单体与微服务

**单体**是一个可独立部署的应用，内部可以有清晰模块；**微服务**是多个可独立部署、通过稳定契约协作的服务。单体不等于混乱，微服务也不自动得到高可用。支付和订单必须独立审计、发布频繁冲突且流量模型差异很大时，拆分有价值；小团队的管理后台为了“像大厂”拆成十个服务，常常只得到十份部署和调用链故障。

## 12.2 副本解决可用性，分片解决容量

一份数据只有一个存储节点时，节点故障会让服务不可用，读写都集中在它上面。**复制（replication）**把逻辑上相同的数据保留在多个副本：常见的主从方式让 leader 接受写入、把变更复制给 follower；读可以从 leader 获得较新的结果，也可以从 follower 换取更低延迟或更高读吞吐，但后者必须接受复制延迟。写路径要明确到足以回答问题：客户端写 leader 后，是 leader 落盘即返回，还是等待若干副本确认？读路径也要明确：下单后立刻查询订单，是否强制读 leader，还是允许短时间查不到？确认数量本身不是承诺；还要说明副本类型、法定多数、故障域、故障切换规则和读一致性。

**分片（sharding/partitioning）**把不同记录分到不同分片，每个分片只承担一部分键空间，从而提高总容量和写吞吐。订单常可按 `user_id` 或 `order_id` 路由；同一键应稳定落到同一分片，否则更新与查询无法会合。分片键要同时看访问模式和数据倾斜：按日期分片会使当天分片成为热点；按租户分片可能遇到一个超级租户；随机散列能分散压力，却让“查某个用户全部订单”需要额外索引或跨分片聚合。分片并非免费扩容，重分片、全局唯一约束、跨分片事务和运维都会变难。

一个实用的组合是“**每个分片再复制**”：分片横向扩展容量，副本提供故障转移和读扩展。不要用多个缓存副本冒充主数据复制；缓存可丢、可过期，数据库或日志中的权威记录才决定事实。

### 高频辨析：扩容与分片

**扩容**泛指增加资源或实例，可以是给机器更多 CPU，也可以是增加无状态 API 副本；**分片**特指把状态按键切开，让不同节点各持有一部分数据。API 层通常可以直接横向扩容，单个可写数据库的表增长到容量瓶颈才需要考虑分片。把一个单库查询慢的问题立刻改成十个分片，往往先放大了问题；索引、查询形状、归档和读副本可能是更低成本的答案。

### 高频辨析：复制与备份

**复制**服务在线读写、故障切换或就近读取，错误也可能很快复制出去；**备份**保存某个历史恢复点，用于误删、逻辑损坏和勒索攻击后的恢复。三副本不等于有备份：一次错误 `DELETE` 可以被三副本一致执行。备份还必须有保留策略、异地副本以及定期恢复演练；对误删和逻辑损坏，常还需要时间点恢复（PITR）或不可变备份，并定义 RPO/RTO，否则只是“看起来存在的文件”。

### 高频辨析：读写分离与分库分表

**读写分离**通常仍是同一份逻辑数据的主副本：写到主库，部分读到副本，难点是复制延迟；**分库分表**是把不同数据切到不同分片，难点是路由、跨分片查询与约束。读写分离不能增加单 leader 的写能力，分库分表也不会自动解决热点键。面试中应先说清读写比例、允许的陈旧窗口和分片键，不能只报两个术语。

## 12.3 一致性不是一个开关

**线性一致性（linearizability）**要求每个操作看起来都在调用与返回之间的某一瞬间生效，并且所有客户端对同一对象观察到同一先后顺序。库存扣减、租约、唯一号占用等“刚写完就必须让下一位读者看到”的操作常需要它或等价的强协调。它并不等于“数据库用了事务”：事务关注一组读写的原子性、隔离性与约束；线性一致性关注跨客户端对单个对象或服务接口的实时可见顺序。

本章后文所说的“强一致性”特指**线性一致性**，以免同数据库的可串行化隔离混淆。**可串行化（serializability）**要求一组成功提交的事务效果等价于按某个串行顺序执行，但该顺序不必满足每个客户端观察到的实时先后；线性一致性额外要求尊重调用—返回之间的实时顺序。两者关注点不同，严格可串行化才同时具备二者。

**最终一致性（eventual consistency）**是指在停止对同一对象的冲突写入、复制链路恢复且冲突处理正确完成的前提下，副本会收敛；它没有承诺“下一次读一定已看到刚才的写”。商品搜索索引、推荐画像、统计报表和消息驱动的通知通常可以接受这种延迟，但必须把体验设计进去：用户创建订单后，订单详情页读 leader 或带会话粘滞；数据看板标注“截至某时”；对依赖未同步的操作返回“处理中”，而不是伪造成功。

中间还有很多可用保证。**读己之写（read-your-writes）**保证同一用户提交后能读到自己的更新；**单调读**避免用户先读到新值、刷新后反而读回旧值；因果一致性保证“回复”不会早于它回复的那条消息。这些往往比对全站每一笔读都追求线性一致性便宜，也更贴近产品需求。PostgreSQL 的事务隔离级别解决的是同一数据库中并发事务看见什么；默认 `Read Committed` 下每条普通查询看见查询开始前已提交的数据，**以及本事务此前自己的写入**。若业务需要序列化结果，仍要正确处理可能的序列化失败与整笔事务重试。[PostgreSQL 事务隔离文档](https://www.postgresql.org/docs/current/transaction-iso.html)给出了各隔离级别的异常边界。

### 高频辨析：线性一致性、可串行化与最终一致性

**线性一致性**规定单个对象或 API 的实时可见顺序；**可串行化**规定一组事务的提交效果可解释为某个串行执行；**最终一致性**只保证停止冲突写入且复制、冲突处理完成后副本最终收敛。CAP 中的 C 在本章采用线性一致性的含义，不是 ACID 的 Consistency，也不是“永不出错”。支付结果可以先显示“受理中”再异步确认；可售库存不能在两个独立副本上各自认为还剩一件并同时售出。选择依据是业务不变量和可见延迟，不是服务名字是否重要。

### 高频辨析：CAP 与可用性

CAP 中的 **P（partition tolerance）**指节点间网络分区或丢包延迟使通信不能可靠完成；现实网络不能被假定永不分区，所以发生分区时，系统必须在 **C（这里指线性一致性）** 与 **A（每个到达未故障节点的请求都在有限时间内获得响应，可能是旧值）**之间取舍。它不是平时随意挑“CA、CP、AP”三个标签，也不等同于 SLO 里的 99.9% 可用率。一个 CP 系统在无法确认 leader 或多数派时可能拒绝写入；一个 AP 风格的购物车可以接受本地写、随后合并冲突。CAP 没有说明延迟、吞吐、备份、权限和所有业务一致性；用它结束设计讨论通常意味着讨论才刚开始。

## 12.4 时钟、顺序与可重试的写入

两台机器的物理时钟会漂移，NTP 校时也可能前跳或回拨。因此“较大的时间戳就是较新的业务状态”只在业务明确允许时才成立。订单状态不能仅按客户端时间决定：`PAID` 与 `CANCELLED` 的并发到达需要状态机和版本条件，例如只允许 `PENDING -> PAID`，或用数据库的版本号执行“当 version=7 时更新为 8”。数据库提交序号、单分区 offset 或 leader 分配的递增版本，通常比墙上时钟更适合定义局部顺序。

全局总顺序代价很高，也常没必要。订单 A 与订单 B 的创建没有因果关系，无须比较先后；同一订单内的 `created → paid → shipped` 必须有序，则让它们按 `order_id` 进入同一分区或经过同一状态所有者。消息系统中“分区内有序”不等于“消费完成顺序有序”：多个消费者、失败重试和下游异步操作都可能重新排序。真正需要的是写清**哪个实体、哪类事件、在哪个边界内**要求顺序。

网络超时时，调用方不知道远端有没有执行。解决方法不是无条件禁止重试，而是为有副作用的命令提供**幂等键（idempotency key）**。客户端为“创建支付”生成稳定请求 ID；服务在权威存储中以该 ID 建唯一记录，并把首次成功结果保存下来。相同 ID 的重试返回同一结果，不再次扣款。幂等键的作用域、过期时间、请求体哈希和冲突行为要写进契约：同一键携带不同金额时应拒绝，而不是把它当成同一请求。保存期至少覆盖客户端可能重试、支付渠道回调和对账所需的业务窗口；短 TTL 的去重缓存不是支付幂等性的最终凭据。

### 高频辨析：幂等与去重

**幂等**描述一个业务操作重复执行后外部可观察结果不变，例如“把订单状态设为已取消”；**去重**是识别多份相同输入并只处理一份的技术。去重可以帮助实现幂等，却不等同于它：消息 ID 去重窗口过期后，业务仍可能收到旧消息；简单地把同一 HTTP 请求丢掉，也未必能返回原先的支付结果。最可靠的幂等通常落在拥有业务状态的数据库唯一约束、条件更新或事务记录上。

## 12.5 共识与选主：只协调必须唯一的事

**共识**让一组节点在部分节点故障、网络不可靠时，对某个值或一串日志顺序达成一致；多数派确认、任期（term）和日志匹配规则保证在正确协议下，不会有两个不同 leader 都提交相互冲突的权威结果。发生分区时，旧 leader 仍可能暂时认为自己是 leader；若它失去多数派，就必须拒绝或无法提交需要线性一致性的写入，资源端还应以 fencing token 拒绝旧任期持有者。它适合保存少量但关键的协调状态：谁是当前 leader、配置版本、分片归属、分布式锁的持有者。Google SRE 对共识的提醒很实际：它是维护关键状态的工具，不是让每个业务读写都经过一轮投票的理由。[《Managing Critical State》](https://sre.google/sre-book/managing-critical-state/)也强调法定多数和故障域会影响可用性。

**选主**是共识的一种用途：同一任务只能有一个执行者时，leader 负责发号施令或调度，其他节点待命。选主成功不等于业务任务一定只执行一次。leader 在把“已处理”写入存储前崩溃，继任者仍可能重做任务；因此业务侧仍需要幂等和可恢复状态。Redis 锁只有在正确租约、原子释放、失联处理和资源 fencing 的前提下，才可能适用于有限场景；它不能替代真正需要线性化/协调保证的共识系统。无论使用何种锁，都要考虑租约过期、时钟暂停、旧持有者恢复后继续写入，以及资源端是否用 fencing token 拒绝旧任期的请求。

### 高频辨析：共识与普通数据库事务

**数据库事务**通常在一个数据库的并发控制范围内维护多行不变量；**共识**在多节点间决定谁拥有权威顺序或配置。两者可以配合，例如选主服务选出调度者，调度者在数据库事务中领取任务；但用共识替代所有事务会增加延迟和运维复杂度，用单库事务假装跨地域选主又会在故障切换时失去明确边界。

## 12.6 跨服务一致性：事务、Saga 与 Outbox

同一个关系数据库内，事务可以把扣库存、创建订单和写出站事件记录原子提交；发生冲突或异常时整笔回滚。跨两个独立数据库、消息系统和第三方支付网关时，已经没有天然的单一提交点。**两阶段提交（2PC）**能在参与者都支持且协调器可用时实现原子提交，但准备阶段会占用资源，协调器故障和参与者阻塞会伤害可用性；许多云 API 或消息系统也根本不参加这种协议。协调器必须把 commit/abort 决定持久化并能恢复；若它在参与者 `prepare` 后失联，参与者可能为了不破坏原子性而阻塞。这种原子性只覆盖能参加该事务协议的资源管理器，不能把 HTTP 扣款、邮件或人工操作纳入同一个可回滚提交。它不是“永远不能用”，但应只用于参与者少、事务短、确实需要原子性且能承担可用性代价的场景。

更常见的是 **Saga**：把长业务拆成一系列本地事务，每步成功后发布下一步命令；后续失败时执行语义上的补偿动作。它可以由编排器（orchestration）驱动，也可以通过事件编舞（choreography）协作，但两者都必须有明确状态与可观测性。例如订票流程先预占座位、再扣款、最后出票；扣款失败则释放预占，出票失败可能退款。补偿不是数据库回滚的魔法倒带：邮件已经发出、外部支付已经清算时，能做的是再发一条更正或退款，而不是假装它从未发生。Saga 必须定义每步状态、超时、重试、人工介入、补偿是否幂等，以及用户何时看到“处理中”。

**Outbox 模式**解决的是“本地写库成功但发消息失败”或“消息发出但本地事务回滚”的裂缝：业务数据和 outbox 表在**同一数据库事务**中写入；独立发布者读取已提交 outbox，投递到 Kafka 或队列，成功后标记或依靠可重放位置推进。relay 在 broker 已确认、标记已发布前崩溃会重投；标记失败或过早标记也必须可恢复，因此 outbox ID 必须稳定，消费者去重仍是必要条件。Outbox 只保证本地状态与“待发布事件”一起提交，**不保证消息一进入外部世界就让所有下游副作用恰好一次发生**。Kafka 的幂等生产者和事务能把其内部 read-process-write 与 offset 边界内的重复处理进一步收紧，但数据库、HTTP 邮件接口和人工动作仍是另一道边界。[Kafka Design 4.3](https://kafka.apache.org/43/design/design/)说明了其事务与 exactly-once 语义的适用范围。

### 高频辨析：事务与 Saga

**事务**在一个受控资源内追求原子提交和隔离；**Saga**接受跨资源的中间状态，通过补偿与状态机恢复业务一致。转账的同库借贷可以用一笔事务；跨库存、支付、物流的下单更适合 Saga。Saga 不是“没有一致性”，而是把一致性从瞬时原子性改成可观察、可补偿、可恢复的过程。

## 12.7 服务之间怎样通信

**同步 RPC**适合调用方必须马上依据结果继续工作：提交支付前校验风控、读取当前价格、登录时验证凭据。接口必须给出超时、错误码、重试条件、幂等要求和版本策略。调用链不能无限变长：A 等 B、B 等 C 时，C 的一点慢会占满上游线程和连接池。入口应设置总 deadline 并向下游传播；每一跳的 timeout 只能消耗不超过剩余预算的时间，还要留出返回与清理余量。重试只用于短暂且可重试的故障，并配合退避、抖动和总预算。

**消息队列或事件流**适合允许稍后完成、需要削峰、需要多方订阅或希望发送者与消费者独立演进的工作：订单创建后发送通知、更新搜索索引、生成报表。它并不消除失败，只把失败从同步响应改为积压、重复和死信处理；事件 schema、保留期、消费者进度、顺序键与重放策略仍要设计。命令表达“请库存服务预占”，应有单一负责者；事件表达“订单已创建”，可以有多个订阅者。不要把一个 RPC 请求序列化后塞进队列就叫事件驱动，先确定谁负责决策、谁拥有状态。

### 高频辨析：同步 RPC 与消息

**RPC**给调用方一次有时限的直接答复，适合强交互；**消息**把接收和处理解耦，适合异步工作和扇出。用户点击“购买”时可同步创建订单并返回订单号，之后异步发货通知；若库存预占的结果决定能否下单，则不能把它随意异步化而立刻返回“购买成功”。两者常在同一流程共存，关键是清楚地告诉用户哪一步已经确认、哪一步仍在处理。

**服务发现**回答“这个服务的可用实例在哪里”，例如 DNS、注册中心或 Kubernetes Service 提供的名字与端点；**负载均衡**回答“这一次请求应送给哪个实例”，可在客户端、sidecar、网关或四层/七层代理完成。发现提供候选集合，不保证每个实例健康；负载均衡需结合健康检查、连接数、延迟、区域和熔断信息做选择。把 Pod IP 写进配置文件，扩缩容或重建时必然失效。

### 高频辨析：负载均衡与服务发现

服务发现像更新“可拨打的通讯录”，负载均衡像从通讯录中选择一个合适的接听者。DNS 轮询可以同时承担一点分流，但 TTL、缓存和连接复用使它不是精确均衡器；反向代理能按连接或延迟分配，也仍依赖正确的实例注册与健康信息。Google SRE 的[负载均衡章节](https://sre.google/sre-book/load-balancing-datacenter/)将目标概括为利用容量并保护单个后端不被压垮。

## 12.8 缓存、读路径与真源

缓存保存的是可丢失的派生副本，**真源（source of truth）**才有权决定业务事实。商品详情可用 cache-aside：先读缓存，未命中则读数据库、填入缓存；更新时先提交数据库，再删除缓存，让下一次读取重新填充，这是常见默认而不是绝对新鲜保证。删除失败需要可靠重试或事件失效；读己之写的关键路径不能只依赖缓存。无论是失效还是更新缓存，都要接受竞态：失效后旧请求可能晚到并把旧值写回缓存。版本号、短 TTL、消息失效和条件写可以降低风险，但不能把缓存当成永不出错的事务参与者。

读写分离会让读路径更复杂。若订单刚创建就从异步副本读取，可能暂时不存在；解决方案包括关键读取走主库、会话粘滞一段时间、等待复制位置，或返回处理中的状态。不要为了一个后台报表的延迟容忍需求，让所有交易接口都读副本；也不要因为有缓存就取消数据库约束。缓存穿透、击穿和雪崩的根因也不同：查询不存在的键会穿透到真源；热门键过期时并发回源会击穿；大量键同时过期或依赖故障会造成雪崩。分别用负缓存/输入校验、请求合并或锁、过期抖动和限流处理。

### 高频辨析：缓存与真源

**缓存**优化读取速度和承载能力，可以重建；**真源**保存可审计、可恢复的权威状态并执行约束。余额、库存和权限最终必须由真源裁决；把余额只放 Redis 会在淘汰、故障切换或写入丢失时无从恢复。缓存里的数据即使“看起来最新”，也不应绕过服务边界被其他服务直接修改。

## 12.9 过载时先保护系统，再谈重试

负载均衡只能分摊已存在的容量，不能创造容量。请求到达率持续超过完成率时，队列会增长，排队时间推高超时；客户端重试又制造更多请求，最终形成级联故障。Google SRE 的[过载处理](https://sre.google/sre-book/handling-overload/)建议让后端只接受能够处理的工作，并尽早、明确地拒绝其余请求。对低优先级推荐、导出或批处理可以降级；对关键写入应保留配额和隔离通道。

**限流**限制某个入口在一段时间内允许的请求或字节数，常按用户、租户、API key 或路径实施；令牌桶允许短暂突发，漏桶通常强调平滑输出速率，并发限制则控制在途工作量。它回答“允许多少请求进来”。**隔离（bulkhead）**把资源分成互不拖累的舱室，例如支付和搜索使用不同连接池、线程池、队列配额或节点池；它回答“一个坏邻居最多拖垮谁”。两者应配合超时、取消、有限队列、熔断与退避。熔断器打开后不再持续请求已知失败的下游，但半开探测必须受控；无限重试、无限队列和共享无上限线程池是故障放大器。

架构中还要识别故障域：同一机架、同一可用区、同一数据库主库、同一认证服务或同一第三方支付渠道，都可能让看似很多的副本同时失效。多副本若都依赖一个不可用的控制面或同一错误配置，数字没有意义。容量设计至少估算正常与峰值 QPS、读写比例、平均与 P99 服务时间、每个请求占用的连接/CPU/内存、队列可容忍时长及依赖上限；再通过压测和线上指标校准，不要用“加机器就好”代替预算。

## 12.10 架构面试：把取舍讲成一条可验证的路径

系统设计题先澄清目标，而不是马上画 Kafka、Redis 和微服务。询问用户规模、峰值与增长、读写比例、延迟目标、可用性目标、数据保留期、是否允许陈旧读、隐私合规和不可违反的业务规则。随后画出最短读写路径：客户端如何认证；写入由哪个服务和真源提交；同步返回什么；哪些后续工作进队列；读从哪里来；缓存失效如何做。每个箭头都应能说明超时、重试、幂等和观测点。

以“限量抢购”为例，最小可行方案可让订单服务在权威数据库事务中以条件更新扣减可售库存并创建订单，返回“已受理”；这要求库存仍属于同一服务、同一真源边界。若库存已独立为另一个真源，应改为预占 Saga 或重新评估边界，不能跨库假装一笔本地事务。支付、通知、搜索更新走 Outbox 加队列。流量增长后，先在入口按用户限流、用队列削峰、缓存稳定商品页；只有单库写入确实成为瓶颈，才讨论按商品或库存桶分片。若把库存预扣放进仅最终一致的缓存而没有条件约束，两个请求可能同时看到剩余一件并都成功，这不是“扩展性”，而是破坏不变量。

最后逐项走失败场景：API 超时但数据库已提交时客户端如何安全重试；消息重复时消费者如何幂等；副本延迟时用户如何读己之写；分片热点时如何迁移；一个依赖变慢时如何隔离；误发布或数据损坏时怎样停止、回滚和恢复。好的答案不承诺“绝不丢、绝不慢”，而是声明边界，例如“付款命令按至少一次投递设计；支付服务以 payment_id/provider 幂等键保证重复投递不会造成重复扣款；通知允许最多五分钟延迟；库存以数据库条件更新为准；跨服务状态通过 Saga 收敛”。

## 12.10.1 故障检测、Quorum 与围栏：不要把“看到心跳”误当成事实

分布式系统无法可靠地区分“对方已经宕机”和“对方只是暂时慢、网络分区或 GC 停顿”。心跳超时只能产生**怀疑**，不是证明；过短会把慢机器频繁误判为故障并触发抖动，过长则恢复慢。可靠系统把这一不确定性写入协议：谁有资格接管，旧持有者怎样失去写权，客户端怎样发现新入口，读写在切换窗口返回什么。仅靠“检测到主节点没响应就再启动一个主节点”会导致双主写入。

复制常用**法定人数（quorum）**来在部分故障下继续确认写入。例如在 N 个副本中要求 `W` 个副本确认写、从 `R` 个副本读取；若 `R + W > N`，读集合与写集合至少有一个重叠副本，但这本身仍不自动得到线性一致读——还要规定版本、读路径、协调者和故障切换协议。多数共识系统用选主与日志复制确定唯一提交顺序：leader 只有获得多数派确认才把一项视为提交，落后的副本随后追赶。它们的成本是跨副本往返、可用性取决于多数派和操作复杂度；不要把所有配置读取、指标上报或可重建缓存都放进共识路径。

**fencing token（围栏令牌）**解决租约过期后的旧持有者仍可能继续写的问题。协调服务每次授予独占权时给单调递增编号；数据库、对象存储或下游资源只接受比已见编号更新的请求。这样即使旧 worker 因网络暂停而不知道租约已失效，恢复后也不能覆盖新 worker 的结果。单纯“拿到分布式锁”不提供这种保护：锁服务和业务资源之间可能失联，锁过期也不等于旧进程立刻停止。真正需要独占写时，应优先让唯一约束、条件更新或带版本号的存储成为最终裁判。

有些状态可以不靠全序写入就安全合并，例如只增计数、集合并集或带明确冲突规则的文档；这类 CRDT/可合并状态能在分区期间继续局部更新，之后收敛。它不适合“余额不能为负”“同一库存只能卖一次”之类必须拒绝冲突的约束。选择最终一致、强一致或可合并数据类型前，先把不允许的业务结果写成不变量，再选复制与协调协议。

## 本章练习

1. 订单创建后 100 ms 内进入详情页偶尔显示“未找到”，两秒后又正常。订单写入主库、详情页读只读副本。列出三种修复路径，并说明各自代价。

2. 团队称系统是“CP”，理由是数据库有三个副本。网络分区后 leader 无法联系多数副本，却继续接收写入；另一侧也开始接收写入。指出这段说法的问题，并给出需要补齐的协议边界。

3. 支付接口收到超时后客户端重试，偶尔产生两笔扣款。设计请求 ID、持久化记录与第三方渠道调用的处理顺序；哪些地方仍需要对账或补偿？

4. 报表服务每小时汇总订单，产品希望将订单、库存和支付分别拆库后仍保持“下单即报表准确”。解释为什么这不是单靠读写分离能解决的问题，并选择事务、Saga 或最终一致视图中的一种方案。

5. 某推荐服务变慢，所有 API 的共享线程池被占满，登录与下单也超时。分别说明限流、隔离、超时与熔断在这里应做什么。

## 练习参考答案

1. 第一，创建后的一小段会话窗口强制读主库，简单但会增加主库读负载；第二，等待副本复制到包含该写入的位置再读，体验较稳定但实现依赖数据库能力且会增加延迟；第三，创建响应直接带回订单摘要，详情页短期使用该摘要或显示“正在同步”，代价是前端要处理状态。不能只把副本数加倍，因为问题是复制滞后而非副本数量。

2. 三副本只描述冗余，不能证明 CAP 意义下的 C。若两边都独立写入同一逻辑键，已经失去单一线性顺序。应明确 leader 任期、法定多数、follower 投票规则、旧 leader 隔离或 fencing、提交条件和分区时的拒绝策略；没有多数派的一侧应拒绝需要强一致的写，而不是静默分叉后期待“自动合并”。

3. 客户端为一次业务意图生成稳定 idempotency key；服务先在事务中创建或读取以该键唯一的支付意图和状态，再以该记录的 payment_id 调用渠道。超时重试同一键只返回同一意图并继续查询/推进其状态，不能新建扣款。渠道若支持自己的幂等键，也传入同一稳定标识；若渠道结果未知，要查询渠道、异步对账并用退款等补偿，而不是假定未扣款。

4. 读写分离只复制同一库的数据，无法原子维护三套真源。若三个更新必须同时成功且都在同一受控数据库，局部事务最简单；跨独立库存、支付和订单服务时，把下单建模为 Saga，报表消费事件建立最终一致视图，并向产品声明延迟及重算能力。要求“每一毫秒都准确”意味着需要重新审视边界与可用性成本，不能只增加消息队列。

5. 对推荐入口按用户或租户限流，避免突发压垮下游；为推荐调用配置独立、有限的线程池/连接池和队列，保护登录下单；设置小于上游预算的超时并取消无用工作；错误率或延迟持续异常时打开熔断，快速返回降级推荐或空结果，半开时少量探测恢复。所有请求共用无界线程池、失败即立刻重试，会把一个推荐故障升级为全站故障。
