后端代码的正确性不能只靠“我本地请求过一次，返回 200”。一个接口可能在常见输入下返回成功，却在并发修改、重试、时钟跨日、数据库迁移、网络超时或权限变化时产生错误结果。**测试**是在可重复的条件下提出一个可验证的断言；**调试**是在已有故障中收集证据、缩小范围并定位原因；**代码质量**则是一套让未来修改仍能被理解、审查和验证的约束。三者相互配合：没有测试的修复容易复发，没有调试方法的失败只是红色日志，没有质量门禁的项目会逐渐失去安全修改的能力。

本章的贯穿例子是“创建订单”。规则看似简单：金额必须为正、库存足够才可预留、相同幂等键不能生成两笔订单，提交后要投递后续事件。它同时牵涉纯业务规则、数据库事务、HTTP 边界和异步任务，正好用来区分不同测试该回答的问题。

## 9.1 测试不是证明程序无错

测试只能证明“在这些输入、这些环境和这些断言下，程序的行为符合预期”；它不能枚举无限输入，也不能自动发现需求本身是否错误。测试的价值在于把需求、不变量和曾经发生过的缺陷变成可执行的证据。若需求是“库存不能为负”，那么测试不应只断言一次成功扣减，而应覆盖库存恰好为零、扣减数量超过库存、重复请求、并发请求后的可观察结果。

一条好测试通常具有三个特征。第一，**失败原因单一**：失败时能大致判断是价格校验、库存规则还是数据库配置出了问题。第二，**可重复**：同一提交在同一环境应给出相同结论，不依赖执行顺序、真实时间、公共测试账号或外部网络。第三，**从行为出发**：断言对用户或调用方有意义的结果，而不是锁死某个私有函数如何调用另一个私有函数。测试代码也是生产资产；难读、脆弱或无人维护的测试会降低而非提升交付速度。

一个纯业务函数适合先写成可直接调用的形式：

```python
def can_reserve(available: int, requested: int) -> bool:
    if requested <= 0:
        return False
    return available >= requested

def test_cannot_reserve_more_than_available():
    assert can_reserve(available=2, requested=3) is False
```

这里测试的重点不是 Python 语法，而是规则被隔离：不需要启动 HTTP 服务、创建数据库连接或伪造当前时间。Rust 官方文档也将单元测试描述为隔离检验一个代码单元，以便快速指出哪里正常、哪里异常；集成测试则通过公共接口检验多个部分能否协作。[Rust Book：测试组织](https://doc.rust-lang.org/book/ch11-03-test-organization.html)给出了这种区分。

### 高频辨析：测试、调试与监控

**测试**在预先构造的受控情形下验证预期；**调试**在测试失败或生产故障后寻找实际原因；**监控**持续观察运行系统的指标、日志和追踪，以发现异常并提供调试线索。订单库存的单元测试可以证明“请求数大于库存时函数拒绝”；监控可以告诉你生产中库存预留失败率突然上升；调试才会判断是促销流量、缓存陈旧还是 SQL 条件写错。监控不是线上测试的替代，测试也不会自动解释一次线上超时。

## 9.2 单元、集成与端到端测试

**单元测试（unit test）**验证一个小的代码单元在可控依赖下的行为，通常运行很快，失败定位清楚。它适合金额计算、状态迁移、权限判定、序列化规则、重试策略等。单元不必机械等于“一个类”或“一个函数”：如果三个私有函数共同实现一个不可分割的领域规则，把它们作为一个单元测试更合理。关键是测试不需要真实网络、数据库或其他进程就能说明规则是否成立。

**集成测试（integration test）**验证多个真实组件之间的边界是否正确，例如 ORM 生成的 SQL 是否适配 PostgreSQL、迁移是否能建立约束、HTTP 客户端是否正确处理真实格式的响应、消息序列化能否被消费者解析。它回答“这些部件接在一起会怎样”，而不是替每条业务分支重复写一遍。订单服务的集成测试应使用接近生产版本和配置的临时数据库，执行迁移，再断言唯一约束和事务回滚；同时断言迁移建立了预期索引和约束。性能或执行计划应在代表性数据上做独立、可容忍波动的性能测试，而不是让普通测试断言优化器永远选择某个索引。只用内存数据库通过并不能证明 PostgreSQL 的 SQL、隔离级别或 JSON 行为正确。

**端到端测试（E2E test）**从外部可见入口走完整关键路径，例如通过 HTTP 创建订单，再轮询订单状态，确认授权、路由、序列化、中间件和存储协同工作。它最接近调用方体验，也最慢、最脆弱、定位最差。E2E 的数量应该少而精：注册、登录、支付回调、关键权限拒绝等高价值旅程值得覆盖；把每个输入组合都放进浏览器或全栈环境，会使反馈慢到开发者不再运行。

可以把测试安排理解为金字塔：底层有大量快速、稳定的单元测试；中层有数量较少的集成测试；顶层只保留少数关键 E2E 测试。它不是要求团队画出固定比例，也不是说 E2E 没价值；它提醒我们，越靠近真实环境，发现配置错误的能力越强，但成本、速度和失败噪声也越高。若某个逻辑只能靠 E2E 才能验证，往往说明业务规则和外部边界缠在一起，应该考虑拆分。

### 高频辨析：单元测试、集成测试与 E2E

三者的差别不是目录名称，而是**真实依赖的范围与失败证据的粒度**。测试 `can_reserve(2, 3)` 是单元测试；启动真实 PostgreSQL，检查 `UPDATE product SET stock = stock - ? WHERE stock >= ?` 在竞争时不会超卖，是集成测试；用真实 HTTP 请求创建订单并验证外部调用方可查询状态，是 E2E。单元测试不能证明连接字符串和迁移正确，E2E 也不适合替代上百个金额边界测试。面试中若只说“单测测函数、集测测模块、E2E 测全链路”，还不够；应补充它们各自的速度、稳定性和适用问题。

## 9.3 测试替身：不要把所有假对象都叫 Mock

真实依赖有时太慢、太昂贵、太不稳定，或根本不应在测试中触发。例如单元测试不该真实扣款或发送邮件。这时可使用**测试替身（test double）**，但不同替身回答的问题不同。


- **Dummy（哑对象）**只为满足参数或接口而传入，测试不读取也不调用它。
- **Stub（桩）**为调用提供预先写好的返回值，用来驱动被测代码进入某个分支。付款网关 stub 可以总是返回“批准”或“余额不足”。
- **Spy（间谍）**在完成 Stub 职责的同时记录调用，测试在执行后检查这些记录；例如内存邮件端口保存发出的收据。
- **Fake（仿真对象）**有可工作的简化实现，例如内存仓储或本地假支付服务；它不自动等价于真实数据库或供应商。
- **Mock（模拟对象）**预先声明期望的交互，并验证调用是否满足这些期望，例如成功扣款时必须带同一个 provider 幂等键。Mock 可以是严格或宽松的；只有确实属于对外契约的交互才值得这样断言。

这些术语在不同框架中会有轻微差异；本章采用 Fowler/Meszaros 的常用词汇，具体框架的 API 命名可能不同。但不能混淆一个实用原则：**优先断言业务结果，只有交互本身重要时才断言交互。**若测试支付后订单状态为 `paid`，用 stub 返回成功即可；若测试“失败时不能发送收据”，可用 spy 检查邮件端口没有被调用。若每个单元测试都精确期待内部调用顺序，重构一个函数就会让大量测试失败，即使外部行为完全不变。Martin Fowler 对 mock 与 stub 的区分强调了行为验证和状态验证的不同，[原文](https://martinfowler.com/articles/mocksArentStubs.html)是理解术语的常用参考。

```python
class PaymentStub:
    def charge(self, amount, key):
        return {"approved": True, "provider_id": "test_1"}

class MailSpy:
    def __init__(self):
        self.sent = []
    def send_receipt(self, order_id):
        self.sent.append(order_id)

def test_paid_order_sends_one_receipt():
    mail = MailSpy()
    service = OrderService(payment=PaymentStub(), mail=mail)
    service.pay(order_id="o1", idempotency_key="k1")
    assert mail.sent == ["o1"]
```

这个例子仍要回答“哪一层该发邮件”。若 `pay` 只负责提交支付并写 outbox，那么它的单元测试应断言产生了 `PaymentSucceeded`，邮件消费者另行测试；不要为了测试方便改变系统真实的事务边界。

### 高频辨析：Stub、Mock、Fake 与 Spy

Dummy 只占位；Stub 主要**给答案**；Spy **记录已发生的交互**；Fake 是**可运行的简化实现**；Mock **验证预先声明的交互期望**。它们都是替身，不等于“假的就不可信”。内存 Fake 很适合快速验证仓储接口的业务流程，却无法验证真实数据库的唯一约束和事务隔离；这两个问题应由不同层次的测试承担。把 Mock 当成一切依赖的默认选择，常导致测试实现耦合和重构恐惧。

## 9.4 契约测试、属性测试与模糊测试

服务之间最常见的问题不是“函数算错”，而是接口双方理解不一致：生产者把 `amount` 从整数分改成小数元，消费者仍按分解释；服务端删除了可选字段，旧客户端启动失败。**契约测试（contract test）**把边界的可观察约定固定下来，例如请求/响应字段、类型、状态码、消息 schema、兼容性规则和错误语义。提供方可以维护公开 schema 并验证兼容性；在消费者驱动契约中，消费者声明其依赖的最小行为。契约测试比全链路测试快，比只测本服务更能发现协议漂移；但它不能证明 DNS、证书、鉴权配置和真实网络全部正确，因此不能取代少量集成或 E2E 测试。

**属性测试（property-based testing）**不为每一个输入手写一个预期输出，而是声明一类输入必须满足的不变量，让框架生成很多样本。例如对任意非负 `a`、`b`，`add(a,b) == add(b,a)`；对任意订单项列表，重新排序后总价不变；对任意由本服务 schema 生成的 JSON 值，解析后再序列化、再解析，得到的结构按 JSON 语义等价（对象键顺序不参与比较）。属性必须真的是规格，不能写成“函数结果等于函数自身结果”这种无信息断言。属性测试遇到失败时通常会把输入缩小为最小反例，这对边界 bug 很有价值。

**模糊测试（fuzzing）**以大量异常、随机或变异后的输入探索崩溃、越界、解析漏洞和未处理异常。它常配合覆盖引导：能走到新代码路径的输入被保留，再由它们继续变异。模糊测试尤其适合协议解析器、文件格式、权限边界、序列化库、C/C++ 的内存安全边界，以及 Rust 中的 `unsafe`/FFI、解析器和资源耗尽边界。它不需要总是有精确业务预期，但至少应有基本 oracle，例如“不崩溃、不超时、不泄露敏感栈信息”。Google 的 [OSS-Fuzz](https://google.github.io/oss-fuzz/) 使用分布式持续模糊测试，并支持多种引擎与 Sanitizer；其 [CIFuzz 说明](https://google.github.io/oss-fuzz/getting-started/continuous-integration/)展示了如何在 Pull Request 阶段运行 fuzz target。

### 高频辨析：契约测试、集成测试与 E2E

契约测试验证的是“边界承诺是否仍成立”，常可在不启动对方完整服务的情况下运行；集成测试验证的是“当前这些真实部件接起来是否可用”；E2E 验证的是“用户可见旅程是否走通”。例如消费者以 schema 测试 `PaymentSucceeded` 必有 `payment_id`，这是契约；用真实 Kafka 序列化并反序列化一条消息是集成；从支付回调到订单页面显示完成是 E2E。三者互补，不能因为有 OpenAPI 或 schema 文件就删除所有真实边界测试。

### 高频辨析：属性测试与模糊测试

属性测试由**明确的不变量**指导输入生成，目标是找“合法或定义域内的输入违反规格”的反例；模糊测试更侧重以海量异常输入寻找崩溃、安全问题和鲁棒性缺口。一个金额分配函数可做属性测试：分配金额之和必须等于原金额；一个 HTTP/二进制协议解析器可做模糊测试：任意字节都不能使进程崩溃。二者可组合：fuzzer 负责探索输入，属性或断言负责判断结果是否可接受。

## 9.5 数据库、外部服务与测试数据

数据库不是普通的实现细节。唯一约束、外键、事务、锁、时区、索引和迁移都可能使“内存 Fake 通过”的代码在生产失败。涉及 SQL 的仓储层、迁移脚本和事务边界，应至少有一组使用真实数据库引擎的集成测试。测试数据库应由自动化创建、迁移和销毁；不要共享一个长期存在的开发库，因为遗留数据和并行测试会互相污染。每个测试可在事务后回滚、使用独立 schema/数据库，或为每条记录加测试运行前缀并可靠清理；涉及多连接提交、并发或迁移的测试，应改用独立数据库/schema 并显式清理。选择哪一种取决于测试框架和连接模式，但目标相同：**测试彼此独立，失败不会留下会影响下一次运行的状态。**

外部 HTTP、支付、邮件和对象存储也应按风险分层。单元测试用替身验证自己的决策；对供应商协议可使用 provider 的 sandbox、协议契约或本地测试服务器验证序列化与错误处理；少数发布前冒烟测试才谨慎调用真实沙箱。绝不能让普通测试连接生产环境，更不能在测试中使用真实客户邮箱、真实支付凭据或可删除的生产桶。测试密钥应权限最小、可撤销、独立于开发者个人账号；CI 应使用独立 project/account，网络策略、凭据命名和启动检查也应拒绝生产 endpoint，不能只依赖测试作者小心。

测试数据应表达业务意图，而不是所有测试复用神秘的 `user_1`、`order_2`。读者应能从 `paid_order_with_two_items` 看出前置条件。Fixture 可以集中创建重复的准备工作，但过大的全局 fixture 会隐藏依赖，使单个测试不知为何需要十张表。pytest 将 fixture 用作测试上下文的复用机制，能够覆盖从小型测试到复杂应用的需要；[官方 fixtures 文档](https://docs.pytest.org/en/stable/explanation/fixtures.html)说明了上下文、作用域与清理。无论框架怎样，fixture 的生命周期、清理责任和可变共享状态都应清楚。

### 高频辨析：Fake 数据库与真实数据库测试

Fake 数据库适合测试“仓储接口被怎样使用”和快速业务流程；真实数据库测试适合验证 SQL、迁移、约束、隔离、编码和驱动行为。前者快、易于构造极端状态，后者慢一些但能发现产品差异。正确做法不是二选一：核心规则用单元测试或 Fake 快速覆盖，数据访问边界用真实引擎少量而有针对性地覆盖。声称“用了 ORM 所以不需要数据库集成测试”是危险的，ORM 只改变书写 SQL 的方式，不删除数据库语义。

## 9.6 时间、随机性与并发：消灭偶发失败

**脆弱测试（flaky test）**是在代码未变的情况下有时通过、有时失败的测试。它会消耗团队信任：大家开始点击“重新运行”，真正的回归被淹没。最常见根源是读取真实当前时间、依赖随机顺序、共享状态、固定端口、异步任务尚未完成、以及测试框架默认并行运行。以 Rust 为例，`cargo test` 默认并行执行，并明确提醒测试不应依赖共享环境变量、当前目录等状态；其他框架的默认并发策略不同，但共享状态同样是常见 flaky 根源。需要诊断时可临时单线程运行，但不能把它当作永久修复。[Rust Book：运行测试](https://doc.rust-lang.org/book/ch11-02-running-tests.html)说明了这种并行默认值。

对时间敏感的业务应注入时钟，而非在领域函数里直接调用 `now()`。例如传入 `clock.now()` 或 `expires_at`，测试就能固定为 `2026-01-01T00:00:00Z`，精确覆盖过期前、刚好过期、跨日和时区转换。随机性也应注入 seed 或随机源；测试失败时记录 seed，才能重放同一案例。生成 UUID、端口和临时目录时，保证唯一性而不是依赖“这次大概不会冲突”。

并发测试比“启动十个线程然后 sleep 一秒”更需要设计。先明确要检验的不变量：例如 20 个并发库存预留请求中，成功数不超过初始库存，最终库存不为负。用 barrier 或可控制的 hook 让请求在同一竞争点开始，用超时防止测试永久挂住，再同时检查成功数和最终持久化状态。若数据库提供条件更新或事务锁，集成测试应验证真实行为；若只是要验证内存算法，则把调度点抽象出来。**sleep 只能猜测事情已经发生，不能证明它发生。**

### 高频辨析：确定性测试与真实时间测试

确定性测试用固定时钟、固定 seed、受控调度和隔离资源，使每次运行可重现；真实时间测试确实调用系统时钟或等待真实延迟。前者应是默认，因为它快且可诊断；后者只在验证定时器、部署环境或第三方服务的必要行为时少量使用。把 `sleep(1)` 加长到 `sleep(10)` 不是修复偶发失败，只是扩大 CI 的随机等待。

### 高频辨析：并发测试与压力测试

并发测试验证特定竞态或同步不变量，例如两个事务同时扣最后一件库存时最多一个成功；压力测试在大量请求和较长时间下测吞吐、延迟、资源和容量。并发测试追求可控交错和确定结论，压力测试接受真实调度波动并报告统计分布。前者发现数据竞争和原子性问题，后者发现队列积压、连接池耗尽和扩容边界；二者不能互相替代。

## 9.7 从错误栈到最小复现

调试的第一步不是修改代码，而是把现象写清：什么请求、什么版本、何时发生、预期什么、实际什么、是否稳定复现、影响范围多大。错误栈（stack trace）记录异常传播经过的调用位置；先定位异常类型和发生位置，再在栈中找到最靠近本服务业务代码、且能解释输入与状态的栈帧，而不是只盯框架函数。栈告诉你“异常在哪里被观察到”，不一定告诉你“错误输入最初从哪里产生”；还需要结合请求 id、trace id、版本号、配置摘要和关键业务标识关联证据。日志中不得记录密码、令牌、完整身份证件或支付数据。

**最小复现（minimal reproduction）**是能稳定重现问题的最小输入、最少步骤和最少依赖。例如“批量导入偶尔失败”应逐步缩小为一份 CSV、一个非法 Unicode 字符和一条解析调用，而不是交给同事一个需要完整生产数据库的项目备份。缩小过程常会暴露根因：错误只在时区为东京且跨月时出现，或只在消息重复投递时出现。若无法在本地复现，先让生产证据更完整：保留脱敏后的请求、配置版本、随机 seed、任务 id、队列 offset 和时间窗口，再在隔离环境重放。

修复前应先写一个会失败的回归测试，或至少保存可自动重放的最小案例；修复后该测试应通过。这样修复不仅解决一次事故，也把知识放进持续验证中。若 bug 依赖真实供应商事故，无法写成普通单元测试，可把重放记录、契约样本或受控测试服务器纳入集成测试。没有回归测试的“已经修好了”只是口头结论。

### 高频辨析：错误栈与根因

错误栈是异常在当前进程中的调用路径，**根因**是最早破坏预期的条件，两者可能相距很远。`KeyError` 出现在响应渲染层，根因可能是上游迁移漏填字段；数据库超时出现在驱动层，根因可能是连接池耗尽或慢查询。栈是重要证据，不是自动判决书。调试要沿数据和因果关系回溯，并用最小复现或指标验证假设。

## 9.8 静态检查、格式化、审查与覆盖率

动态测试要运行程序，**静态检查**在不执行或很少执行目标程序时分析代码。类型检查器可发现把 `Optional[User]` 当作 `User` 使用、函数返回类型不一致等问题；linter 可发现未使用变量、可疑比较、资源未关闭和已知危险模式；安全扫描器可发现依赖漏洞或常见污点流。它们覆盖的是不同错误类别，不能因为单元测试全绿就关闭类型检查，也不能因为静态分析无告警就相信并发和业务逻辑正确。

**格式化工具（formatter）**只把代码变成一致的排版，例如缩进、换行和 import 顺序；它应自动运行，避免审查者把时间花在括号位置。**linter**检查可疑或不符合约定的写法；**类型检查器**检查类型推理或标注的一致性；**代码审查（code review）**由人理解变更意图、业务规则、架构边界、可运维性和测试缺口。格式化不能替代 linter，自动工具也不能替代有上下文的人类审查。GitHub 的 Pull Request review 允许评论、建议、批准或要求修改，其目的正是让变更在合并前被讨论和审查，[官方说明](https://docs.github.com/pull-requests/reference/pull-request-reviews)将其视为维护质量与共享知识的机制。

审查时应首先读 PR 描述：它解决什么问题、改变什么行为、如何验证、风险和回滚是什么。再按数据流检查输入验证、权限、错误处理、事务和并发边界，最后看测试是否覆盖新规则和失败路径。有效评论应说明风险和理由，例如“这里重试会在支付成功但响应超时时再次扣款，应传入 provider 幂等键”，而不是只说“这段不太好”。小而聚焦的 PR 更容易被完整理解；巨型格式化与业务重构混在一起，会让真正的行为变化难以审查。

**覆盖率（coverage）**衡量测试执行过多少代码或分支，常见有行覆盖、分支覆盖和函数覆盖。它是发现明显空白的地图，不是正确性的分数。100% 行覆盖仍可能没有断言、只走了错误的分支，或完全没覆盖并发时序；反过来，错误处理、日志和极难触发的防御路径可能无法轻易达到 100%，却不应为报表去写无意义测试。将覆盖率阈值作为防止大幅倒退的护栏可以，但必须结合关键不变量、变更风险、缺陷历史和测试可读性审查。OSS-Fuzz 的覆盖报告也只是分析 fuzz target 质量的一个视角，不能单独代表安全性或功能完整性。[其 coverage 文档](https://google.github.io/oss-fuzz/advanced-topics/code-coverage/)体现了这一限制。

### 高频辨析：格式化、静态检查与代码审查

格式化解决“代码长什么样”，静态检查解决“代码文本和类型中可自动发现的风险”，代码审查解决“在这个业务和系统上下文下，改动是否应该这样做”。三者应串联而非互相竞争：保存时格式化，提交前运行类型/lint/测试，PR 中审查语义、风险和缺失的验证。让人逐行挑格式会浪费审查带宽；让工具决定退款状态机是否正确也不现实。

### 高频辨析：覆盖率与测试质量

覆盖率回答“哪些代码被运行过”，测试质量回答“这些运行是否验证了重要行为并能可靠发现回归”。一条没有断言的测试可以提高覆盖率；一条对并发、权限或金额边界的精确测试即使只覆盖少量行也可能价值很高。查看覆盖率报告时，优先寻找关键代码从未执行的区域，再写有意义的场景，而不是为每行补一条只为变绿的断言。

## 9.8.1 从样例到性质：怎样判断测试真的在防错

一个测试的价值不由覆盖率数字决定，而取决于它是否能在错误发生时失败。样例测试针对已知输入输出，例如“库存为 1 时只允许一个订单成功”；**性质测试**声明更一般的规律，例如“任意合法批次扣减后，库存永不为负”“序列化再反序列化保持等价”“相同幂等键不会创建第二笔订单”，框架再生成大量输入寻找反例。性质必须可判定、可缩小失败输入，并避免把被测实现的同一错误复制进断言；它尤其适合解析器、金额计算、排序、状态机和协议转换。

**变异测试**会有意把条件反转、删除分支或改动常量，观察现有测试能否杀死这些变异；若一个明显错误仍全部通过，说明覆盖的路径可能没有被真正断言。它比行覆盖更接近“测试能不能抓 bug”，但成本高，适合关键金额、权限、状态转换或基础库，而不是把每个服务都跑到极慢。覆盖率仍有用途：它帮助发现完全未被执行的错误处理、边界分支和新代码；它不能证明断言正确、并发安全或业务需求完整。

并发和异步代码的测试要把不确定性纳入控制。不要用 `sleep(0.1)` 祈祷任务恰好执行完；让 fake 时钟、屏障、事件或可控队列明确安排“事务 A 已读取、事务 B 再提交”的交错，再断言冲突处理、取消和资源释放。对于跨数据库与队列的动作，集成测试至少应覆盖：事务回滚时没有可消费事件；提交后事件最终可投递；消费者在副作用成功、确认前崩溃后重复运行仍正确。后者不是单元测试能替代的，它验证的是系统承诺的恢复路径。

## 9.9 回归测试与质量门禁

**回归测试**是把一个已发现的缺陷、风险场景或关键承诺固定为自动检查。它不一定只在 bug 修复后写：一次线上事故、一次客户投诉、一次安全审计发现的绕过路径，都应评估能否转成测试。订单重复创建事故的回归测试应使用同一幂等键发送两次请求，并断言数据库只出现一张订单、两次响应具有一致结果；只测试“第一次成功”无法防止同一事故复发。

持续集成（CI）的目标是让每个变更尽早得到可信反馈。典型分层是：每次提交快速运行格式化、静态检查和单元测试；涉及数据库、协议或关键服务时运行集成测试；合并或发布前运行少量 E2E、迁移演练、安全扫描和必要的性能检查。不要把所有昂贵测试都塞进最短 PR 阶段，也不要把关键验证全部放到发布后。失败的测试不能长期标记为“已知 flaky”而继续忽略；应隔离其影响、登记负责人、收集失败样本并修复根因，必要时暂时从阻塞门禁中移出，但必须保留可追踪的恢复计划。

质量门禁不是为了让工具阻止人工作，而是把团队已经同意的最低标准自动化：代码能构建、依赖无已知高危漏洞、迁移可执行、类型检查通过、核心测试通过、审查完成。门禁越明确，例外越少依赖记忆和口头承诺；但门禁也不应把无意义的 100% 覆盖率、耗时一小时的全量 E2E 或易误报规则强加给每个小改动。好的门禁提供快速、可信、可解释的反馈。

## 本章练习

1. 为“订单金额为正、库存足够才预留”设计三条单元测试和一条数据库集成测试。说明为什么其中至少一条不能只用 Fake 数据库验证。

2. 团队为支付客户端的每个方法都用了严格 Mock，重构时即使外部行为未变也有数百条测试失败。应怎样调整替身使用？哪些交互仍值得验证？

3. 订单服务调用 `now()` 判断优惠券是否过期，CI 每月一两次在午夜失败。怎样修改设计与测试？若优惠券按用户所在地时区到期，数据模型还要保存什么？

4. 有报告称某些重复 Webhook 让积分增加两次。请写出最小复现需要的输入、观察点和回归断言；为什么只看异常栈不足以定位问题？

5. PR 将消息中的 `amount_cents: integer` 改为 `amount: number`，本服务单元测试全绿。应增加什么契约或集成测试，为什么不能只增加 E2E？

6. 某模块行覆盖率 98%，但一次生产事故来自未授权用户调用管理员导出接口。这个数字为什么没有阻止事故？应补哪些测试和审查问题？

## 练习参考答案

1. 单元测试至少覆盖：金额为零或负数时拒绝；库存等于请求量时允许；库存小于请求量时拒绝。集成测试可在真实 PostgreSQL 中执行带 `stock >= requested` 条件的更新，并并发运行多个预留请求，断言成功数不超过库存且最终库存不为负。Fake 数据库未必实现真实的条件更新、唯一约束、事务隔离和锁，因此不能代替这条边界验证。

2. 对只需驱动分支的付款结果使用 Stub；对需要保存结果供断言的邮件或审计端口使用 Spy；需要跑通简单流程时使用 Fake。严格 Mock 只保留给“调用本身就是需求”的交互，例如成功扣款必须携带相同 provider 幂等键、禁止未授权导出时绝不能调用导出器。业务状态和返回值应优先成为主要断言，避免锁死私有调用顺序。

3. 注入 `Clock` 或把当前时刻作为参数，在测试中固定 UTC instant，分别覆盖过期前、恰好到期和过期后；不要等待真实午夜。若规则是“当地时间当日 23:59 失效”，除 UTC 时间戳外还要保存或可推导业务时区、当地日历规则与 DST 处理方式，不能把服务器时区当用户时区。

4. 最小复现应包含同一个稳定 webhook/event id、相同用户和积分值、两次投递的顺序，以及数据库中积分流水与余额的初始状态。执行后观察唯一流水数、余额变化、消费者 ack/重试记录和外部调用 id；回归断言是重复投递后流水仍一条、余额仅增加一次。异常栈只显示哪里抛错或观察到错误，重复可能来自发送端重试、broker 重投、消费者在 ack 前崩溃或去重约束缺失，必须沿链路看证据。

5. 增加生产者和消费者共用或分别验证的 schema/契约测试，明确金额单位、整数性、范围、可选字段与版本规则；再以真实序列化器和 broker/测试服务器做集成测试。只增加 E2E 仍可能只覆盖一个双方都更新后的版本，无法保护独立发布、旧消费者或第三方消费者的兼容性。

6. 98% 只说明多数行执行过，未说明未授权分支是否被精确断言，也不保证权限中间件在真实路由上生效。应补单元测试验证权限策略、集成测试验证路由和认证上下文、E2E 测试验证未授权请求返回拒绝且没有生成导出文件；审查时应问“这项操作谁能执行、拒绝路径是否在副作用之前、日志是否记录审计信息”。
