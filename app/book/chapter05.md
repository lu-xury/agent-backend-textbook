关系数据库不是“把对象存进表格”的工具，而是一套把**业务事实、约束和并发修改**放在同一套规则里处理的系统。后端服务可以把订单、账户、库存、权限等长期事实交给数据库保存，并用 SQL 声明希望得到或改变什么；数据库再决定如何执行、如何在故障后恢复、如何让多个请求同时工作而不破坏数据。本章以 PostgreSQL 为例。语法会有方言差异，但数据建模、查询代价与并发控制的思考方式适用于多数关系型数据库。

## 5.1 从业务事实到关系模型

**关系（relation）**在关系模型中是“属性相同的一组元组”，可以把它理解为一个由列定义的逻辑集合。`user(id, email, created_at)` 描述的是用户这一类事实及其属性；一行是一个用户事实，一列是事实的一个维度。SQL 中的表是关系模型的工程实现，但二者不能机械画等号：SQL 查询结果通常按**多重集**处理，允许重复行；表中也没有天然顺序，`SELECT` 没有 `ORDER BY` 时，即使这次看起来按主键返回，下次也可能变。

例如在线商店至少有用户、商品和订单三类事实。订单行不应只保存“张三买了键盘”这一句自由文本，而应分别保存是谁下单、何时下单、当前状态和金额。一个简化的模式如下：

```sql
CREATE TABLE app_user (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email       text NOT NULL UNIQUE,
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE purchase_order (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id     bigint NOT NULL REFERENCES app_user(id),
  status      text NOT NULL CHECK (status IN ('pending', 'paid', 'cancelled')),
  total_cents integer NOT NULL CHECK (total_cents >= 0),
  created_at  timestamptz NOT NULL DEFAULT now()
);
```

这里 `id` 用来稳定地指向一行，`email` 是用户的业务标识，`status` 的取值范围、金额非负、订单必须属于已有用户，都是**数据库可验证的不变量**。把这些规则仅写在 Web 表单或某个服务函数中是不够的：脚本、后台任务、另一个服务和故障重试都可能绕开那段代码；约束靠近数据，才能覆盖所有写入入口。

四个建模问题是：这个实体是否有独立生命周期；它与其他实体是一对一、一对多还是多对多；哪些字段在创建后允许变；哪些事实必须永远成立。多对多通常需要中间表，例如 `order_item(order_id, product_id, quantity, unit_price_cents)`。把多个商品 ID 用逗号拼到 `orders.product_ids` 中，会让外键、按商品统计、库存校验和单项价格历史都变得困难。

### 范式是减少更新矛盾的工具，不是比赛规则

**规范化**的目标是让每个事实只在一个合理的位置维护，从而避免“同一事实改了一处、另一处没改”的更新异常。第一范式要求一个字段保存一个可操作的值而不是重复组；第二范式关注非键属性不能只依赖复合键的一部分；第三范式进一步避免非键属性经由另一非键属性间接决定。比如 `order_item(order_id, product_id, product_name)` 以 `(order_id, product_id)` 为主键时，`product_name` 只依赖 `product_id`，应放在 `product` 表中。初学时不必背定义，记住一个实用问题：如果修改某个事实必须同时更新很多行，或者删除一行会意外丢掉另一种事实，模式可能混淆了职责。

例如把 `order_item` 中的 `product_name`、`current_product_price` 当作“商品当前信息”维护，会在改名、调价时造成大量更新。商品当前名称应在 `product` 表；订单项只存当时成交的 `unit_price_cents`，因为它不是“当前售价”的复制，而是不可变的历史事实。**看似重复的字段不一定是冗余：关键在于它是否代表同一时刻、同一语义的事实。**

反规范化也并非错误。商品详情页的平均评分可以从评论实时聚合，也可以写入 `product.rating_avg` 以换取读取速度。后者必须明确谁更新、事务失败如何恢复、异步更新期间允许多旧的数据。正确顺序是：先有能保持正确性的规范化模型；用真实查询和指标证明瓶颈；再引入一个能验证、能重建的冗余字段，而不是凭直觉复制数据。

### 主键、外键和其他约束

**主键**是一行的首选身份，必须唯一且非空；一张表只能声明一个主键，主键可以由多列组成。自然键如身份证号、邮箱有业务含义，但可能因隐私、格式或更名而变化；代理键如自增整数、UUID 没有业务含义，通常更适合内部引用。使用代理键不表示放弃业务唯一性：邮箱仍应有 `UNIQUE` 约束。

**外键**要求子表的引用值在父表中存在，防止“孤儿订单”。删除或更新父表时的动作必须是业务选择：`RESTRICT` 拒绝仍被引用的删除；`CASCADE` 连带删除；`SET NULL` 保留子记录但解除关联。PostgreSQL 默认的 `NO ACTION` 与 `RESTRICT` 在可延迟约束时检查时点不同；普通业务更重要的是明确删除策略，而不是依赖默认值。绝不要因为省事把所有外键设成级联删除——删一个测试用户而删除付款记录，往往不是期望的业务行为。PostgreSQL 会为被引用的主键或唯一键建立/使用索引，但**不会自动为引用列建立索引**；若经常按 `purchase_order.user_id` 查订单，或删除用户时要检查其订单，应显式为该列考虑索引。

除 `NOT NULL`、`CHECK`、`UNIQUE`、`FOREIGN KEY` 外，数据库还可以用默认值、排他约束、触发器等表达规则。原则是优先使用声明式约束：它清晰、可被优化器理解、错误可预期；触发器适合确有必要的跨表派生或审计，但隐藏副作用较多，应少而明确地使用。

## 5.2 SQL：声明结果，而不是描述循环

SQL 是声明式语言。`SELECT` 说“要哪些行和列”，不是“先遍历数组，再调用函数”。优化器会依据统计信息和成本模型选择顺序扫描、索引扫描、哈希连接或合并连接。因此同一 SQL 在十行测试数据和千万行生产数据上的计划可能不同；调优应从工作负载和执行计划开始，而不是把查询强行翻译为应用层循环。

一个常见查询是“列出某用户最近已支付的十笔订单”：

```sql
SELECT id, total_cents, created_at
FROM purchase_order
WHERE user_id = $1 AND status = 'paid'
ORDER BY created_at DESC, id DESC
LIMIT 10;
```

`$1` 是参数占位符。**永远把外部值作为绑定参数传给驱动，不要用字符串拼接 SQL。**参数化既处理引号和类型，也防止 SQL 注入；它不等于可以把列名、排序方向随意参数化，这些标识符应来自有限白名单。`ORDER BY created_at DESC, id DESC` 中加入 `id` 是为了让同一时刻创建的订单仍有确定顺序；分页、游标和测试都依赖这种稳定排序。

连接的含义要讲清。`INNER JOIN` 只保留两侧能匹配的行；`LEFT JOIN` 保留左表全部行，右侧不匹配处为 `NULL`。若要“没有订单的用户”，应写 `LEFT JOIN ... WHERE o.id IS NULL`，或常用的 `NOT EXISTS`。把右表条件放在 `WHERE` 中可能把左连接意外变成内连接：

```sql
-- 错误地漏掉了没有 paid 订单的用户
SELECT u.id FROM app_user u
LEFT JOIN purchase_order o ON o.user_id = u.id
WHERE o.status = 'paid';

-- 若目标是保留所有用户，条件属于连接条件
SELECT u.id, o.id FROM app_user u
LEFT JOIN purchase_order o
  ON o.user_id = u.id AND o.status = 'paid';
```

聚合先分组后计算。`WHERE` 在聚合前过滤行，`HAVING` 在聚合后过滤组。窗口函数如 `row_number() over (partition by user_id order by created_at)` 能在不折叠行的情况下给每位用户的订单编号，适用于“每个用户最新一笔订单”等问题。遇到慢查询，先确认语义：少一个连接条件会把两张表相乘，再好的索引也救不了错误结果。

### 读懂执行计划

`EXPLAIN` 给出优化器估算的计划；`EXPLAIN (ANALYZE, BUFFERS)` 会真正执行查询并报告实际时间、实际行数和缓冲区 I/O。由于后者会执行写语句，分析可回滚的 `UPDATE` 或 `DELETE` 可用 `BEGIN; EXPLAIN (ANALYZE, BUFFERS) UPDATE ...; ROLLBACK;`；有外部副作用的程序调用不应在生产上随意分析。阅读计划可遵循三步：从缩进看输入树；比较每个节点的 `rows` 估计值与 `actual rows`；找总耗时、循环次数和读盘最多的位置。一个节点“估计 10 行、实际 100 万行”常意味着统计信息过旧、列之间存在相关性、谓词写法使估计困难，或参数值分布差异很大。

看到 `Seq Scan` 不要本能地加索引。若查询要返回表中很大比例的行，顺序读连续页面往往比反复通过索引随机取行更快；小表甚至全部在一个数据页里。反过来，索引不被使用也不必先怀疑数据库“笨”：条件可能对列进行了函数包装，索引顺序与谓词不匹配，或统计信息没有更新。应先在接近生产的数据分布上 `ANALYZE` 并收集计划，避免用一百行随机数据推断千万行表的选择。

## 5.3 索引：用写入成本换取定位速度

索引是额外维护的数据结构，记录键值与行位置或行版本。它能减少读取的数据页，却占磁盘、缓存和写入成本：一次 `INSERT`、`UPDATE`、`DELETE` 不仅改表，还可能改多个索引。**索引不是越多越好**；应围绕高频、耗时、选择性足够的查询设计，并定期检查是否真的使用。

PostgreSQL 默认且最常见的是 B-tree。可以把它看作页化的平衡搜索树：内部页保存分隔键并指向子页，叶子页按键有序，扇出很高，因此即使有大量记录，根到叶的层数也很少。范围条件、相等条件和与索引顺序一致的排序都适合 B-tree。它不是哈希表：哈希擅长等值定位，而 B-tree 的有序性同时支持 `>=`、`BETWEEN`、`ORDER BY`。全文、数组或 JSON 包含查询常需要 GIN；按物理位置高度相关的大型时间序列表可考虑 BRIN；选择索引类型应从操作符和数据分布出发。

为前述订单查询，一个常见索引是：

```sql
CREATE INDEX order_user_status_created_idx
ON purchase_order (user_id, status, created_at DESC, id DESC)
INCLUDE (total_cents);
```

**复合索引**的列顺序由查询决定，不是把所有常用列随意堆进去。对 B-tree，前导列上的等值条件最能缩小扫描范围，随后可接一个范围或排序列。索引 `(user_id, status, created_at)` 非常适合 `WHERE user_id = ? AND status = ? ORDER BY created_at`；仅按 `status` 过滤通常不能高效利用其有序前缀。新版 PostgreSQL 在某些低基数前导列场景可做 skip scan，但这是一项优化，不应推翻“按真实查询设计前导列”的基本原则。

`INCLUDE (total_cents)` 让 `total_cents` 存在于索引叶子项中但不参与键排序。若查询只需索引键和包含列，且可见性映射表明对应数据页的行对所有事务可见，PostgreSQL 可以进行 **Index Only Scan**，少回表读取堆表。把查询所需列放进索引常被称为“覆盖索引”设计，而 PostgreSQL 的具体执行方式叫 Index Only Scan；它不是保证：刚更新的数据页未必 all-visible，仍可能发生 heap fetch。这样的索引会增大索引和写入负担，所以只覆盖非常稳定、非常高频的读路径。

范围条件之后的键通常不能再缩小连续扫描的主要范围，但仍可能帮助索引过滤或特定排序/计划；复合索引不是只靠一条“最左前缀”口诀就能设计完，最终以实际参数的 `EXPLAIN` 验证。部分索引如 `CREATE INDEX ... ON purchase_order(created_at) WHERE status = 'paid'` 只保存满足条件的行，适合某状态极少但经常单独查询的情况。表达式索引如 `CREATE INDEX ... ON app_user (lower(email))` 只有当查询也使用相同表达式时才有用。对大小写不敏感邮箱查询，应同时决定唯一性语义，不能只加查询索引而允许 `A@example.com` 与 `a@example.com` 并存。

### 高频辨析一：索引与缓存

**索引**是数据库内部按键定位行的持久数据结构，仍以数据库中的当前事务语义为准；**缓存**是把结果或对象副本放到更快的位置，例如应用内存、Redis 或 CDN。索引通常不改变“谁负责数据正确性”，缓存却引入失效、过期、击穿和读旧数据的问题。订单按用户查得慢，先看是否缺少合适索引和是否返回过多列；不是一开始就把结果塞进缓存。缓存适合重复读多、允许一定陈旧或有明确失效协议的数据，不能替代约束和事务。

## 5.4 事务：把一组变化作为一个业务动作

**事务（transaction）**是数据库保证的一组读写操作单元。转账不是先把 A 扣款、过几秒再给 B 加钱的两个无关请求；它是“两个账户余额同时更新，或者一个也不更新”的业务动作：

```sql
BEGIN;
UPDATE account SET balance_cents = balance_cents - 1000
WHERE id = $1 AND balance_cents >= 1000;
-- 应检查受影响行数必须为 1，否则余额不足或账户不存在
UPDATE account SET balance_cents = balance_cents + 1000 WHERE id = $2;
COMMIT;
```

ACID 是理解事务的坐标，而非“数据库永远不会出错”的承诺。**原子性（Atomicity）**指事务的改动要么全部提交、要么全部回滚；**一致性（Consistency）**指提交前后满足数据库约束及应用定义的不变量；**隔离性（Isolation）**规定并发事务彼此可见的方式；**持久性（Durability）**指成功提交后，崩溃恢复仍能保留结果。以 PostgreSQL 为例，预写日志（WAL）等恢复机制支撑持久性；但“已提交”不等于已经同步到所有异地副本，也不等于外部支付平台已经完成扣款。

事务边界应围绕业务不变量，而不是“把一次 HTTP 请求从头到尾包住”。在事务里做远程 HTTP 调用、等待用户输入或上传大文件，会长时间占用连接、持锁或保留旧版本。更稳妥的模式是：短事务写入业务状态和 outbox 事件；事务提交后由后台工作者投递消息；消费者以幂等方式处理。这样无法得到跨数据库、消息队列和支付平台的魔法原子提交，却能把失败恢复设计得明确。

### 高频辨析二：事务与连接

**连接**是应用进程与数据库服务器之间的会话通道；**事务**是该连接中从 `BEGIN` 到 `COMMIT`/`ROLLBACK` 的工作单元。连接可以复用许多短事务，一个事务也必须在同一连接上完成。连接池借出连接时，借出的其实是会话状态：事务未结束、隔离级别被改过、临时表或 `SET` 参数遗留，都可能污染下一个请求。因此应用必须在归还连接前提交或回滚，并让驱动或池在归还时清理状态。

### 高频辨析三：原子性与幂等性

**原子性**约束一次事务内部“全成或全败”；**幂等性**约束同一个业务请求被执行多次后的可观察效果与执行一次相同。网络超时后客户端不知道服务是否已提交，重试可能使“创建订单”发生两次；即使每次创建都在原子事务里，重复仍会发生。解决方法是让客户端提供 idempotency key，并在数据库中对 `(user_id, idempotency_key)` 设唯一约束，保存第一次处理结果。原子性解决半完成，幂等性解决重复完成，两者通常需要同时具备。

## 5.5 隔离级别、MVCC 与锁

并发的难处不在“两个请求同时来”，而在它们基于相同旧值作决定。库存为 1 时，两个请求若都先读到 1，再把应用层算出的结果作为常量写回，例如都写成 0，就发生**丢失更新**：实际卖出两件，库存却只减少一件。若无条件执行 `stock = stock - 1`，PostgreSQL 会在行锁等待后基于新版本重新计算，库存可能变成负数；这同样是超卖，但原因不同。隔离级别定义允许看到什么中间状态、冲突时怎样阻止或报错。SQL 标准常用三种读异常说明差异：

- **脏读**：读到另一事务尚未提交、后来回滚的数据。
- **不可重复读**：同一事务两次读同一行，期间别的事务提交修改，读到不同值。
- **幻读**：同一事务两次按条件查询，期间别的事务插入或删除符合条件的行，第二次集合多了或少了。

PostgreSQL 的 `READ UNCOMMITTED` 实际按 `READ COMMITTED` 工作，因此不会脏读。`READ COMMITTED` 是默认级别，每条 SQL 语句获得一个新快照：同一事务的两次 `SELECT` 可能见到不同的已提交数据。`REPEATABLE READ` 在 PostgreSQL 中以事务级快照提供比标准最低要求更强的保护，通常不会出现上述三种读现象；但它本质上接近快照隔离，复杂读写决策仍可能发生序列化异常，并可能因并发更新报 serialization failure。`SERIALIZABLE` 让并发执行的效果等价于某个串行顺序；若数据库不能安全地安排，会中止其中一个事务，应用必须整体重试。提高隔离级别不是免费午餐：冲突、重试和长事务成本都可能上升。

**MVCC（多版本并发控制）**的思想是同一逻辑行在更新时产生版本，读取事务按自己的快照判断哪个版本可见。这样普通读取通常不需要阻塞写入，写入也不需要等普通读取结束；读者看旧的已提交版本，写者创建新版本。版本不是永远保留的，PostgreSQL 的 VACUUM 会在不再可能被任何事务看见后清理死元组。若事务长期不结束，旧快照会拖住清理，导致表膨胀和性能问题；“开事务后慢慢处理十万条任务”因此是危险做法。

### 高频辨析四：MVCC 与锁

**MVCC**解决的是“读哪个版本”的可见性，使许多读写可以并行；**锁**解决的是“两个操作能否同时改变或使用同一资源”。二者同时存在。两个事务更新同一行时，后者仍会等待或冲突；`SELECT ... FOR UPDATE` 会对选中的行取得最强的行级锁之一，另一个事务若要 `UPDATE`、`DELETE` 或取得与之冲突的行锁，通常会等到当前事务结束。PostgreSQL 还有较弱的 `FOR SHARE`、`FOR KEY SHARE` 等模式，是否等待取决于锁模式是否冲突；DDL、外键检查、唯一性检查也涉及不同粒度的锁。不要把“PostgreSQL 用 MVCC，所以没有锁”当成结论。

库存扣减可用一条带条件的 `UPDATE`，避免读—改—写窗口：

```sql
UPDATE product
SET stock = stock - $1
WHERE id = $2 AND stock >= $1;
```

受影响行数为 1 才表示预留成功。若业务必须先读取多行、再按它们的状态做决定，可在短事务内按固定顺序 `SELECT ... FOR UPDATE` 锁住相关行，并保持规则简单。可用乐观并发控制：表中加 `version`，更新时写 `WHERE id = ? AND version = ?`，受影响行数为零就提示或重试；它适合冲突较少、编辑操作可以失败后重试的场景。

**死锁**是事务 A 持有资源 1 等资源 2，事务 B 持有资源 2 等资源 1 的循环等待。数据库会检测循环并中止一个事务，应用收到错误后回滚并按策略重试。死锁的根治不是无限延长超时，而是所有代码路径以相同顺序锁定同类资源、缩短事务、避免用户交互置于事务内。锁等待超时和死锁不同：前者未必存在环，只是等得过久；两者都应在监控中记录 SQL、等待时间和事务上下文。

### 高频辨析五：脏读、不可重复读与幻读

这三个词的对象依次是“未提交的值”“同一行已提交后的变化”“满足条件的行集合变化”。面试回答不能只背定义，还应说出其含义：银行余额不能读到会回滚的扣款是防脏读；报表在一个事务内要看到同一快照是避免不可重复读；“今天未处理工单数量”若作为后续写入决策的前提，则要考虑新工单带来的幻读或更一般的序列化异常。具体数据库对标准级别的实现强度不同，必须查所用产品的文档，不能只搬标准表格。

## 5.6 连接池、ORM 与常见查询陷阱

建立数据库连接要经历网络握手、认证、进程或线程资源分配；无限制地为每个请求新建连接，会增加延迟并耗尽数据库可承受的并发。**连接池**复用少量已建立连接，并在数据库前形成背压：池满时请求等待或快速失败，而不是让几千条连接把数据库拖垮。池大小没有固定“最佳数字”，应同时考虑数据库 `max_connections`、所有服务实例总数、单查询耗时和数据库 CPU/IO。先限制每实例上限、设置获取超时和查询超时，监控池等待时间、活跃/空闲连接、慢查询和连接泄漏；再根据压测和生产指标调整。若有大量短连接客户端，可考虑 PgBouncer 等独立池；事务池中连接不再固定属于某个客户端，不能依赖跨事务会话状态，prepared statement 的支持与限制也取决于 PgBouncer 版本、配置和驱动行为。

ORM 能减少样板代码，却不能替你理解 SQL。最典型的 **N+1 查询** 是先查 100 个订单（1 条 SQL），然后循环对每个订单再查用户或订单项（100 条 SQL）。本地数据少时看不出问题，网络往返、数据库 CPU、连接池排队和 I/O 会在生产中放大。解决方案不是永远大 `JOIN`：对于多对一关系，可批量查询再按 ID 映射，或使用 ORM 的预加载；对于一对多关系，直接连接会把订单行按每个订单项重复，可能造成巨大结果集和错误分页。应按页面所需字段、基数和总量选择批量 `IN`、适当连接、两阶段查询或专门的读模型，并用查询数和计划验证。

### 高频辨析六：关系与表；主键与唯一索引

**关系**是逻辑模型中的同型元组集合；**表**是 SQL 中存放和操作数据的对象，SQL 允许重复行、物理存储也可能有行版本，因此不是纯数学集合。理解此差异能避免依赖隐含行顺序或把重复结果误判为数据库错误。

**主键**是该表选定的行身份，只能有一个，隐含唯一与非空；**唯一约束/唯一索引**用来表达其他不能重复的候选标识，例如邮箱、外部支付单号，一张表可有多个。在 PostgreSQL 中普通唯一约束默认允许多个 `NULL`，因为 `NULL` 表示未知且彼此不相等；若业务要求“最多一个空值”，需要改变模型或使用支持 `NULLS NOT DISTINCT` 的唯一约束。主键通常也会自动建立唯一 B-tree 索引，但“有唯一索引”不自动使字段成为业务上的主键。

## 5.7 分页、读写分离与一致性边界

列表接口必须指定稳定顺序。`LIMIT 20 OFFSET 100000` 的 offset 分页易理解，也便于跳到第 N 页；但数据库仍要走过前面大量行，页数越深越慢。并发插入或删除还会让用户在翻页时看到重复或漏项。**keyset（seek/cursor）分页**把上页末尾的排序键作为游标，例如按 `(created_at DESC, id DESC)`：

```sql
SELECT id, total_cents, created_at
FROM purchase_order
WHERE user_id = $1
  AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

它可从匹配排序的索引一次定位到游标之后，深页性能稳定，对连续“下一页”体验更好。例如此查询通常需要 `(user_id, created_at DESC, id DESC)`，或包含全部固定筛选条件的相应 B-tree 索引；没有它，keyset 的语义虽正确，性能却未必稳定。游标应包含完整排序键，通常编码成不透明 token；不能只用 `created_at`，否则同一时间的多行会跳过或重复。其代价是难以直接跳第 5000 页，也要定义若排序字段会修改时的行为。

### 高频辨析七：offset 分页与 keyset 分页

**offset 分页**使用“跳过多少行”，适合数据量小、需要任意页码、后台管理页；**keyset 分页**使用“从哪一个排序键之后继续”，适合大表、无限滚动、按时间浏览的 API。二者都不是天然一致性快照：若产品要求一次导出或逐页审核看到完全固定的集合，应考虑在同一事务快照中处理、物化待处理 ID，或把查询条件冻结。不要为了追求 keyset 而牺牲“跳页”这个真实产品需求。

读写分离常把写请求送到主库，读请求送到异步复制的副本，以扩展读取能力。它解决的是容量，不自动保证用户刚写完就能读到。用户更新资料后立即访问副本，可能因复制延迟看到旧资料。**读后写一致性**的常见做法是：关键读固定走主库；写后的一小段时间将该会话粘到主库；携带复制位置并等待副本追上；或让界面明确显示异步状态。是否接受陈旧读是业务契约，例如库存、权限和支付状态通常比推荐流更敏感。

### 高频辨析八：读写分离与一致性

**读写分离**是一种路由和扩容架构；**一致性**是读操作能看到哪一版本数据的语义。主从复制可以是同步或异步，不同实现的确认点不同。即使事务在主库已提交，异步副本仍可能滞后；即使使用同步复制，也需说清它保证哪些副本收到日志、故障切换时的读路由如何处理。面试中若只回答“读多写少就读写分离”，遗漏了延迟、故障切换和读己之写，答案是不完整的。

## 5.8 模式迁移、备份与恢复演练

数据库模式会随着程序演化。**迁移（migration）**是可版本化、可审查的模式或数据变更脚本，不是上线后手工在生产库敲命令。每次迁移应记录版本、按顺序执行、在预发布环境用接近生产的数据验证时间和锁影响。开发阶段可以重建数据库，生产环境却不能假设回滚总是安全：删除列后写入的数据无法凭空恢复，大表回填也可能耗时很久。

安全的兼容变更常采用 expand–contract：先新增可空列或新表，发布能同时读旧/新结构的应用，后台分批回填并校验，再把新列设为约束、切换读取，最后在一个独立版本删除旧列。这样旧版本与新版本短暂共存时仍可工作。对大表新增外键或检查约束，可先使用 `ADD CONSTRAINT ... NOT VALID`，再在合适窗口 `VALIDATE CONSTRAINT`；具体 DDL 与 PostgreSQL 版本的锁行为仍应先在预发布验证。PostgreSQL 多数 DDL 可以放在事务中，但不是全部；例如 `CREATE INDEX CONCURRENTLY` 不能在事务块内运行。大表加非空约束、默认值、索引或外键之前，都要查运行时间，必要时选择并发建索引、分批回填和低峰执行。

备份回答的核心不是“我每天跑了 pg_dump”，而是“我能在目标时间和目标恢复点恢复，并验证恢复结果”。RPO（最多允许丢失多少时间的数据）决定备份与 WAL 归档频率；RTO（允许多长时间恢复服务）决定备份介质、恢复流程和演练容量。`pg_dump` 产生逻辑备份，适合导出单库/对象、跨版本迁移和可读审查；恢复大库或精确恢复到某一时刻通常还需要物理基础备份与归档 WAL，形成 PITR（point-in-time recovery）能力。备份必须放在与主库故障域不同的位置，至少加密、限制访问、监控成功与大小变化；更重要的是定期在隔离环境**实际 restore**，检查目标时间点、角色/权限、扩展、应用迁移版本、关键表行数和一次只读业务校验。没有演练过的备份只是希望，不是恢复能力。

## 5.9 复习：高频问题的短答

1. **为什么外键不能只靠应用层校验？** 因为写入入口不止一个，且并发下“先查存在再插入”会有竞态；外键把引用完整性作为提交时的数据库规则。它不替代业务授权和删除策略。
2. **为什么加了索引查询仍慢？** 可能返回比例太高、谓词无法匹配索引、统计信息过旧、连接条件错误、回表和随机 I/O 成本高。用真实参数的 `EXPLAIN (ANALYZE, BUFFERS)` 定位，不要凭猜测。
3. **事务是否等于锁？** 不等于。事务定义一组操作的原子提交和隔离语义；锁是并发控制的一种机制。MVCC 下普通读通常不阻塞写，但写冲突和显式锁仍存在。
4. **Serializable 是否让代码不需要重试？** 不会。它可能主动中止无法安全串行化的事务；应用应对 serialization failure 做有限、带退避的整体重试，并保证副作用不会重复。
5. **N+1 为什么不只是性能小问题？** 查询次数随列表长度线性增加，连接池排队和网络往返会放大延迟，并可能拖慢同库其他请求；但解决时要防止一对多 JOIN 造成行爆炸。

## 5.10 练习与参考答案

**练习 1：** 为“用户最近已支付订单”设计表约束和索引。要求邮箱不可重复，金额非负，订单必须引用存在用户，查询返回 `id`、`total_cents`、`created_at`，按创建时间倒序。

**答案：** `app_user.email` 使用 `NOT NULL UNIQUE`；订单的 `user_id` 用外键、`total_cents` 用 `CHECK >= 0`，状态用枚举或 `CHECK`。可从 `(user_id, status, created_at DESC, id DESC) INCLUDE (total_cents)` 开始验证。它匹配等值过滤和排序；是否保留 `INCLUDE` 应看 Index Only Scan、写放大和实际读取比例，而不是机械添加。

**练习 2：** 两个请求都要购买最后一件商品。为什么“先 `SELECT stock`，在应用层计算后把结果常量写回”不安全？无条件 `UPDATE stock=stock-1` 的问题又是什么？给出一种 SQL 方案。

**答案：** 两个请求可能都读到 `stock=1`，随后都把应用层计算出的 `0` 写回，产生丢失更新：卖出两件，库存却只少一件；无条件的 `stock=stock-1` 则可能扣成负数。可使用 `UPDATE product SET stock=stock-$1 WHERE id=$2 AND stock >= $1`，以受影响行数判断成功；若还要创建订单，应把扣库存和订单写入放到同一短事务。复杂的跨行决策可在固定顺序下 `SELECT ... FOR UPDATE`，或使用版本列做乐观并发控制。

**练习 3：** 为什么 keyset 分页要使用 `(created_at, id)` 而非只有 `created_at`？它何时不如 offset？

**答案：** 单独时间戳通常不唯一，会使边界同时间的行重复或遗漏；复合排序键形成总顺序，游标也必须带两列。keyset 不适合直接跳到任意远页，若产品必须精确显示页码并允许跳转，offset 或预先物化结果集可能更合适。

**练习 4：** 一个支付创建接口已使用数据库事务，客户端超时后重试仍创建了两笔支付。缺少什么？

**答案：** 缺少跨请求的幂等设计。为调用方提供 idempotency key，在支付表上建立恰当唯一约束，并将第一次结果与该键关联；冲突时返回已完成或处理中结果。事务保证单次写入不半完成，不能判断客户端重试是不是同一意图。
