一个后端服务在刚上线时，往往只有“收到请求，查询数据库，返回结果”这一条直线。用户量增长以后，直线会暴露两个事实：数据库和下游服务的处理能力有限；请求也不会均匀地到来。一次热点活动、一段异常重试代码，甚至一台实例变慢，都可能让原本可用的系统在几分钟内耗尽连接、线程和 CPU。本章讨论的缓存与流量保护，目的不是把系统变得“永远不出错”，而是**在资源不足或依赖异常时，把正确、有限、可恢复的服务留给更多用户**。

贯穿本章的例子是“内容平台”的 `GET /articles/{id}` 接口。文章正文存于 MySQL，文章浏览量和短期热点状态放在 Redis；首页推荐依赖一个可能变慢的推荐服务。这个例子足够小，却包含了大多数业务服务会遇到的读多写少、热点、限额和下游故障。

## 6.1 缓存首先是一份副本

**缓存（cache）**是为了更低延迟、更少访问昂贵资源而保存的可复用副本。它不是“更快的数据库”这一抽象替代品。对文章服务而言，MySQL 中已提交的 `articles` 行才是正文、作者、发布时间的**真源（source of truth）**；Redis 中的 `article:42` 只是某个时刻的副本。承认这一点会立刻带来设计上的约束：缓存可以丢，缓存可以过期，缓存也可能暂时旧；但不能因为缓存丢失而凭空改写业务事实。

把缓存当作副本，能帮助我们先回答三个问题。第一，能否容忍读到旧值，以及最多旧多久？文章浏览数晚几秒显示通常可接受，余额和库存通常不可接受。第二，副本失效时能否安全地回源？文章详情可以查库，昂贵的报表查询则可能把数据库压垮。第三，写入以后谁负责让副本接近真源？答案决定了更新顺序和故障恢复方式。

缓存的收益可粗略表示为：平均延迟约为 `命中率 × 缓存延迟 + 未命中率 × 回源延迟`。例如 Redis 命中耗时 1 ms，查库耗时 20 ms，命中率从 90% 升到 99%，平均延迟会从约 2.9 ms 降到约 1.19 ms。但不能只追逐命中率：错误地把每个用户的一次性搜索结果缓存七天，命中率也许不错，却消耗内存、制造旧数据，并让失效逻辑难以理解。

### 真源与缓存：面试常问的第一层辨析

**缓存与数据库真源的区别**不在于“一个在内存、一个在磁盘”，而在于事实由谁定义。数据库也可以在内存中，Redis 也可以开启持久化；这些都不改变业务上的权威性。若订单表是唯一可审核、可约束、可恢复的记录，订单状态应以它为准。缓存只保存“订单当前显示为已支付”的投影。面试中若被问“Redis 持久化了，能当主库吗”，应先讨论一致性、查询能力、事务约束、恢复目标和业务容错，而不是把答案简化为某个产品“能”或“不能”。

## 6.2 三种常见读写路径

缓存策略说的是：读或写发生时，应用、缓存和真源分别做什么。没有一种策略天然最好；关键是数据的新鲜度要求、回源成本和团队能否可靠实现失效流程。

**Cache-aside（旁路缓存）**由业务应用主动管理缓存。读文章时，应用先 `GET article:42`；命中就返回；未命中才查 MySQL，把结果以带 TTL 的形式写入 Redis，再返回。写文章时，最常见的做法是先更新 MySQL，成功提交后删除 `article:42`。下一次读取自然会从 MySQL 装入新副本。它的优点是透明、灵活，适合绝大多数“数据库是真源”的业务；代价是每个读写路径都必须正确处理缓存。

```text
读：Redis 命中 → 返回；Redis 未命中 → MySQL → SETEX Redis → 返回
写：事务提交 MySQL → DEL Redis（失败则可靠地重试删除）
```

这里特别容易犯的错误是“先删缓存，再更新数据库”。如果删除后到数据库提交前有一个请求到来，它会查到旧数据库值并把旧值重新写回缓存；此后数据库虽然更新，旧缓存却可能活很久。**先更新真源、再删除缓存**并不能让所有并发瞬间完全线性一致，但把错误窗口缩小到了更可控制的方向。删除失败也不能被忽略：可以通过事务消息、变更日志订阅或带退避的任务重试补删，并保留 TTL 作为最后一层自愈。

**Read-through（读穿透缓存）**把“未命中后到真源加载”的责任放到缓存库或封装层。应用只请求 `cache.get(key)`，封装层在缺失时查询加载器并填充缓存。这能减少业务代码重复，尤其适合大量读模型相似的服务；但必须看清封装层的语义：它是否会合并并发加载、加载失败如何传播、能否按租户或权限生成正确键。Read-through 不是“没有回源”，只是把回源从业务函数移动到了组件内部。

**Write-through（写穿透缓存）**要求一次写操作同时同步写入真源和缓存，应用只面向这一层写。它适合读后立刻要求看到新值、并且写量不高的数据，例如用户资料的展示副本。同步双写意味着更长的写路径和更复杂的失败处理：数据库成功而缓存失败怎么办？缓存成功而数据库失败又怎么办？若真源必须可靠，最终仍应以真源提交结果为准，缓存失败通常应删除或让其失效，而不是把缓存中的成功错当作业务成功。

有的系统还使用 **write-behind（异步回写）**：先写缓存，稍后批量落库。它能吸收高频计数写入，却会在缓存故障时丢失尚未落库的数据，因此只适用于可以补偿或容忍少量丢失的场景，如非结算性质的浏览计数；不能直接用于账户余额。

### 缓存更新与缓存删除：不要只背“删缓存”

“更新数据库后删除缓存”是 cache-aside 的常见默认，而不是放之四海皆准的口令。删除比直接更新副本更稳妥，是因为复杂对象可能被多处缓存，写请求很难知道所有派生键；删除让下一次读取从真源重建。但对于严格要求读己之写的页面，可以在数据库提交后同步更新一个明确的单键，或在短时间内把刚写入的版本直接返回给当前用户。无论选更新还是删除，都要处理并发乱序：给对象加版本号、让较旧版本不能覆盖较新版本，往往比无限增加“再删一次”的技巧更可验证。

## 6.3 TTL、失效与缓存一致性的现实边界

**TTL（time to live，存活时间）**是缓存项在多久后不再可用的上限。它解决两类问题：业务忘记主动失效时，副本最终会自行消失；缓存容量有限时，旧数据不会永久占据空间。TTL 不等于缓存一定在精确的某一毫秒被物理删除。Redis 会在访问键时检查过期，也会周期性清理过期键；对调用方更重要的语义是“过期键不应再作为有效值返回”，而不是依赖某一时刻内存一定已经回收。

TTL 的设置来自业务，而不是从“30 分钟”这样的习惯数字开始。商品价格可能要求数秒内收敛；个人头像更新后晚一分钟可接受；配置开关更适合事件驱动失效并用短 TTL 作保险。若设置过长，数据旧的风险增大；过短，回源和写入放大；没有 TTL，则一次失效失败可能永久污染结果。为避免许多键在同一秒失效，常给基础 TTL 加随机抖动，例如 `3600 ± 300` 秒。抖动不是提高缓存命中率的魔法，而是把同时回源的尖峰摊平。

缓存与真源之间通常只能做到**最终一致**：写已提交后，在失效消息传播、旧请求完成和下一次加载之间，少数读取可能暂时看到旧副本。若业务不能接受这个窗口，就应把关键判定放回具有事务或条件更新能力的真源，而不是声称“把 TTL 调小即可强一致”。例如下单扣库存必须在数据库中用条件更新或事务确认可售数量；商品详情页展示库存则可以来自短 TTL 缓存。

一个隐蔽的竞争如下：请求 A 未命中，查到了旧数据库值；请求 B 更新数据库并删除缓存；随后 A 才执行 `SETEX`，将旧值重新放回。对这种“旧读晚写回”，可靠的收敛方式是让真源和缓存值携带单调版本，并在写回前确认读取版本仍是当前版本；必要时用脚本或条件写拒绝旧版本覆盖新版本。较短 TTL 只能缩短旧值存活时间。单键请求合并解决的是多个未命中同时重建的**击穿**，可降低数据库压力，却不能单独解决这里的读写乱序。重要的是明确保证级别：很多内容类服务只保证最终一致，并不值得为极小窗口引入极高复杂度。

### 多级缓存：L1 更快，也让失效从一份变成 N 份

高频读路径常在进程内设置 L1 缓存，再以 Redis/CDN 作为共享 L2，最后回源数据库。L1 避免网络往返，适合体积小、读远多于写、允许短暂陈旧的数据；但十个应用实例就有十份互相独立的副本。更新数据库并删除 Redis，并不会自动删除每个进程里的旧对象。应给值携带版本或 `updated_at`，通过事件通知各实例失效，并用较短 TTL 作为通知丢失后的收敛保险；事件可重复、乱序和延迟，所以收到旧版本失效事件时不能反过来覆盖新值。

多级缓存的读取顺序也要防止级联击穿：L1 未命中后先查 L2，L2 未命中才以单飞/有界并发回源；Redis 故障时，不能让每个实例把全部未命中流量直接放大到数据库。权限、账户冻结、Secret 撤销和余额等要求快速生效的判定，通常不适合依赖一个无法集中失效的长 TTL L1。若确实缓存，应把版本检查或权威判定留在关键写路径，并把“最多陈旧多久、通知丢失如何收敛、实例启动如何预热”写成协议。

## 6.4 三类缓存事故：穿透、击穿和雪崩

这三个词都表现为“缓存没有挡住数据库”，但根因与处置不同，不能混用。

**缓存穿透**是请求的键在缓存和真源中都不存在，攻击者或异常客户端反复请求 `article:-1`，每次都穿过缓存查数据库。先做参数校验和权限校验：负数 ID、格式错误的 UUID 不应被送进数据库。对于“合法格式但确实不存在”的文章，可短时间缓存空值或 404 结果，这叫**负缓存**；TTL 必须较短，因为对象可能稍后被创建。数据集相对稳定且查询键规模很大时，可在入口使用 Bloom Filter。它能以较小内存判断“该元素一定不在集合中”或“可能在”，后者还要查缓存/数据库；它允许假阳性，不能把“可能在”当作真实存在。

**缓存击穿**针对的是一个或少数极热的真实键。热门文章刚过期，成千上万请求同时发现未命中，于是同时查 MySQL。解决重点是**合并同一份重建工作**：第一个请求获得很短的重建租约，其他请求等待少量时间、返回旧值或快速失败；也可以让缓存保留逻辑过期的旧值，由后台单飞刷新（stale-while-revalidate）。对确定的长期热点，预热和不设置短物理 TTL 也可行，但仍要准备内容变更时的主动失效。

**缓存雪崩**是大量不同键同时失效，或整个 Redis 集群不可用，导致大范围请求同时回源。给 TTL 加抖动只能解决“同批设置同批过期”，不能解决 Redis 整体故障。还需要缓存集群的容量与故障演练、数据库回源限额、服务端降级、客户端有界重试，以及把非关键请求拒绝在更靠前的位置。雪崩是系统级问题；单独给每个 key 加锁并不能阻止数百万不同 key 回源。

### 负缓存与空值：有用但不等于永久记录

负缓存是“缓存一个不存在的查询结果”，空字符串、特殊 JSON 或单独的标志位都可以实现。它的价值是阻断重复无效查询，风险是把“暂时不存在”误当成“长期不存在”。例如用户刚注册，先前对其资料的 404 负缓存尚未过期，就会造成短暂看不见新资料。因此负缓存 TTL 通常比正常对象短，且创建对象时应主动删除对应负缓存。不要用 `null` 的真假判断混淆“缓存未命中”和“命中了空值”，封装 API 应明确返回 `hit` 与 `value` 两个维度。

## 6.5 Redis：适合保存什么，也不适合替谁承担责任

Redis 是以内存为主的数据存储，提供字符串、哈希、列表、集合、有序集合、流等结构及其原子操作；它还提供复制与不同持久化选项。[Redis 官方概览](https://redis.io/docs/latest/get-started/) 列出的这些能力解释了它为何既常被当作缓存，也常被用于会话、排行榜、短期计数和消息流。

**String**适合序列化后的文章、验证码、计数器和锁令牌；`INCR` 对单键递增是原子的。**Hash**适合字段较多但常局部读取的对象，如 `user:7` 的昵称和头像版本；不要因为 Hash 名字像“对象”就把几十 MB 文档塞进去。**List**适合简单队列或最近记录，但消费者确认、重试和多消费者语义要谨慎。**Set**适合去重、标签和集合关系；**Sorted Set（ZSET）**通过分值排序，适合排行榜、按时间范围取记录和滑动窗口计数。**Stream**提供追加日志、消费者组和待确认条目，适合需要显式消费状态的事件流。选择结构应从要执行的原子操作出发：若需求是“某用户一分钟内第几次访问”，原子 `INCR` 加过期比取出 JSON、在应用中加一、再写回更可靠。

Redis 的内存并非无限。要为最大内存和淘汰策略作明确选择，并监控 `used_memory`、命中率、过期数、淘汰数、慢命令、连接数和复制延迟。淘汰策略意味着 Redis 在内存紧张时可能主动丢失某些键；因此缓存键本就要可重建。把不可重建的账务事实与大量可淘汰缓存混在一个实例和同一种淘汰策略下，是很危险的配置。

### 持久化与复制不是“自动高可用”

RDB 快照会在某些时刻把内存数据写成紧凑文件，恢复快、适合备份，但故障时可能丢失上一次快照之后的数据。AOF（append-only file）记录写命令，恢复时重放；按 `fsync` 策略可在性能与可能丢失的最近写入之间取舍。Redis 官方的[持久化说明](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)强调 Redis 提供多种落盘选项；应把它们看成恢复目标的选择，而不是替代业务数据库的统一承诺。

主从复制通常是异步的：[官方复制文档](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)明确说明副本确认与主节点处理并非同步。于是刚写到主节点的键可能尚未到副本；主节点故障切换后，客户端可能读到旧值，最近写入也可能丢失。Redis Cluster 同样存在异步复制下网络分区期间丢写的窗口。[Cluster 规范](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)对此有明确的写安全说明。对缓存，这通常可接受；对支付成功、库存扣减等业务事实，不能只靠复制来证明正确性。需要的是具备正确事务/条件约束的真源，或按业务目标选择共识与持久化方案。

## 6.6 分布式锁：只在“协调”确实是问题时使用

单进程的互斥锁只能协调同一个进程内的线程；多个服务实例同时处理同一资源时，才可能考虑**分布式锁**。典型且相对合适的用途是：热门文章缓存失效时，只允许一个实例重建；同一份离线任务只希望一个执行者启动。它不应被用来替代数据完整性约束。

以单 Redis 实例为例，获取锁至少应是带过期时间的原子条件写入：`SET lock:article:42 <随机令牌> NX PX 3000`。随机令牌属于持有者身份；释放锁不能只执行 `DEL`，而要以 Lua 脚本原子地“比较令牌相同才删除”，避免 A 的锁过期后 B 已取得新锁，A 却误删 B 的锁。TTL 是防止持有者崩溃后永久死锁的保险，但它也引入难题：A 因 GC 暂停或网络阻塞超过 3 秒，锁已过期，B 开始执行，A 恢复后仍可能写入，于是两个执行者并存。

因此，锁适合把重复工作从“常态”变为“少数异常”，而不适合承担绝对排他性的金融语义。对必须禁止旧执行者写入的资源，应使用**fencing token（递增栅栏令牌）**：资源服务只接受比自己已见令牌更大的写入。或者干脆在数据库以唯一索引、条件更新和事务维护不变量。Redis 的[分布式锁文档](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)给出了 Redlock 等方案；但即使多节点锁减少单点故障，也不能消除时钟、暂停、网络分区和下游不识别旧持有者的问题。设计时先写下“锁失效期间两个执行者同时运行，最坏会怎样”，再决定它是否可接受。

### 分布式锁与数据库约束：谁保证什么

**分布式锁**试图在操作开始前减少并发竞争，属于协调机制；它可能超时、失效或因为故障出现双持有者。**数据库唯一约束/条件更新**在提交事实时拒绝不合法状态，属于正确性机制。例如“每个用户只能领取一次优惠券”应在领取记录上建 `(user_id, coupon_id)` 唯一索引；Redis 锁可减少重复计算，却不能替代唯一索引。正确姿势经常是二者并用：锁削峰，数据库约束兜底。

## 6.7 速率、配额、并发与队列：先区分要保护什么

**限流（rate limiting）**限制一段时间内允许开始的请求数，例如每个 API Key 每秒最多 100 次；**配额（quota）**限制较长周期累计可消耗的额度，例如每个组织每天最多生成 1 万份报告；**并发限制（concurrency limiting）**限制正在执行的请求数，例如推荐服务同时最多处理 200 个推理。它们都可能返回 429 或拒绝请求，却解决不同问题。限流控制到达速度，配额控制总量和商业/公平规则，并发限制控制当前占用的连接、线程、GPU 或下游容量。

**QPS**是每秒开始或完成的请求数量，**并发数**是在某时刻尚未完成的请求数量。两者由平均响应时间联系，而不是可以互相替换。按 Little 定律的直觉形式，`并发数 ≈ QPS × 平均响应时间`：100 QPS 的接口若平均耗时 50 ms，平均同时在途约 5 个；一旦下游变慢到 5 s，即使 QPS 不变，在途就可能膨胀到 500 个，耗尽线程池。故障时只按 QPS 限流不够，还要限制并发和排队。

**背压（backpressure）**是下游或消费者把“我处理不过来”的信号传回上游，使上游减速、排队或丢弃，而不是无限制积压。HTTP 的 429/503 与 `Retry-After`、消息队列的消费者拉取上限、RPC 客户端的在途请求上限都可以承载这种信号。队列不是背压的反面：有界队列可吸收短暂波动；无界队列只是把拒绝延后为内存耗尽和极长延迟。排队后已经没有业务价值的请求，应该被丢弃或降级，而不是为了“最终都处理”拖垮整个服务。

## 6.8 四种常见限流算法

**固定窗口计数器**把时间切成固定段。例如键 `rate:u7:202608051530` 的 TTL 为一分钟，`INCR` 后若值超过 60 就拒绝。它实现简单、适合大多数 API，但边界会放大流量：用户在 12:00:59 发 60 次、在 12:01:00 再发 60 次，极短时间内实际有 120 次。Redis 中 `INCR` 与首次设置过期要放在 Lua 脚本或事务式封装中，避免进程崩溃留下永不过期计数键。

**滑动窗口**按“过去连续 60 秒”计数，消除固定窗口边界问题。精确实现可将每次请求写为 ZSET 的**唯一成员**，例如 `毫秒时间戳:随机后缀`，并以时间戳作分值；在同一 Lua 脚本或原子函数中删除窗口外成员、检查当前数量、决定是否加入并设置键过期。只把时间戳当成员会使同一毫秒的请求互相覆盖；把这几步拆给多个客户端，又会在检查与加入之间出现竞态。代价是每个请求都存一条记录，热门用户会占用更多内存。工程中也可用滑动窗口计数近似：保留当前窗口与上一个窗口的计数，按已过去的比例加权。精确度、内存和实现复杂度之间需要取舍。

**令牌桶（token bucket）**以速率 `r` 向容量 `b` 的桶补令牌，请求消耗一个或多个令牌；桶满后新令牌丢弃。它允许最多 `b` 的短时突发，同时把长期平均速率限制在 `r`。例如桶容量 20、每秒补 10 个，空闲后用户可立刻发 20 个请求，随后稳定在每秒 10 个。API 网关常喜欢令牌桶，因为“偶尔连点”不必被严厉惩罚。

**漏桶（leaky bucket）**把进入的请求排队，并以近似固定速率流出；队列满时拒绝。它更强调平滑输出，适合保护一个吞吐稳定的下游。它与令牌桶的差异是：令牌桶约束的是准入，允许已积累的令牌造成突发；漏桶约束的是离开速率，通常会把突发变成等待或丢弃。很多资料把两者都称作“限流”，面试回答应从是否允许突发、是否排队和延迟上区分，而不是只画一个桶。

分布式限流还要确定**限流键**：按 IP 会误伤公司 NAT 后的许多人，按用户 ID 需要先认证，按 API Key 适合合作方，按租户可保护付费公平。常常需要多层叠加：边缘按 IP 抵御攻击，网关按租户实行套餐，上游服务按下游资源设置全局并发上限。所有限制都应返回可理解的错误，并记录被拒绝的维度与数量；否则团队无法判断是攻击、产品增长还是阈值过低。

## 6.9 熔断、降级和负载丢弃

当推荐服务错误率急升、延迟显著增大时，继续把所有首页请求转发过去，会占满调用线程，并让重试流量进一步放大故障。**熔断器（circuit breaker）**针对这个依赖状态工作：关闭（正常放行）时收集最近失败/慢调用；超过阈值后打开，后续请求立即失败或走备用结果；等待一段时间后进入半开状态，只放少量探测请求，成功才重新关闭。熔断判断应结合错误种类和超时比例，不能把用户 4xx 或参数校验错误算作下游故障。

**降级（degradation）**是当资源不足或依赖不可用时，主动提供较弱但仍有价值的结果。例如首页推荐服务熔断后，改为展示“近期热门文章”；文章详情页的个性化点赞状态不可用时，仍返回正文并标记该字段缺失。熔断是控制“是否调用某依赖”的机制，降级是决定“不调用后向用户提供什么”的产品与业务策略。它们可以一起用，也可以单独存在：某个功能可因容量不足而降级，即使依赖尚未被熔断。

**负载丢弃（load shedding）**则是在本服务接近容量时拒绝一部分请求，给最重要的请求留下资源。Google SRE 对级联故障的讨论指出，过载是常见根因，且在总负载超过总容量时，上游丢弃一部分流量（包括重试）能阻止故障扩大。[《Site Reliability Engineering》关于级联故障](https://sre.google/sre-book/addressing-cascading-failures/)与[生产服务实践建议](https://sre.google/sre-book/service-best-practices/)都强调测试过载模式、限制重试和提供降级结果。应优先丢弃预取、分析、非登录爬虫等低优先级流量；而不是随机丢弃所有请求后再宣称系统“很公平”。

重试必须从属于流量保护。只对暂时性、幂等或具有幂等键的操作重试，设置总时间预算、次数上限、指数退避与随机抖动。若三层调用链都设置“**总共最多三次尝试**”，最坏可能把一次用户操作放大为 `3³ = 27` 次下游调用；若每层是在首次之外再重试三次，则会是 `4³ = 64` 次。更糟的是许多请求在服务端其实已经执行完成，只是响应在网络中丢失；对创建订单等写操作，应使用幂等键查询既有结果，而不是盲目再写一遍。

### 熔断与降级：两个经常被混为一谈的词

**熔断**根据观测到的依赖健康度临时停止调用，核心是保护调用方及依赖；**降级**是在能力不足时选择较低质量的功能或结果，核心是保留用户可用价值。例子中，连续超时后打开推荐服务的熔断器；首页改为热门文章是降级。若只熔断不设计替代结果，用户得到的只是错误；若只做降级却仍不断调用已经故障的依赖，线程和连接仍会被耗尽。

## 6.10 把机制组合成文章服务的防线

`GET /articles/{id}` 可以这样工作。网关先校验 token，并按用户限 20 QPS、按 IP 限较宽的突发阈值；服务自身只允许 500 个文章请求在途，多出的请求迅速返回 503 与短 `Retry-After`。应用随后读 `article:{id}:v{schemaVersion}`：命中直接返回；命中负缓存则返回 404；未命中时以单飞方式让一个请求查 MySQL，其余请求短暂等待或使用仍可接受的旧版本。若 MySQL 的连接池已经接近饱和，服务不再让每个未命中都排队，而是优先服务缓存命中与已登录读者，低优先级预览请求降级。

编辑文章时，在**同一数据库事务**中写入新内容、版本号和一条 `article_changed` outbox 记录；提交后由中继任务发布事件，并按版本删除或更新相应缓存键。中继可以重复投递，因为失效操作必须幂等；它暂时失败时，outbox 记录仍在，之后会重试。仅在事务提交后由应用直接发事件，不能避免“数据库已提交、进程在发事件前崩溃”的丢失窗口。正文缓存设置随机化 TTL，防止同步过期。浏览数由 Redis `INCR` 累计后异步聚合，明确标注为近实时统计，不能拿它做结算。推荐服务慢时，熔断器停止远程调用，首页返回热门文章；操作面板同时显示缓存命中率、回源 QPS、拒绝率、在途数、队列长度、依赖 p95/p99 延迟和熔断状态。这样，缓存、限流和熔断不再是三段互不相干的代码，而是围绕“真源不被打穿、关键请求能完成、用户知道发生了什么”的同一套边界。

这套设计仍会失败：Redis 整体不可用时，命中率降为零；数据库读副本延迟时，刚编辑文章可能暂时读旧；锁持有者暂停时，单飞可能重复执行。因此上线前要用压测与故障注入验证每一种失效路径：关闭 Redis、让推荐服务延迟 10 秒、让数据库连接池只剩 10 个连接、在活动开始瞬间制造十倍流量。正确的指标不是“完全没有错误”，而是核心读写在可预期的延迟与错误预算内恢复，且没有把局部问题放大成全站不可用。

## 6.10.1 Redis 的运行语义：快不等于没有数据结构和故障模型

Redis 的常用值类型服务于不同访问模式：String 适合小对象、计数器和简单缓存；Hash 适合按字段读取的对象；List 适合两端队列；Set 适合去重和集合运算；Sorted Set 以成员与分数维护有序集合；Stream 记录追加事件及消费组状态。选择类型时先定义读取、更新、范围查询、过期和容量需求；把一个巨大的 JSON 文档塞进 String 后频繁读改写，会放大网络与序列化成本，也让字段级并发更新变得困难。Redis 单个命令通常原子，但“读一个键—在客户端判断—再写另一个键”不是原子事务；需要同一 Redis 实例内的短逻辑原子化时可使用条件命令、事务或受控 Lua 脚本，并限制脚本执行时间。

TTL 不是精确到毫秒的后台删除承诺：键会在访问时被被动检查，也会由服务器主动抽样清理；业务不能把“过期后一定立刻消失”当作权限撤销或付款时钟。内存触及 `maxmemory` 时的淘汰策略决定是淘汰部分键还是返回错误，必须与缓存可丢失、会话可否失效、队列数据能否丢失的业务要求匹配。把 Redis 同时用作缓存、会话、限流和可靠队列时，应分开内存上限、监控与故障域，否则一次缓存热点就可能逐出登录态或任务状态。

复制通常是异步的：主节点成功返回并不代表副本已经拥有该写入，故障切换可能丢失最近确认的数据或使读取短暂回退。持久化、复制、Sentinel/Cluster 选主各解决不同问题；Cluster 的分片可扩容量，却要求多键操作位于同一哈希槽或改变建模。因而 Redis 很适合把可重建、可过期、可降级的数据放在内存近处；对于余额、订单和唯一约束，仍应以具备事务与恢复语义的真源为裁判。

Redis Cluster 把键映射到固定的 **16,384 个 hash slot**；同一 slot 再归某个主节点负责。它不是一致性哈希的别名。键名中的 hash tag 可以让一组相关键按花括号中的共同部分进入同一 slot，例如 `cart:{u42}:items` 与 `cart:{u42}:coupon`；这才使需要同槽的多键命令或短 Lua 脚本可用。滥用 tag（例如所有热键都写成 `{global}`）又会把负载集中到一个节点。客户端需要理解重分片时的 `MOVED`/`ASK` 重定向，或使用由成熟库维护的 slot 映射；把一条普通单机连接字符串硬接到 Cluster，故障迁移和扩容时会暴露错误。一个**热 key**仍只在一个 slot 上，扩容不能把它自动拆开，通常要改键设计、做本地/副本读缓存、请求合并或限制热点。

“Redis 变慢”也不能先假定服务器命令慢。先沿链路分层：客户端连接池是否排队、网络是否跨地域；实例的 CPU、事件循环、慢命令和 big key 是否占用时间；RDB/AOF 重写、全量同步、内存淘汰或迁槽是否造成尖峰；最后再看缓存未命中是否把真正的慢点留在数据库。`SLOWLOG`、`INFO`、命令耗时分布、连接数、内存碎片率、网络 RTT 和 Trace 应互相印证。禁止所有慢命令不是答案：先确认命令的 `O(N)` 中 N 是什么、是否在热路径、是否能改为分批或更合适的数据模型。

## 6.11 面试高频辨析速查

1. **缓存与数据库真源**：缓存是可重建副本，真源定义业务事实与约束；Redis 持久化不自动使它成为事务真源。
2. **穿透、击穿、雪崩**：穿透是不存在的键反复回源；击穿是少数热点键失效时并发重建；雪崩是大量键或整个缓存层失效。对应防线分别是校验/负缓存/Bloom Filter、单飞/旧值刷新、抖动/回源限额/降级。
3. **缓存更新与删除**：cache-aside 通常先提交真源再删缓存；删除避免维护多个派生副本，但失败必须补偿，竞态可用版本控制收敛。
4. **负缓存与空值**：负缓存是有意缓存“不存在”以阻断回源；空值只是某种表示。它要短 TTL，并在创建对象时删除，API 要能区分命中空值与未命中。
5. **限流与配额**：限流约束短时间的到达速率以保护容量；配额约束长周期总消耗以落实公平或套餐。一个用户可以不超每秒限流，却用完每天配额。
6. **QPS 与并发**：QPS 是速率，并发是尚未完成的在途数；慢请求会使同样 QPS 占用更多并发，二者要分别限制。
7. **分布式锁与数据库约束**：锁减少冲突、可能失效；唯一索引和条件更新在提交点守住不变量。关键正确性以约束兜底，锁用于削峰或协调。
8. **熔断与降级**：熔断停止调用不健康依赖；降级提供更弱的替代结果。二者配合才能既止损又保留体验。
9. **令牌桶与漏桶**：令牌桶允许在桶容量内突发，限制长期平均速率；漏桶平滑输出，突发通常等待或被拒绝。
10. **限流与并发限制**：前者限制开始速度，后者限制当前资源占用；依赖变慢时后者尤其重要。

## 6.12 练习与答案

**练习 1**：文章详情的缓存 TTL 是一小时。运营在活动页置顶文章后要求 30 秒内所有用户看见新排序。只把 TTL 改为 30 秒是否合适？

**答案**：通常不合适。它会让所有文章回源频率提高约 120 倍，也不能保证更新刚好发生在 30 秒边界。更合适的是把排序版本写入真源，发布变更事件删除/更新首页排序缓存；TTL 作为事件丢失时的兜底。若首页结果生成昂贵，可保留旧结果并由单飞刷新。

**练习 2**：某接口限每用户 60 次/分钟，采用固定窗口。为什么用户仍可能在两秒内完成 120 次调用？给出一种改进。

**答案**：固定窗口在边界重置计数：用户可在前一分钟最后一秒调用 60 次，再在下一分钟第一秒调用 60 次。可采用滑动窗口精确计数或近似计数；若希望允许可控突发，则采用容量和补充速率明确的令牌桶。

**练习 3**：领取优惠券流程已用 Redis 锁保护。是否还需要数据库唯一索引？说明一个锁失效的时间线。

**答案**：仍需要。实例 A 获得 3 秒锁后发生 5 秒 GC 暂停，锁过期；实例 B 获得新锁并写入领取记录；A 恢复后也写入。没有唯一索引就可能出现两条记录。唯一索引使第二次提交失败，锁只负责减少竞争。若后续动作不可重复，还应使用幂等键或状态机。

**练习 4**：推荐服务错误率 40%，首页团队说“加三次重试就好”。请指出风险并设计更安全的策略。

**答案**：重试会把已经过载的依赖推向更高请求量，且等待重试会占住调用线程。应先设置短且有总预算的超时；仅对可重试错误和幂等请求作少量、带抖动的重试；当错误率/慢调用超过阈值时打开熔断器，首页降级为热门内容，并用半开探测恢复。

**练习 5**：Redis 从节点可读，是否可以让“用户修改昵称后立刻刷新个人页”总是读从节点？

**答案**：不能保证。复制常为异步，刷新时从节点可能尚未收到最新写入。可以在短时间内粘到主节点、直接返回写后版本、等待复制确认（理解其性能与可用性代价），或接受最终一致并在产品上避免承诺立刻可见。
