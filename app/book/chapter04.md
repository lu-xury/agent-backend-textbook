一个后端服务不是“接收 JSON，再写数据库”这么简单。它还要在不可信的网络输入和可信的业务规则之间建立边界：识别请求指向什么资源，判断数据是否合格、调用者是谁、调用者能做什么，把一次业务操作正确地写入持久化系统，并用稳定的响应告诉调用方发生了什么。本章以一个任务管理服务为例：用户能创建、查询和修改自己的任务；企业客户还能接收任务状态变化的 Webhook。重点不是记住某个框架的装饰器，而是理解框架替我们组织了哪些边界，以及哪些决定仍只能由业务代码作出。

## 4.1 API、HTTP 与路由

**API（应用程序编程接口）**是组件之间约定的可调用边界。Web API 是其中一种：客户端以 HTTP 请求表达意图，服务器用 HTTP 响应交付结果。HTTP 是应用层通信协议，规定方法、目标 URI、字段（Header）、状态码和消息内容的语义；API 则是在 HTTP 之上约定“本服务有哪些资源、每个操作接收什么表示、返回什么表示”。因此，HTTP 不是 REST 的同义词，也不是只要返回 JSON 就叫 REST。

可以把资源理解成客户端可命名的业务对象或对象集合，而不是数据库表的别名。例如，`GET /tasks/42` 表示读取任务 42 的一个表示；`POST /tasks` 表示向任务集合提交一个新任务；`PATCH /tasks/42` 表示对该任务作部分修改。路径应主要表达名词与层级，方法表达动作的通用语义。`POST /tasks/42/complete` 并非绝对错误：当“完成”是一个有独立业务规则、审计记录或异步过程的命令时，它比把复杂命令伪装成字段更新更清楚。接口设计追求的是调用者能预测，而不是形式上最像某一种风格。

**路由（routing）**是把“HTTP 方法 + 主机/路径，有时再加媒体类型或版本”映射到处理函数的过程。框架在启动时通常把路由声明编译成查找结构；请求抵达后，先由反向代理或 Web 服务器按域名转发到应用，再由应用路由器选择处理器。路由匹配失败通常返回 404；路径匹配但该资源不支持所用方法时，应返回 405，响应**必须**带 `Allow` 字段列出该资源支持的方法。不要把“数据库中没有这条记录”的 404 与“路由不存在”的 404 混在日志里：对客户端二者都可表现为 404，但服务端排障需要不同的错误码和上下文。

一个路由只应承担传输层职责：从路径、查询串、Header 和正文取值，调用用例，并把结果转换成响应。若在路由函数中写权限规则、跨多表事务、第三方调用和 SQL 拼接，短期很快，长期会让同一规则散落在多个入口（HTTP、定时任务、消息消费者）中。路由是门牌号，不是整个房间。

## 4.2 一次请求如何穿过框架

典型生命周期可写成：连接建立或复用 → **在读取和解析过程中**执行请求大小、速率与超时限制 → 解析 HTTP 报文 → 全局中间件 → 路由匹配 → 身份认证 → 参数解析和格式校验 → 处理器/用例 → 数据库或外部依赖 → 响应序列化 → 响应中间件 → 写回网络。具体由网关还是框架先执行取决于部署方式，但限制不能等到完整读入正文后才做。这个因果顺序稳定：**先把字节变成受限的数据，再决定谁在请求，最后执行业务操作**。

请求体不是天然安全的对象。`Content-Type: application/json` 只是调用者的声明；服务器仍要按内容类型选择解析器，控制最大长度、嵌套深度和解析时间，处理无效编码与畸形 JSON。对于 `GET /tasks?limit=20`，`limit` 在网络上原本是字符串，框架可以把它转换为整数；转换失败不应悄悄使用默认值，否则客户端以为自己拿到 20 条，实际可能拿到所有数据。

状态码需要能反映失败发生的层次。畸形 HTTP/JSON 或无法按契约读取请求可归为 400；正文超过上限是 413；不接受的 `Content-Type` 是 415；JSON 本身合法、却不满足字段或业务前置条件时可使用 422。许多团队把字段校验统一映射为 400 也可以，但必须写入 API 契约，不能因此掩盖 413、415 等有明确语义的错误。

处理器成功返回的也不应直接交给 JSON 编码器。响应模型负责选择对外字段、序列化时间和金额、隐藏内部信息，并稳定表示空值。例如数据库实体中的 `password_hash`、内部风控分数、撤销标记都不应因为“对象自动序列化”而出现在响应里。无论 Python 的 FastAPI、Java/Spring、Go 的 handler，还是 Rust 的 Axum，框架最有价值的地方是把生命周期中的重复工作标准化；它不能替你决定任务能否被关闭。

## 4.3 DTO、领域模型与 ORM 实体：同一数据的三种视角

常见的混乱来自把三个模型当成一个模型。**DTO（Data Transfer Object，数据传输对象）**描述边界上的数据契约，如 `CreateTaskRequest { title, due_at }` 和 `TaskResponse { id, title, status }`。它服务于 API 的输入输出，字段可为了易用性而命名或组合。**领域模型**表达业务含义和不变量，例如任务只能从 `open` 变为 `done`，完成后必须记录完成时间；它不应知道 HTTP Header 或 JSON 字段名。**ORM 实体**则是持久化映射，关心主键、列类型、外键、延迟加载和版本号。

三者可以在极小的 CRUD 服务中由一个类暂时兼任，但职责并没有消失。直接把 ORM 实体当 DTO 的风险有三类：一是客户端可提交本不该修改的列，例如 `owner_id` 或 `is_admin`；二是表结构迁移不小心破坏公开接口；三是序列化触发延迟加载，造成 N+1 查询或递归关系泄露。反过来，为每一个两字段查询强行建立十个映射类也会增加噪声。实用的判断是：当输入字段需要白名单、输出要隐藏字段、业务规则不等于列约束，或者 API 与表会独立演进时，就应分开；先分 DTO 与实体，复杂到出现真实业务行为时再抽出领域模型。

以创建任务为例，输入 DTO 只允许 `title` 和可选的 `dueAt`。服务层从认证上下文取得 `actorId`，而不是相信正文中的 `ownerId`；它构造任务领域对象并检查标题长度、截止时间和状态转移。Repository 把该对象保存为 ORM 实体；最后再映射为响应 DTO。这个小小的“不要从请求取 ownerId”就是对象级授权漏洞的常见防线。

## 4.4 解析、校验与业务规则

**解析（parsing）**回答“这些字节能否读成约定的数据格式”；**校验（validation）**回答“该格式的数据是否满足约束”；业务规则回答“在当前状态和上下文中，这个操作是否成立”。三者宜分开思考。`{"dueAt":"tomorrow"}` 可以解析为 JSON 字符串，却不能转换为契约要求的时间值，或不能通过时间格式校验；`title:""` 可能格式正确但违反长度约束；任务已经归档时调用“完成”则是业务规则拒绝。把三者都称为“参数错误”会损失定位能力。

校验至少包括结构校验（字段类型、必填项、枚举）、范围校验（长度、上限、日期范围）和关联校验（开始时间早于结束时间）。但“用户名在库中尚未使用”“余额足够扣款”往往不能只靠请求校验完成：并发请求可能同时通过检查。因此，数据库唯一约束、条件更新、事务或锁仍是最终裁判。一个好用的规则是：**尽早拒绝明显无效输入，但把必须在共享状态下成立的不变量交给事务中的原子操作保证。**

不要让验证器接收任意未知字段后默默忽略。对写入接口，未知字段通常应拒绝或至少记录；否则前端拼错 `due_at`，请求看似成功却没有效果。对于需要向前兼容的客户端，可有选择地容忍新增响应字段，但请求字段的宽容要结合安全风险决定。

## 4.5 认证、授权与 401/403

**认证（authentication）**确认“你是谁”：验证会话 Cookie、API Key、OAuth access token 或 mTLS 客户端证书，得到一个主体（principal），例如用户 `u_17` 或服务 `billing-worker`。**授权（authorization）**确认“这个主体能否对这个资源执行这个动作”：`u_17` 是否能读取任务 42，管理员是否能导出组织成员。认证成功绝不表示授权成功；有有效令牌的普通用户仍不能修改别人的任务。

认证中间件的输出不应只是布尔值，而应是最小、可信的身份上下文，例如主体 ID、租户 ID、已验证的权限范围和认证时间；追踪 ID 属于请求上下文，而不是身份本身。可信令牌中的 role 或 scope 可以是服务端授权策略的输入，却不能替代对象级检查：`task:write` 仍不能证明任务 42 属于该主体。尤其是 `GET /tasks/{id}`、`PATCH /tasks/{id}`、下载文件和批量操作，必须在资源查找后检查归属或策略；只在前端隐藏按钮不是安全控制。

HTTP 里，**401 Unauthorized 的实际语义是“未通过认证”**；令牌缺失、过期或无效时适用，响应**必须**带至少一个 `WWW-Authenticate` challenge，指出可用认证方案。**403 Forbidden 表示服务器理解身份但拒绝该操作**，例如已登录用户访问他人的私有任务。出于防枚举资源的考虑，有些系统会对无权访问的私有资源返回 404；这是一种产品与安全策略，不意味着 403 的语义消失。无论选择哪种对外状态码，内部审计必须记录授权拒绝的原因，且不得记录完整令牌、口令或敏感个人信息。

## 4.6 中间件与服务边界

**中间件（middleware）**是围绕请求处理器执行的一段通用代码，常构成洋葱模型：请求进入时按注册顺序经过若干层，响应返回时反向经过。日志关联 ID、CORS、请求体限制、认证、速率限制、统一异常转换很适合放这里，因为它们与具体用例无关或跨越多数路由。**CORS 只约束浏览器的跨源访问，不是访问控制**；非浏览器客户端不会受它约束，权限仍由认证与授权决定，Cookie 认证的写操作还要设计 CSRF 防护。中间件要短小、可组合，并能在不调用下一层时明确终止请求，例如认证失败直接返回 401。

业务服务（Service 或 Use Case）则是完成一个业务动作的边界，如 `CreateTask`、`CompleteTask`、`InviteMember`。它协调领域对象、Repository、邮件或消息发布器，并决定事务何时开始和结束。把“只有创建者可以完成任务”放在全局中间件很别扭：中间件不知道路由最终取到哪条任务，也难以复用于异步消费者。将它放在用例或领域策略中，HTTP、命令行脚本和队列消费者才能执行相同的规则。

Repository 的职责是以业务需要的集合与查询方式访问持久化数据，例如 `findOwnedTask(taskId, ownerId)`、`save(task)`；它不应向上暴露 SQL 拼接细节。Adapter 是对外部技术的适配层，例如把 `EmailSender` 接口接到 SES、SMTP，或把 `ObjectStorage` 接到 S3。分层不是要求每个目录都有抽象接口。若一个依赖没有替换需求、没有业务语义且只有一处使用，直接调用也更清楚；当框架类型、第三方 SDK 或数据库查询开始污染业务代码时，边界才开始带来收益。

一个简洁的调用方向是：Controller/Handler → Application Service → Domain + Repository Port；数据库、缓存、HTTP 客户端、对象存储实现这些 Port。依赖应从外层技术指向内层业务抽象，而不是领域层导入某 ORM 的注解或 HTTP `Request`。这使测试可用内存实现或 fake adapter 覆盖核心规则，但不应为了“可测”伪造一套与真实数据库完全不同的行为。

## 4.7 事务、连接与一致性边界

**数据库连接**是应用与数据库之间可复用的通信会话和资源；连接池负责借出、归还和限制它。**事务**是数据库保证的一组读写作为整体成功或失败的执行单元。原子性只回答“全成或全败”，提交前后并发事务能否看见彼此的变化，由隔离级别和数据库实现决定。一个连接可以在不同时间执行许多事务；一个事务通常需要绑定一个连接才能维持隔离状态，但两者不是同义词。把网络调用、长时间文件上传或等待人工审批放在事务内，会长期占用连接和锁，最终耗尽连接池。

事务边界应该围绕一个必须共同成立的业务不变量。创建任务并写入其初始审计记录应放在同一事务：任一写入失败就回滚。发送“任务已创建”邮件则不宜直接放在该事务里，因为邮件服务可能慢、不可回滚，数据库提交后网络超时还会造成“邮件到底发没发”的不确定性。常见做法是事务内写任务和 outbox 事件；提交后由独立 worker **至少一次**投递邮件或 Webhook。worker 在“已经发送”与“标记已投递”之间崩溃时仍会重复发送，所以接收方必须按事件 ID 去重，或使下游操作幂等。Outbox 消除了数据库提交成功却没有待投递事件的双写窗口，**并不自动提供严格一次投递**。这不是为了复杂而复杂，而是承认数据库事务不能原子地覆盖外部网络。

隔离级别决定并发事务能看到彼此的哪些效果。应用开发中首先要用唯一约束、外键、检查约束和条件更新表达不变量；遇到实际并发竞争，再选择锁、版本号或更强隔离。比如领取一张待处理任务可用 `UPDATE tasks SET assignee_id = ? WHERE id = ? AND assignee_id IS NULL`，再检查影响行数，而不是先查询“未领取”再无条件更新。后者在两人同时领取时会丢失业务语义。

**原子性（atomicity）**表示一次操作的效果要么全部发生、要么全部不发生；**幂等性（idempotency）**表示相同请求执行一次或多次后的可观察最终状态相同。二者独立。`POST /payments` 可以在单个数据库事务中原子地创建支付记录，却因为客户端重试而扣两次款，因而不幂等。为高风险创建操作设置 `Idempotency-Key`：服务将“调用者 + key + 请求摘要”与首次结果持久化，同 key 的重试返回同一结果；同 key 但正文不同则拒绝。该记录也应受并发唯一约束保护。文档还要公布 key 的作用域、保留期，以及首个请求尚在处理时相同 key 是等待、返回“处理中”还是合并；这是一项 API 契约，不是 HTTP 自动提供的功能。

## 4.8 错误模型与可观察的失败

错误响应是 API 契约的一部分。它至少要让调用方知道：请求是否成功、是否可以修正后重试、该失败对应哪次请求。若采用 RFC 9457 的 Problem Details 风格，可使用如下统一形状：

```json
{
  "type": "https://api.example.com/problems/validation-error",
  "title": "输入不符合要求",
  "status": 422,
  "code": "TASK_TITLE_TOO_LONG",
  "detail": "title 最多 200 个字符",
  "requestId": "req_9f2...",
  "errors": [{"field": "title", "reason": "maxLength"}]
}
```

其中 `type`、`title`、`status`、`detail` 是该标准的成员；`code`、`requestId`、`errors` 是本服务的扩展字段。响应应设置 `Content-Type: application/problem+json`，而 HTTP 响应状态码仍是权威状态，正文中的 `status` 只用于表达和核对。稳定的 `code` 供程序判断；面向人的 `title`、`detail` 可本地化但不应成为客户端分支条件；`requestId` 把客户端报告与日志、Trace 串起来。不要把异常堆栈、SQL、云厂商响应、密钥片段直接返回给客户端。未知异常应记录完整诊断信息，对外返回通用 500；已预期的领域冲突可映射为 409，验证失败映射为 400 或 422。触发速率限制通常返回 429，并可带 `Retry-After`；业务配额耗尽则另按产品契约选择状态与稳定错误码。状态码不需要穷尽使用，但不能把所有错误包成 HTTP 200 再在 JSON 中写 `success:false`，否则缓存、监控、SDK 重试和网关都失去标准语义。

“超时”尤其值得谨慎：网关得到 504，只说明它没有在时限内获得上游响应，并不证明上游没有完成写入。客户端若不加幂等保护地立即重发创建请求，可能制造重复数据。面向写操作，应把超时视为结果未知，先用请求 ID 查询或使用幂等键重试。

## 4.9 查询、分页与筛选

集合资源需要稳定、受限的查询契约。`GET /tasks?status=open&assignee=me&sort=-createdAt&limit=20` 中，筛选条件应白名单化，排序字段与方向也应白名单化；不要把 `sort` 原样拼进 SQL。白名单解决的是列名、方向等 SQL 结构位置，筛选**值**仍必须通过参数绑定传入。`limit` 要设最大值，避免单次请求拉走百万行并拖垮序列化和数据库。对于多个筛选条件，文档必须说明它们是 AND 还是 OR、时间边界是否包含、空值如何处理。

**偏移量分页**使用 `offset`、`limit`，直观且便于跳到第 N 页，适合数据量有限、排序稳定且可接受深页变慢的后台页面。它的问题是数据在翻页期间插入或删除会造成重复或遗漏，并且数据库需要跳过大量行。**游标分页（keyset/cursor pagination）**把上一页最后一条的稳定排序键编码为不透明 cursor，例如 `(created_at, id)`，下一页查询“小于该键”的记录。它更适合按时间不断增长的 API；排序必须有确定的并列规则，常以唯一 ID 作第二排序键。cursor 是实现细节，不要要求客户端拼装数据库主键范围。游标能减少深页扫描和同键跳项，却不能把持续变化的列表变成一致快照；确需绝对一致的多页视图，要额外设计 snapshot 或 as-of 语义。

响应应显式说明分页信息，如 `items`、`nextCursor`、`hasMore`。总数 `total` 看似方便，但在复杂过滤和大表上可能昂贵，也难以与持续变化的数据形成绝对一致的承诺；只有确有产品需要时再提供，并说明其一致性与成本。

## 4.10 API 兼容与演进

公开 API 一旦被调用，接口不只是代码，而是别人系统的一部分。**向后兼容的变更**通常包括新增可选请求字段、新增响应字段、新增端点和放宽某些限制；前提是旧客户端不依赖新字段，旧服务端或网关也不把它当未知字段拒绝。但“客户端会忽略未知响应字段”只是理想假设，仍应评估严格解析器。删除字段、改变字段类型或单位、给旧枚举新增客户端未处理的值、改变默认排序、把同步 200 改成异步 202，都会影响调用方。

演进的第一选择是兼容性设计，而不是立即加 `/v2`。例如新建任务时新增 `priority`，先将其设为可选并提供稳定默认值；废弃字段时保留一段窗口、在文档和响应 Header 中公告、观测旧字段使用率，再删除。无法兼容时才进行版本化，可以在 URI、媒体类型或 Header 中表达；选一种并长期一致。版本号不能替代迁移计划：新版本仍需要清楚的截止日期、示例、SDK 迁移指南和灰度观察。

契约测试是防止无意破坏的手段。服务端可用 OpenAPI 或 JSON Schema 描述请求与响应；消费者可在 CI 中验证依赖的字段和语义。文档不能只列字段，还应写出状态码、错误码、认证方式、分页、限流、重试以及副作用。

## 4.11 Webhook 与文件上传：两个容易被低估的入口

**Webhook**是服务端主动向订阅方 URL 发送 HTTP 回调的机制，适合“任务完成后通知对方”这类事件，而非让客户反复轮询。生产 Webhook 通常设计为不可靠网络上的**至少一次投递**：接收端可能超时、返回 500，或已处理成功但响应在途中丢失。因此事件必须有唯一 `eventId`，接收方按 ID 去重；发送方以指数退避重试，并允许重放或查询投递状态。不要把“成功回调一次”误认为严格一次投递。

Webhook 的安全重点是验证来源和防止 SSRF。发送方应给每个租户配置签名密钥，将时间戳与原始请求体计算 HMAC，接收方在**解析前保留原始字节**并做常量时间比较，同时限制允许的时间窗口以防重放。接收端也要验证请求方法、内容类型和体积。若产品允许用户登记回调 URL，优先使用客户域名 allowlist；禁用重定向或逐跳重新验证，并在实际连接时校验解析出的所有 IP 不属于本地、私网、链路本地及云元数据地址，还要配合出网策略。只在登记时解析一次 URL 不能防 DNS 重绑定或解析—连接竞态；否则攻击者可诱导服务访问内网管理面。

文件上传不是“收到一个文件字段”即可。服务器应限制 `Content-Length` 和流式读取上限，生成随机对象名而不是使用原始文件名，存入应用不可执行的对象存储，并进行恶意内容扫描。扩展名、客户端声明的 MIME 和 magic bytes 都只是信号：应按业务 allowlist 控制类型，并在上传完成后解析或扫描真实内容。上传成功后返回文件 ID 或受控下载 URL；下载时再次做对象级授权，必要时设置 `Content-Disposition: attachment` 和 `X-Content-Type-Options: nosniff`。大文件通常由服务签发短时预签名上传 URL，使浏览器直接写对象存储；它可约束声明的大小和 MIME，却不能证明文件安全，应用仍须在完成回调或元数据登记时验证对象属性。不要把用户上传的文件放在 Web 根目录并直接以原文件名访问。

## 4.12 高频面试辨析

1. **REST 与 HTTP 有什么区别？**HTTP 是标准协议，定义请求、响应和通用方法的语义；REST 是一组架构约束和风格。可以用 HTTP 写 RPC 风格接口，也可以设计 REST 风格 API。回答时不必声称 REST 要求“URL 绝不能出现动词”；核心是资源表示、统一接口、无状态交互等约束带来的可理解性。

2. **认证和授权有什么区别？**认证建立主体身份，授权依据主体、动作和资源作许可决定。JWT 或 Session 解决的是“令牌是否可信”，而任务归属检查解决“此人能否改这条任务”。二者分别失效都会形成漏洞。

3. **401 与 403 怎么选？**没有可接受的认证凭据、凭据失效或缺失，用 401，响应**必须**带至少一个 `WWW-Authenticate` challenge；身份已确认但权限不足，用 403。隐藏资源存在性时可对外选择 404，但内部仍要作为授权拒绝记录。相近的协议题是 405：路径指向的资源不支持该方法时，响应**必须**带 `Allow` 列出支持的方法。

4. **DTO、领域模型、ORM 实体为什么不应总是同一个类？**它们分别服务于网络契约、业务不变量和表映射。小项目可以暂时合并以减少样板代码；当字段白名单、隐私、表/API 独立演进或复杂行为出现时必须拆开，避免越权写入和持久化细节泄漏。

5. **PUT 与 PATCH 的区别？**PUT 的目标是用请求表示替换指定资源的当前表示，按 HTTP 方法语义是幂等的；PATCH 按声明的 patch 媒体类型应用部分修改，服务端必须将**整个补丁全成或全败**，整体是否幂等取决于具体操作。把数量加一这类增量命令不是幂等；把状态设为 `done` 在同一前提下通常是。若修改基于刚读到的旧表示，应使用 `If-Match: <ETag>` 或版本号防止后写覆盖前写，不匹配时可返回 412 或采用文档说明的冲突策略。实际 API 还必须说明省略字段代表“不变”还是“清空”。

6. **接口幂等和原子性有什么区别？**幂等关心重复执行后最终结果，常用于网络重试；原子性关心一次操作内部不能只完成一半，常由事务保证。一次转账可以原子但因重复扣款而不幂等；一次“设置状态为关闭”可幂等，却可能在跨两个系统时不是原子。

7. **中间件与业务层怎样分工？**中间件处理与多条路由正交的请求管线问题，如认证解析、日志、限流和统一错误转换；业务层处理某个用例的规则、资源级授权和事务。若规则要知道“哪条任务”“当前状态”“扣多少余额”，通常不该在全局中间件中实现。

8. **事务和连接有什么区别？**连接是通信资源，事务是一组原子、隔离的数据库操作。连接池耗尽与长事务常相关，但“连接多”不等于“事务多”。一个请求不必总开事务，只有跨多步且需共同成立的写入才需要明确事务边界。

## 4.14 练习参考答案

1. `CreateTaskRequest` 可含 `title`、可选 `dueAt`、可选 `idempotencyKey`（更常放 Header）；响应含 `id`、`title`、`status`、`owner` 的安全表示和创建时间。`ownerId` 从认证上下文取得，否则攻击者能指定他人。将调用方、幂等键和请求摘要以唯一约束写入同一事务；重复键返回首次响应，不同摘要报冲突。

2. 路由匹配；解析 Header、路径和 JSON；认证得到主体；DTO 格式校验；服务读取任务并检查对象级授权；检查归档状态与状态转移；在必要事务中写入任务和审计记录；映射响应 DTO；异常转换为状态码。归属检查应在服务/领域策略靠近资源处，归档状态是领域规则，不能只放路由或前端。

3. 仅有时间戳不能全序排序：两条记录相同时间会在“下一页小于时间戳”的查询中遗漏，或使用小于等于时重复。cursor 可编码 `(createdAt, id)`；查询条件为 `createdAt < lastCreatedAt OR (createdAt = lastCreatedAt AND id < lastId)`，并对两列建立相应索引。

4. 发送内容至少有 `eventId`、事件类型、发生时间、资源 ID、必要快照和签名时间戳。接收方先读取受限原始正文，验签和时间窗口；再在短事务中把 `eventId` 写入带唯一约束的 inbox/event record，唯一冲突即视为已可靠接收；事务提交后，请求即可返回 2xx，独立 worker 再从 inbox 异步执行业务。2xx 表示“已可靠接收”，不表示所有下游副作用已经完成。响应可能在网络中丢失，发送方会重试；因此协议通常实现至少一次投递，持久去重使业务效果接近一次。

5. 服务读取时返回 `ETag: "7"`，客户端修改时携带 `If-Match: "7"`；服务用带版本条件的更新，例如 `WHERE id = ? AND version = 7`，并在成功后将版本递增。若影响行数为零，说明表示已经改变，条件请求应返回 412；也可用 409 表达团队定义的业务冲突，但必须在契约中固定语义。这样“HTTP 方法幂等”不会被误解为“不会覆盖别人的并发更新”。
