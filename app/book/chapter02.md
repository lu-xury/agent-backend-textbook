后端程序不是直接运行在 CPU 上的一段代码，而是运行在操作系统提供的边界之内。Web 服务要接收连接、读写文件、访问数据库、定时执行任务并在发布时退出；这些动作最终都会落到进程、线程、内存、文件描述符和信号上。本章的目的不是教你背系统调用，而是建立一个判断框架：**什么资源被谁拥有，什么工作正在等待，什么时候需要隔离，什么时候需要并发。**

## 2.1 进程：资源隔离与执行环境

**进程（process）**是一个正在执行的程序实例，也是操作系统进行资源保护和资源记账的重要边界。启动两个 `python server.py`，即使它们使用同一个可执行文件和同一份代码，也会成为两个进程：各自有进程标识符 PID、虚拟地址空间、打开的文件、环境变量、当前目录、权限和退出状态。操作系统可以把其中一个终止或限制其内存，而不必直接改动另一个。

把进程理解为“程序”并不准确。程序是磁盘上的静态文件；进程是它被加载后的一组动态状态。一个进程至少包含可执行指令、数据、当前执行位置、寄存器状态，以及它拥有或引用的内核对象。服务器的配置文件相同，并不意味着两个进程会共享内存中的缓存；默认情况下，一个进程把字典写入内存，另一个进程看不见。这个隔离让故障更容易收敛，也意味着跨进程协作需要 Socket、管道、共享内存或数据库等显式通信手段。

### 进程状态、僵尸与孤儿：退出不等于已经消失

调度器需要区分“此刻能运行”和“仍然存在但在等待”。不同内核的状态名称不同，但后端排障通常关心：**runnable/running** 表示可占用或正在占用 CPU；**interruptible sleep** 表示等待 I/O、锁或定时器且通常可被信号唤醒；**uninterruptible sleep** 往往表示等待某些内核 I/O，任务可能暂时无法响应普通信号；**stopped/traced** 表示被作业控制或调试器停止；**exited** 表示用户态执行已结束。`ps` 的单个状态字母只是一个时刻的快照，不能单独用来断言“CPU 一定慢”或“磁盘一定坏”，应与 run queue、I/O 延迟和应用指标结合。

子进程调用 `exit` 后，内核还需要把退出码和资源使用情况交给父进程读取；在父进程调用 `wait`/`waitpid` 前，它会保留一个很小的**僵尸进程（zombie）**记录。僵尸不再执行，也通常不占用其原来的用户态内存，但会占 PID/进程表槽位；持续累积通常说明父进程没有正确回收子进程。**孤儿进程（orphan）**则是父进程先退出、子进程仍运行；它会被 init/systemd 或配置的 subreaper 接管，之后仍可被回收。孤儿不是天然泄漏，僵尸才是“已经退出却未被回收”的问题。Web 服务若自己拉起 worker，应由一个明确的监督者 `wait` 子进程；不要依靠反复 `kill -9` 掩盖生命周期错误。

### 地址空间为什么重要

**虚拟地址空间**是进程眼中可使用的地址范围，而非它已经占有的物理内存。程序里的指针，例如 `0x7f...`，先经页表翻译，才可能对应某个物理页。每个进程通常有自己的映射和页表，所以两个进程都可以把某个变量放在“看起来相同”的虚拟地址，却不会互相覆盖。内核借此同时实现地址隔离、内存保护和按需分配。

常见的地址空间区域可以这样理解：代码段保存机器指令，已初始化和未初始化数据保存全局状态，**堆（heap）**保存运行期动态分配的对象，**栈（stack）**保存函数调用现场、局部变量和返回地址；共享库、文件映射以及运行时申请的大块区域也会出现在其中。它们是理解工具输出的概念模型，不应被误解为所有语言、所有系统都严格采用一块连续的固定布局。比如 Python 对象常经解释器和内存分配器管理；Go 的 goroutine 栈可随需要扩缩；大块申请可能直接变成独立的 `mmap` 映射。

`fork` 与 `exec` 说明了 Unix 进程模型的两个基本动作。`fork()` 产生一个子进程；父子进程起初看到相同的内存内容，但拥有彼此独立的地址空间，之后一方对普通私有内存的写入不会影响另一方。现代 Linux 通常以**写时复制（copy-on-write）**避免在 `fork` 那一刻复制全部页面：先共享只读页面，谁要写谁再获得私有副本。`execve()` 则用新的程序映像替换当前进程的用户态地址空间，PID 通常仍是原来的 PID。默认情况下，未设置 close-on-exec 标志的文件描述符会跨越 `exec` 保留；创建不希望传给子程序的 fd 时应使用 `FD_CLOEXEC` 或等价接口。Shell 执行外部命令时，常见做法就是 `fork` 子进程再 `exec` 新程序，父进程负责等待或继续交互。

多线程进程调用 `fork()` 有一个常被忽略的限制：子进程中只保留**调用 `fork` 的那一条线程**。其他线程可能曾持有锁，却不会出现在子进程中释放它；因此在子进程 `execve()` 前，只应调用异步信号安全的函数，否则可能在锁或运行时内部状态上死锁。实际服务中应避免在复杂的多线程状态下随意 fork，或尽快 exec 新程序。

后端中的 worker 进程常被用来获得隔离。例如一个图像处理任务发生 native 扩展崩溃，单独的 worker 进程退出不会立即带走 API 进程；主进程可以记录失败、拉起替代 worker。代价是进程之间不能随意传递内存对象，序列化和 IPC 会增加开销。对于只需并发等待网络的服务，先创建大量进程通常不是最优答案。

### 调度与上下文切换

程序的大部分业务代码运行在**用户态**，权限受限，不能直接操作受保护的硬件和内核数据；打开文件、收发网络包等需要经**系统调用**受控地进入内核态。进入内核态不等于一定切换到另一个线程：短系统调用可以很快返回；只有当前线程因 I/O、锁等原因不能继续运行时，调度器才可能换出它。这一区分能避免把“系统调用”“模式切换”和“上下文切换”混成一个概念。

CPU 在任一时刻只执行某个逻辑 CPU 上的一个**可调度执行实体**。在 Linux 中，内核调度的基本对象是任务；一个多线程进程包含多个这样的执行线程。调度器可能因为时间片用尽、更高优先级任务就绪、当前线程等待 I/O 或主动让出 CPU，而选择另一个线程运行。

**上下文切换（context switch）**是把即将暂停的执行状态保存起来，并恢复另一个执行状态的过程。状态包括程序计数器、栈指针和通用寄存器等；切换到另一地址空间时还涉及内存管理上下文，可能影响 TLB 等硬件缓存。它不是一个固定耗时的“数字”，成本受处理器、缓存命中、地址空间是否改变、负载和内核版本影响。实务上应关注现象：若大量线程频繁抢一个锁，CPU 时间可能花在调度与同步而非业务计算上；若线程因 I/O 阻塞，切换反而让 CPU 有机会运行其他工作。

可以用 `pidstat -w -p <pid> 1` 或 `/proc/<pid>/status` 中的 `voluntary_ctxt_switches` 与 `nonvoluntary_ctxt_switches` 观察切换线索。自愿切换往往发生在等待锁、睡眠或 I/O；非自愿切换常表示调度器抢占。二者都不是性能问题的定论，需要结合 CPU 利用率、延迟和火焰图判断。

## 2.2 线程：共享资源的执行单元

**线程（thread）**在本节指操作系统线程，是进程内部的一条执行路径。一个进程可以有一个或多个线程；同一进程的线程通常共享地址空间、打开文件和大多数进程级资源，但每个线程都有自己的寄存器上下文、内核调度状态、栈和线程局部存储。因而，线程创建与协作通常比独立进程轻量，却也把“能直接访问同一对象”变成了正确性风险。

例如订单服务有一个进程、八个请求处理线程，内存中有 `available = 1`。两个线程都执行“读 available；如果大于零则减一”，可能都读到 1，最后售出两件商品而变量只剩 0。这是**数据竞争（data race）**：多个并发执行单元访问同一可变状态，至少一个是写入，并且缺少适当同步。它的危险不只在“结果偶尔错”：在某些语言的内存模型下，未同步的数据竞争还可能使程序行为不再可可靠推理。数据竞争不等于所有**竞态条件（race condition）**；后者更宽，例如先检查文件存在、随后再打开文件时被他人替换，即使没有两个线程同时读写同一个内存变量，也会发生检查与使用之间的竞争。

正确做法取决于不变量。若操作必须把“检查库存”和“扣减库存”视为一个不可分割的动作，可用互斥锁保护同一临界区，或把操作放到数据库事务的条件更新中，例如 `UPDATE ... SET stock=stock-1 WHERE stock>0` 并检查受影响行数。**锁不是让程序更快的装饰**；锁为共享数据建立互斥和可见性边界。锁粒度过大使所有请求排队，粒度过细则增加死锁、遗漏保护和维护成本。先明确“谁拥有这个状态、允许哪些状态转换”，再选择锁、原子操作、消息队列或数据库约束。

线程共享文件描述符也值得警惕。一个线程关闭了共享的 Socket，另一个线程随后在该描述符上写数据就可能失败；如果描述符号被内核复用，错误的“按数字关闭”甚至可能关掉一条新连接。把连接对象的生命周期归属明确给一个事件循环或一个 worker，比让许多线程随时都能关闭它更容易验证。

**线程池**适合把许多短任务交给有限数量的工作线程，避免每个请求临时创建线程。线程池不是越大越好：CPU 密集任务中，远大于可用 CPU 核数的可运行线程通常只会增加切换；I/O 密集任务中，适度更多的线程可能掩盖等待时间，但阻塞外部依赖仍会把池耗尽。必须设置队列上限、超时和拒绝策略；无界队列会把瞬时流量变成不断增长的内存与排队延迟。

## 2.3 协程、异步 I/O 与事件循环

**协程（coroutine）**是由语言或运行时在用户态管理、可以在特定位置暂停并稍后恢复的执行单元。它不是 Linux 内核调度的线程，也不是“自动并行”。`await` 的直观含义是：当前协程在等待某项结果时把控制权交还给运行时，运行时可以安排同一线程上的其他就绪协程继续执行。协程的保存与恢复通常比内核线程切换轻，但仍有调度、对象和状态机成本。

协程真正适合后端，原因常是网络 I/O 的等待比例高。假设一个 API 同时向三个下游服务发请求，每个请求大部分时间在等网络。同步串行写法会让总延迟接近三段等待之和；在正确设置超时、取消和并发上限的前提下，异步方式可以让三项等待重叠。这里重叠的是等待，不代表同一 CPU 核同时执行三段 Python 或 JavaScript 计算。若协程内部运行压缩、图像推理或大循环，它仍会占住事件循环线程，其他协程无法得到调度。

**异步 I/O**描述的是“发起操作后，调用者不必一直阻塞等待完成，完成或就绪由后续机制通知”的协作方式；协程只是组织异步代码的一种语法和运行时形式。Linux 的 `epoll` 是就绪通知机制：程序把关心的文件描述符登记进 interest list，内核把可读、可写等就绪项放进 ready list，`epoll_wait` 返回它们。它不替应用读取消息，也不保证一次 `read` 就读到完整 HTTP 请求。TCP 是字节流，应用仍要处理分帧、部分读写、连接关闭和错误。

非阻塞 Socket 在暂时没有数据可读或缓冲区没有空间可写时通常返回 `EAGAIN`，而不是让线程睡眠。事件循环应把当前解析进度保存到连接状态中，等下一次就绪事件后继续。边沿触发的 `epoll` 尤其要求程序把非阻塞 fd 持续读或写到 `EAGAIN`；只读一小段就回去等待，可能再也收不到新的边沿通知，从而形成“明明有数据却卡住”的连接。初学时优先理解默认的水平触发语义；只有在压测证明需要、并能正确维护状态机时再使用边沿触发。

### `select`、`poll`、`epoll` 与 Reactor：谁负责发现就绪连接

它们都回答“哪些 fd 现在可以尝试 I/O”，而不是“哪条业务消息已经完整”。`select` 以位集合传入 fd，在常见 Linux 环境中受 `FD_SETSIZE`（通常 1024）限制，并且每次调用都要重建/检查集合；`poll` 用数组表示兴趣事件，摆脱了这个位集合上限，但每次仍要提供并扫描关注集合；`epoll` 在内核中维护 interest list 和 ready list，`epoll_wait` 只返回已就绪项，因此特别适合大量长连接。它们的差别不是“epoll 永远更快”：连接数小、代码路径短时，`poll` 的简单性可能更有价值；磁盘普通文件也不适合被当作网络 Socket 那样依赖就绪通知。

**Reactor** 是常见的组织方式：一个或少数 I/O 线程等待就绪事件，按 fd 找到连接状态机，读取到应用缓冲区并解析完整帧；耗 CPU 的工作再交给有界 worker 池。它避免了“一连接一线程”的线程数膨胀，却把所有权放大为关键问题：同一连接应由谁修改读写缓冲、何时关闭、worker 的结果如何回到 I/O 线程。下面只是“可读事件”的最小骨架；它刻意没有假装是完整 HTTP 服务器。

```cpp
void on_readable(Connection& connection) {
  char buffer[8192];
  for (;;) {
    const ssize_t n = ::recv(connection.fd, buffer, sizeof buffer, MSG_DONTWAIT);
    if (n > 0) {
      connection.input.append(buffer, static_cast<std::size_t>(n));
      dispatch_complete_frames(connection);  // 可能留下半帧，等待下次可读。
      continue;
    }
    if (n == 0) { close_connection(connection); return; }  // 对端有序关闭。
    if (errno == EAGAIN || errno == EWOULDBLOCK) return;   // 本轮读空。
    if (errno == EINTR) continue;
    close_connection(connection);                           // 记录具体 errno。
    return;
  }
}
```

循环读到 `EAGAIN` 对边沿触发尤其必要；对水平触发也不会破坏语义。真正的实现还要控制单连接单轮读取上限，防止一个持续活跃的 fd 饿死其他连接；写路径也要处理部分写入，在 `EAGAIN` 时登记 `EPOLLOUT`，缓冲清空后取消写关注。所谓“百万连接”首先是 fd、内核 socket 缓冲、连接状态内存、TLS 成本、accept 队列和业务处理能力的总预算，不能仅靠把 `epoll` 换进代码获得。

一个简化的 Python 例子如下。它展示“等待时让出”，但生产代码仍应加上总超时、连接池、限流和异常分类：

```python
async def fetch_profile(client, user_id):
    response = await client.get(f"https://profile/users/{user_id}")
    return response.json()

async def render_page(client, user_id):
    profile, orders = await asyncio.gather(
        fetch_profile(client, user_id),
        client.get(f"https://orders/users/{user_id}"),
    )
    return {"name": profile["name"], "orders": orders.json()}
```

`gather` 让两个可等待任务并发推进；它并没有使一个阻塞的普通数据库驱动自动变为非阻塞，也没有使 CPU 计算自动利用多个核。把 `time.sleep(5)`、同步 HTTP 请求或耗时 JSON 处理放进事件循环，仍会阻塞同一线程上的其他请求。遇到这种库，要么使用匹配的异步驱动，要么把阻塞调用交给受限线程池或独立 worker，并保留背压。

## 2.4 为 CPU 与 I/O 选择并发模型

选择模型前先问：任务的瓶颈是在等，还是在算？**I/O 密集型**任务大部分时间等待网络、磁盘、数据库或其他进程；一个事件循环加协程可以用较少线程管理很多处于等待状态的连接。**CPU 密集型**任务大部分时间在压缩、加密、编解码、排序或模型推理；要提高吞吐，需要真正并行地使用多个 CPU 核，通常采用有限的进程 worker 或线程 worker，具体受语言运行时和所用库是否释放运行时锁影响。

混合服务最常见的结构是：事件循环或少量 I/O 线程负责接入、超时和协议状态；耗 CPU 的部分投递到**有界**执行器；结果回到请求状态机。关键不是“异步到底”，而是不能让无上限请求把 worker 队列、内存和下游连接同时撑爆。请求排队本身会增加尾延迟，所以当队列满时，快速拒绝、降级或让上游重试，通常比无限等待更能保护整体服务。

进程、线程和协程可以共存。一个常见部署是多个进程分摊多核，每个进程内有少量线程或一个事件循环，每个事件循环管理大量协程。不要把它当公式：小型管理后台用同步代码加少量线程也可能最清晰；高连接数网关则更受益于非阻塞事件循环。先测量 CPU、连接数、阻塞来源、P99 延迟和下游容量，再决定复杂度是否值得。

## 2.5 虚拟内存、RSS、堆栈与 OOM

内存监控最常见的误解是把一个数字当作“进程真实占用”。`VmSize`（也常被工具显示为 VIRT）描述进程映射或保留的虚拟地址范围，可能包含尚未驻留的页面、共享库和映射文件；**RSS（Resident Set Size）**表示当前驻留在物理内存中的页面集合。RSS 仍包含共享页，因而把多个进程的 RSS 简单相加可能重复计算共享库页。需要更细的归因时，查看 `/proc/<pid>/smaps_rollup` 或进程分析工具，而不是仅凭 `top` 的一列数字下结论。

堆与栈也不是“一个大、一个小”的面试口号。堆主要承载生命周期由分配器或垃圾回收器管理的动态对象；栈主要承载调用链的帧。递归过深或在线程栈上放很大的局部数组，会发生栈耗尽；把每个用户会话永久存进全局 Map，则是堆或缓存无限增长。两种问题的修复不同：前者通常改算法、限制递归或调整受控的栈配置；后者需要生命周期、淘汰策略、容量上限或泄漏定位，不能靠“增大容器内存”掩盖。

内存分配成功也不代表物理页此刻已经全部到位。操作系统可以延迟实际分配到第一次访问页面时；文件映射则可能由页缓存支持。正因如此，压测应观察真实工作集和峰值，而不是只看启动后是否能申请一大块地址。把数据读成巨大的字符串、把请求体无上限地缓存在内存、线程池队列无限积压，都会在高峰时把 RSS 推高。

**OOM（out of memory）**是内核在无法满足内存分配并且回收等手段无效时采取保护动作的统称之一。在宿主机内存紧张时可能触发全局 OOM；在 cgroup 设置内存限制时，也可能发生 cgroup 范围的 OOM，即宿主机尚有余量但这个工作负载已超出自己的配额。内核或运行时可能终止某个进程以恢复可用内存。容器平台上看到退出码 137 通常说明进程收到过 `SIGKILL`，但它**不是 OOM 的充分证据**：人工强杀、超出优雅退出期限等也会造成同样结果。诊断要同时看容器状态、cgroup `memory.events`、内核日志、RSS 曲线和应用的请求/队列变化。

### 用户态分配器、伙伴系统与 Slab：一次 `malloc` 不等于一次物理页申请

应用调用 `malloc`、C++ `new` 或语言运行时分配对象时，通常先进入**用户态分配器**。分配器从已经取得的 arena、span 或空闲链表中切出一块；现有区域不足时，才通过 `brk`/`mmap` 等方式向内核扩大虚拟映射。释放对象也常只是把块还给进程内分配器，未必立刻归还内核，所以“业务对象已释放”与“RSS 立即下降”不是同一件事。大量不同尺寸对象、跨线程 arena 和长期存活小对象会产生内部或外部碎片；排查应同时看语言堆、分配器统计、匿名映射和 RSS，不能只凭对象计数判断泄漏。

内核还要管理物理页与自己的小对象。Linux 常用**伙伴系统（buddy allocator）**按 2 的幂次连续页块分配和合并物理内存，适合页级请求，却可能因长期切分形成高阶连续页不足；Slab/SLUB 一类分配器在页之上为 `inode`、目录项、Socket 等固定或相近尺寸的内核对象维护缓存，减少反复初始化与碎片。二者都不等于应用堆分配器：用户态分配器管理某个进程取得的虚拟区域，伙伴系统管理物理页，Slab 管理内核对象。机器还有很多空闲内存却分配不了一大块连续页，和进程因堆碎片变大，是不同层面的故障。

## 2.6 文件描述符、Socket 与管道

**文件描述符（file descriptor，fd）**是进程在用户态持有的一个小整数，用来索引内核维护的已打开对象。文件、Socket、管道、标准输入输出、`epoll` 实例都可以通过 fd 操作；这就是 Unix “很多东西都能像文件一样读写”的统一接口。fd 不是网络连接本身，更不是全局唯一 ID；它在一个进程的 fd 表中才有意义，关闭后其数值可能很快被复用。

打开文件、`accept()` 新连接、创建 pipe 或 socket 都会消耗 fd。一个反向代理每接受一条 TCP 连接，通常会多持有一个连接 fd；忘记关闭响应体、客户端连接或临时文件，会使 fd 数不断上升，最后得到 `EMFILE`（进程可打开文件数达到限制）或触及系统级限制。排障时可用 `ls /proc/<pid>/fd | wc -l` 观察数量，用 `lsof -p <pid>` 或 `/proc/<pid>/fd` 看对象类型；但计数增长只能说明泄漏方向，还要顺着请求生命周期定位谁保留了引用。

**Socket**是用户进程与内核协议栈之间的端点接口。TCP Socket 是双向字节流，可 `connect`、`listen`、`accept`、`send`、`recv`；UDP Socket 则面向数据报。**管道（pipe）**用于同一主机上进程间传递顺序字节流，典型匿名管道有读端和写端两个 fd；写端全部关闭后，读端读尽缓冲区会见到 EOF。它们都可作为 fd 被 `read`、`write` 或等待就绪，但 Socket 有网络地址、连接和协议语义，管道没有。不要把一次 `read` 返回当成一条完整业务消息：管道和 TCP 都是流，应用协议必须自己定义边界。

### 页缓存、`mmap` 与“零拷贝”：先问数据经过哪里

普通文件的 `read` 通常先让内核把磁盘块放入**页缓存（page cache）**，再把所需字节复制到用户缓冲区；后续读取可能直接命中内存，所以“调用了磁盘文件读取 API”不等于本次一定发生物理磁盘 I/O。`mmap` 把文件页映射进进程虚拟地址空间，程序通过普通内存访问触发按需缺页，不必先显式 `read` 到另一块用户缓冲区；但它仍要处理页错误、文件截断、脏页回写和访问模式，不能简单理解为“永远更快”。数据库会根据自己的缓存、写前日志和崩溃恢复设计决定使用页缓存、直接 I/O 还是两者组合。

网络文件发送中的“零拷贝”通常表示避免一次或多次用户态中转复制，例如 Linux `sendfile` 可让内核把文件数据从页缓存送到 Socket 路径。它不表示 CPU、DMA、内核元数据或协议处理完全没有复制和成本，也不适用于必须在用户态逐字节压缩、加密或改写内容的路径。面试中应先画出“存储设备 → 内核缓存 → 用户缓冲区 → Socket 缓冲区 → 网卡”的数据路径，再说明具体 API 省掉哪一步；只背“少两次拷贝、少两次切换”容易忽略内核版本、硬件和 TLS 路径差异。

### VFS、inode、目录项与链接：文件名不是文件本身

**VFS（Virtual File System）**为不同文件系统提供统一的 `open/read/write/stat` 接口。路径解析时，内核逐级查找目录项（dentry）并定位 inode；**inode**保存文件类型、权限、所有者、大小、时间和数据块映射等元数据，通常不保存人类看到的文件名。目录维护“名字 → inode”的映射，因此重命名常主要改变目录项，而不是复制文件内容。打开文件后，进程 fd 指向内核的打开文件对象；即使路径被删除，只要仍有打开引用，对应数据通常要到最后一个引用关闭后才真正回收。这解释了日志文件 `rm` 后磁盘空间为何可能没有释放：旧进程仍持有已删除文件，应定位 fd 并让应用重新打开或重启，而不是继续删除其他文件。

**硬链接**是另一个目录项指向同一个 inode，不能跨文件系统，通常也不允许普通用户给目录创建硬链接；删除其中一个名字不会删除仍有其他链接的文件。**符号链接（软链接）**则是保存另一条路径的特殊文件，可跨文件系统，但目标移动或删除后会悬空。权限检查还要沿路径逐级进行：目录的执行权限表示可以穿越或查找其中名字，读权限表示可以列出目录项，写权限通常与执行权限共同决定能否创建或删除目录项；删除文件主要受父目录权限影响，不是只看文件自身是否可写。`/proc` 和 `/sys` 多数是内核导出的虚拟视图，不是磁盘上的普通业务文件；读取它们是在查看进程、设备和内核状态。

## 2.7 信号与优雅退出

**信号（signal）**是内核或其他进程向进程报告某件异步事件的一种机制。`kill` 这个命令名容易误导：相应系统调用的本质是“发送信号”，可发送的不只有终止信号。信号有默认动作；程序也可为可捕获信号安装处理方式。多线程进程中，信号处置是进程级属性，但每个线程可以有不同的屏蔽字，因此不要假定“信号总在某个固定线程执行”。

线上服务通常把 `SIGTERM` 视为“请开始停止”的通知：停止接受新请求，向负载均衡器报告不可用，等待已有请求在截止时间内完成，关闭连接池和日志，然后退出。处理器中只应做安全、极短的工作，例如设置一个停止标志或唤醒主循环；多数普通函数不是异步信号安全的，在处理函数中直接记录复杂日志、拿互斥锁或分配内存，可能死锁或破坏状态。更稳妥的设计是把信号转成主循环可处理的事件。进程定向的信号会交给某个未屏蔽该信号的线程；而 `pthread_kill` 等接口可以定向到指定线程，所以服务不应假定处理器固定跑在某一条线程上。

`SIGKILL` 不能被捕获、阻塞或忽略，内核收到后直接终止目标。因此它适合无法自行退出的进程，却不会给程序清理临时文件、提交缓冲或发送最终指标的机会。发布系统应先给 `SIGTERM` 和明确的优雅退出期限，超期才以 `SIGKILL` 兜底；应用也必须假设断电和强杀会发生，把关键数据的一致性建立在持久化协议和事务上，而不是寄希望于 `finally` 一定运行。

## 2.8 容器：隔离视图与资源控制

容器不是一台轻量虚拟机，也不是一个神奇的进程类型。典型 Linux 容器仍是一组普通进程，只是被放进不同的**命名空间（namespace）**并受 **cgroup** 约束。命名空间改变进程“看见什么”：PID namespace 让容器内外可看到不同 PID；mount namespace 隔离挂载视图；network namespace 隔离网卡、路由和端口；UTS namespace 隔离主机名；IPC、user、cgroup、time namespace 各自处理相应视图。隔离视图不等于完整安全边界，实际部署还要考虑用户权限、Linux capabilities、seccomp、只读文件系统和镜像供应链。

**cgroup（control group）**按层级组织进程，并由控制器对 CPU、内存、I/O 等资源进行统计和分配。常见的 cgroup v2 容器配置中，一个进程属于 v2 树中的一个 cgroup，限制沿层级生效。容器的 memory limit、CPU 配额或权重通常最终落在这里。它回答的是“这个工作负载最多能用多少、用了多少”；命名空间回答的是“它能看见哪些对象”。两者互补，不能互相替代。

因此，在容器内 `ps` 只看到很少进程、却发现宿主机端口冲突，或容器里看似内存不高却被 OOM 杀死，都应从这两个层面检查：前者可能是命名空间和网络配置，后者可能是 cgroup 限制与记账。排障不要只相信容器名；需要查看进程所在 cgroup、限制值、事件计数和宿主机内核日志。

## 2.8.1 用户态、内核态与一次 I/O 真正经过什么

现代操作系统把执行权限划分为不同的特权级。应用代码处在**用户态**：它可以计算、访问被映射且允许的内存，却不能直接执行特权指令、任意配置网卡或读取其他进程的页表；**内核态**拥有管理处理器、内存、设备和全局内核数据的权限。这个边界不是为了让程序“慢一点”，而是为了让一个有 bug 或被入侵的普通进程不能直接接管整台机器。CPU 会在进程的页表和权限规则不允许某次访问时触发异常；内核检查后可能交付信号、终止进程或完成受控操作。

**系统调用**是应用主动请求内核服务的受控入口，例如 `read`、`write`、`open`、`accept`、`mmap`。调用约定会把系统调用号和参数放入寄存器，CPU 执行专门的陷入指令，保存必要现场并切到内核入口；内核验证指针、权限与对象状态，执行 VFS、网络栈或驱动路径，再返回用户态。它是一次**模式切换**，并不必然是一次**上下文切换**：若数据已经在页缓存或 Socket 接收缓冲区中，`read` 可以立即返回；若没有数据且 fd 是阻塞的，当前线程会睡眠，调度器才可运行另一个可运行任务。

还要分清三类会打断普通控制流的事件。**系统调用/陷入（trap）**通常由当前指令同步触发并有意进入内核；**异常（exception）**由当前指令的特殊情况触发，例如缺页、除零或非法访问；**硬件中断（interrupt）**来自当前指令之外的设备或时钟，例如网卡收到包、磁盘完成 I/O、定时器到期。缺页很能说明边界：用户态访问一个合法但尚未驻留的虚拟页时，CPU 触发同步缺页异常；内核可能从零页、文件或交换空间准备页面并更新页表，随后让同一条指令重试。若页面不可访问，才会给应用一个错误。因而“发生内核态切换”不等于“发生了错误”，而“调用 `read`”也不等于“数据已经从磁盘物理读完”。

网络请求的接收路径可以用这个模型理解：网卡通过 DMA 把帧写入内存并中断 CPU；内核协议栈校验、重组并把字节放入 Socket 缓冲区；阻塞在 `accept` 或 `recv` 的任务被唤醒，或 `epoll` 报告 fd 就绪；用户态服务器再把字节解析为协议消息。中断处理通常只做最紧急的工作，较重的协议处理会延后，以免一个设备把 CPU 长时间占住。应用层看到的“请求到了”已经是内核完成大量工作之后的事件，所以排查网络慢时要分别观察网卡、内核队列、Socket 缓冲、事件循环排队和业务执行时间。

## 2.8.2 同步原语、内存可见性与死锁

并发正确性不只要求“同一时刻只有一个线程写”。处理器和编译器会为了性能重排独立操作，每个 CPU 核也可能暂时看到不同缓存状态；**内存模型**规定哪些同步动作能建立 happens-before（先行发生）关系。互斥锁的正确 `unlock` 与另一个线程成功 `lock`、原子变量的 acquire/release 操作、线程创建和 join 等，通常能把一个线程已发布的写入变成另一个线程可见。只把一个普通布尔变量写成 `ready = true`，再让另一线程忙等并读取对象字段，在一些语言中不构成可靠发布；应使用语言提供的 Mutex、Channel、条件变量或正确的原子序。

**Mutex**保护临界区的互斥与可见性；**条件变量**让线程在“条件尚未满足”时睡眠，并在被唤醒后重新检查条件；**信号量**用计数表达可用许可，例如最多同时运行 N 个任务；**读写锁**在读远多于写且实现与公平性合适时允许多读者并行；**消息通道**把所有权交给单一处理者，常能避免共享可变状态。不要以为原子操作一定优于锁：一段涉及多个字段、失败回滚或跨调用不变量的更新，用小而清楚的锁或数据库条件更新通常更安全。

死锁需要四个条件同时成立：互斥资源、持有并等待、不可抢占和循环等待。工程上最可靠的预防不是“出问题时多重试”，而是减少嵌套锁、给同类资源规定全局加锁顺序、缩短临界区、避免在持锁时做网络 I/O，并在真正需要时设置超时和取消路径。活锁则是多个执行单元都在改变状态却没有推进，例如两个重试循环持续礼让；饥饿是某任务长期得不到资源，例如不公平调度或高优先级流量永远占满连接池。三者都可能表现为“卡住”，但诊断和修复不同。

## 2.9 高频辨析：把相近概念分开

**问：进程、线程、协程的核心区别是什么？** 进程主要提供地址空间和资源隔离；线程是内核可调度的执行路径，并共享所属进程的大部分资源；协程由用户态运行时调度，通常在显式挂起点切换。进程适合隔离故障和利用多核部署，线程适合共享内存下的并行或阻塞库整合，协程适合大量可等待 I/O。它们不是三选一的产品标签：一个服务可以有多个进程，每个进程有线程，每个线程运行很多协程。

**问：并发和并行是不是同义词？** 不是。**并发**表示多个任务在时间上交错推进，例如单核事件循环在 A 等网络时处理 B；**并行**表示多个任务在同一时刻由多个 CPU 核实际执行。并发关注任务组织和等待重叠，并行关注硬件计算资源的同时使用。协程经常带来并发，但单个事件循环本身通常不带来 CPU 并行。

**问：虚拟内存就是物理内存的别名吗？** 不是。虚拟内存是每个进程可寻址、可映射的地址空间抽象；物理内存是实际 RAM 页面。`VmSize` 很大不必然等于占用大量 RAM；RSS 更接近当前驻留页，但包含共享页。用“内存用了多少”回答事故前，应先说清取的是哪个指标和哪个 cgroup 范围。

**问：`SIGTERM` 和 `SIGKILL` 都能杀进程，为什么要区分？** `SIGTERM` 可被应用捕获或忽略，适合作为协作式终止请求；`SIGKILL` 不可捕获、阻塞或忽略，立即终止但没有清理机会。正确顺序是先 TERM、等待有限时间、再 KILL，而不是把 KILL 当成正常停机手段。

**问：用户态和内核态的差别是什么？系统调用一定会发生上下文切换吗？** 用户态代码权限受限，不能直接访问受保护硬件或内核数据；系统调用是进入内核请求服务的受控入口。进入内核态不等于必然切换到另一个线程：`getpid()` 这类短调用可能很快返回；`read()` 因数据未到而睡眠时，调度器才可能选择其他线程。模式切换和线程上下文切换相关但不是同一件事。

**问：阻塞、非阻塞、同步、异步如何区分？** 阻塞/非阻塞描述一次操作在当前条件下会不会让调用线程等待；同步/异步描述结果和完成通知如何交付。非阻塞 `read` 没数据时返回 `EAGAIN`；事件循环稍后收到可读通知再读，是常见异步组织方式。异步 API 内部仍可能用线程完成阻塞工作；“用了 async 关键字”也不保证底层调用不阻塞。

**问：一个进程内线程共享内存，为什么还要数据库事务？** 线程锁只协调同一进程内的内存；多个进程、多台机器、重试请求和直接写数据库的后台任务都绕过它。事务与条件更新保护的是持久化数据上的约束。两者的范围不同：锁可能保护本地缓存的一致性，事务保护订单、余额等跨请求、跨进程的持久状态。

**问：容器和进程隔离是否足以保证安全？** 不足。进程隔离和命名空间减少可见性，cgroup 限制资源，但错误的权限、危险的 capability、挂载宿主机目录、内核漏洞或泄露的凭据仍可能造成严重影响。容器是隔离层的一部分，不能替代最小权限、补丁、网络策略和密钥管理。

## 2.10 小结与练习

本章应留下四个可复用的判断。第一，进程决定隔离边界，线程带来共享状态，协程主要解决等待期间的调度；不要用一个词覆盖三种问题。第二，内存、文件描述符和队列都是有限资源，任何并发设计都要有上限和释放路径。第三，I/O 等待适合事件循环或受控线程，CPU 计算需要有限的并行 worker。第四，容器是 namespace 与 cgroup 等机制的组合，排障必须查看宿主机与 cgroup 事实。

**练习 1：** 一个单线程异步 HTTP 服务在一次图片缩放后，其他请求的延迟突然升高。最可能的原因是什么？应如何改？

**答案：** 图片缩放是 CPU 密集工作，阻塞了事件循环线程，使协程无法在等待点恢复。应把缩放投递到有界的进程或线程 worker，具体选择取决于语言运行时与图像库；同时限制队列和单任务资源，不能无限提交。

**练习 2：** 部署后容器偶发退出码 137。能否直接断言是内存泄漏？列出验证步骤。

**答案：** 不能。137 说明常见情况下进程被 `SIGKILL` 终止，但强制停止也会产生它。检查容器终止原因、cgroup 的 `memory.events`、内核日志与内存限制；再将 RSS/工作集曲线与请求量、缓存、队列和重启时间关联。若增长随负载回落，可能是峰值或缓存；若持续增长且对象无法释放，才进一步查泄漏。

**练习 3：** 你为每个 TCP 请求创建一个线程，流量增大后 CPU 并不高，但 P99 延迟恶化、内存上涨。提出两个可能原因和一个更稳妥的方向。

**答案：** 线程栈和运行时对象使内存增大；大量线程竞争调度、锁或连接池，会增加等待和上下文切换。可改为有界线程池，或对高连接数的 I/O 使用非阻塞事件循环/协程；无论哪种都要设置连接、队列和下游并发上限。

**练习 4：** 为什么 `epoll` 返回“可读”后，仍不能假定读到一条完整 JSON 请求？

**答案：** `epoll` 只报告 fd 当前具备读取条件；TCP 交付的是字节流，数据可能分段到达，也可能一次携带多条应用消息。应用要用长度字段、分隔符或 HTTP 协议解析状态机确定边界，并处理部分读取。

**练习 5：** 订单进程中用互斥锁保护库存变量，是否能阻止两个副本同时超卖？

**答案：** 不能。每个进程有独立的锁和内存，两个副本之间不互斥。应把库存约束放到共享的持久化系统中，例如数据库的条件更新、事务与合适的隔离级别；本地锁只能保护该进程内的状态。
