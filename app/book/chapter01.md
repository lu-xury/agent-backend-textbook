## 1. 从一次请求看程序究竟在做什么

设想客户端请求“查询用户 42 的公开资料”。服务端先把网络报文解析为 user_id=42，检查这个值是否合格，从存储系统取到记录，按照权限删去不该公开的字段，再把结果编码为 JSON 返回。这里至少有四种东西：**值**（42、昵称、布尔值）、**对象或数据结构**（用户记录）、**操作**（查询、校验、转换）和**边界**（网络、数据库、文件、其他服务）。

程序执行时会保存状态。局部变量保存一次函数调用暂时需要的信息；进程内存中的对象保存正在处理的结构；数据库保存跨请求、跨重启也要存在的业务事实。不要把它们混为一谈。变量只是在一次计算中给某个东西起名字，内存对象的生命期受进程影响，而数据库记录通常才是“用户已经注册”“订单已经付款”这类业务状态的权威来源。承载该进程的实例重启后，局部变量和普通内存对象会消失；已提交、已持久化且存储系统仍可用的记录通常还能被读取。

这一区分解释了一个常见故障：开发者把“已登录用户”放进某个进程的全局字典，单机测试正常；扩容到两台机器后，下一次请求可能落到另一台机器，字典里没有这个用户。故障来自状态层次误判：**进程内状态**被当成了**跨机器共享的业务状态**。以后学习缓存、会话和一致性时，本章的状态层次会反复出现。

> **读代码的起点**：先找输入来自哪里、哪些地方会改变外部世界、哪个系统保存最终事实。不要从第一行开始逐字翻译。

## 2. 变量、对象和值：名字不是东西本身

**变量**是在某个作用域内可重新绑定的名称或存储位置；在许多高级语言的解释模型中，可把赋值理解为“名称绑定到一个值，或绑定到可引用对象的引用”。**值**强调数据内容，例如整数 18、字符串 “alice”、真值 true。**对象**通常指有身份、类型和可访问状态的运行时实体；不同语言对“对象”和“变量”的精确定义不同，但把它先理解为“程序能引用和操作的一份数据实体”已经足够实用。

变量不是一个装数据的小盒子。这个比喻在初学阶段有用，却会遮住别名问题。看 Python：

```python
profile = {"name": "Lin", "roles": ["reader"]}
same_profile = profile
same_profile["roles"].append("writer")
print(profile["roles"])  # ["reader", "writer"]
```

profile 和 same_profile 是两个名字，却引用同一个字典对象；第二行没有复制用户资料。这个现象叫**别名**：多个入口可以修改同一可变对象。后端里的配置对象、请求上下文和缓存值若被意外共享，就会出现“明明只改了 A，B 为什么也变了”的错误。

**不可变对象**创建后不能就地改写。Python 的整数与 `str`、Java 的数值包装类型与 `String` 都属于常见例子：把 `count` 加一，是计算新值后让名字指向它；对 Python 列表调用 `append` 则是修改原对象。Rust 还把“绑定能否重新赋值”和“值类型能否修改”分开：`str` 内容不可变，拥有所有权的 `String` 在可变绑定下可以修改。C/C++ 的字符数组也可以原地改写。因此，“字符串是否可变”必须同时说明语言和具体类型。不可变值更容易安全地共享、缓存和作为映射键；可变对象适合表达逐步构造的状态，但必须确认谁拥有修改权，以及谁还能看见这次修改。

对象身份也与值相等不同。两张内容完全相同的订单快照可能是不同对象；同一个订单对象更新后，身份可以不变而字段值已改变。业务代码通常关心订单号或响应内容是否相等，而不是它们是否恰好在同一块内存。因此比较规则必须明确，不能把语言里的引用比较随手当作业务相等。

复制也有层次。浅复制只复制最外层容器，内部可变对象仍会共享；深复制递归复制全部内容，代价更高，也可能破坏本来应共享的对象身份。对外返回 API 数据时，更稳妥的做法常常不是深复制整个领域对象，而是构造一个只含允许字段的响应 DTO。这样同时解决字段泄露、对象耦合和复制成本三个问题。

## 3. 类型不是装饰：它在边界处缩小不确定性

**类型**说明一个值可取的集合，以及程序允许对它做的操作。整数、文本和布尔值都是常见类型；UserId 则可以是更有业务含义的值对象。静态类型语言在编译期检查许多不匹配；动态类型语言把更多检查留到运行期，但同样需要把输入转成合适的类型。

类型把“任何输入都可能到来”的模糊地带变为可验证的有限情况。HTTP 路径参数 “42” 起初只是字节和文本；在确认它能表示十进制整数且范围合理后，业务代码才可以把它当作**格式合法的用户标识符**。用户是否存在、当前调用者能否访问它，则是随后查询和授权要回答的不同问题。若跳过解析和校验，“-1”、“4.2”、极长字符串甚至恶意构造的 JSON 都会渗进本应只处理正常业务的函数。

**边界**是数据从一种可信度、表示或所有权跨到另一种的地方：网络请求进入服务、数据库行变成领域对象、环境变量读入配置、第三方接口返回响应，都是边界。边界处应完成解析、校验和归一化。解析回答“能否按语法读出来”；校验回答“读出来的值是否符合规则”；归一化回答“等价输入要不要变成统一表示”。手机号可去掉空格和连字符；密码不能擅自去掉空格，因为空格可能就是密码的一部分。

```python
def parse_page(raw: str) -> int:
    try:
        page = int(raw)
    except ValueError as exc:
        raise ValueError("page 必须是整数") from exc
    if not 1 <= page <= 1000:
        raise ValueError("page 必须在 1 到 1000 之间")
    return page
```

这段代码先处理表示层错误（不能转成整数），再处理业务边界（虽是整数但不在允许范围）。把两件事分开，错误信息和测试都会清楚得多。类型和校验也不能互相替代：即使 page 的静态类型是整数，仍可能是负数；即使数据库列是 VARCHAR(32)，也不表示其中一定是合法邮箱。类型主要减少“形状错误”，业务规则表达“在当前领域中是否允许”。

## 4. 函数与契约：把可依赖的条件写出来

**函数**把一段计算封装为可调用单元：给定输入，按照某种规则产生返回值、错误或副作用。函数为调用者提供稳定的理解边界，拆分粒度应服从这个边界。调用者应知道需要提供什么，成功时得到什么，失败时会发生什么；实现者可以在不破坏这些承诺的前提下替换内部算法。

这组承诺就是**契约**。一个好的函数契约至少包含前置条件、后置条件和副作用。前置条件是调用前必须满足的事实，例如金额为正；后置条件是成功返回后保证成立的事实，例如创建订单后返回唯一编号；副作用是函数会改变函数外世界的部分，例如写库、发消息、扣库存。普通业务函数通常无需形式化证明，但这些内容应能从命名、类型、注释、测试或接口文档中看出来。

```python
def withdraw(account: Account, amount: Money) -> Receipt:
    """从可用余额扣除正数金额；余额不足时不改变账户。"""
```

“余额不足时不改变账户”很关键：它规定了失败路径的状态。后端事故常不是成功路径写错，而是失败后只扣了余额、没有生成订单，或者重复调用又扣了一次。

函数可以是纯函数，也可以有副作用。**纯函数**的结果只由输入决定，且不修改外部可观察状态，例如把金额从分格式化为字符串；它易测试、易缓存、易并行推理。读取当前时间、写数据库、调用支付服务则不是纯函数。无需把所有代码伪装成纯函数；更实际的设计是把“计算规则”和“执行 I/O”分开。订单总价计算可以是纯函数，保存订单和发送通知集中在较薄的一层里。

契约还包括**所有权**。函数收到一个列表后，是只读、会原地排序，还是会把它保存起来供以后使用？三种行为都可能合理，但必须可预期。对公共接口而言，默认不修改调用者传入的可变数据通常更安全；若为了性能必须原地修改，应从名称或文档显式表达，例如 sort_in_place。

## 5. 错误、异常与资源：失败不是“返回空值”

后端程序面对的失败比普通算法题多得多：客户端参数错误、账户不存在、权限不足、数据库暂不可用、网络超时、磁盘写满，以及程序自身的断言被破坏。把它们全都写成 None、false 或字符串 “error”，调用者就无法判断下一步该提示用户、重试、报警还是立即停止。

先按可恢复性和责任划分错误。**预期的业务拒绝**，例如库存不足、优惠券过期，通常应该有稳定错误码和面向调用者的说明；它们是正常业务分支，不应按服务崩溃告警，但仍应以业务指标统计其数量和比例。**暂时性基础设施错误**，例如依赖服务超时，可能可以在受控条件下重试，但重试必须有次数上限、退避和幂等保护。**程序错误**，例如违反内部不变量，不能靠无限重试掩盖，应保留诊断信息并修正代码。

异常是一种语言级的非正常控制流工具，不等同于“所有错误”。对 HTTP API 而言，通常用结构化错误响应表达可预期失败；在服务内部，可以用 Result、异常或显式错误对象。选择哪种风格不如保持一致重要。关键是调用者必须能区分：这次失败是否可以修正输入、是否值得重试、是否需要报警。

```http
HTTP/1.1 409 Conflict
{"code":"INSUFFICIENT_STOCK","message":"可售库存不足","request_id":"req_7f"}
```

**HTTP 状态码**描述本次 HTTP 交互的大类结果，便于通用客户端、网关和监控理解；**业务错误码**给本系统调用者稳定的分支依据；**内部异常**保留堆栈和依赖错误等诊断信息，不应原样暴露给客户端。同一个库存不足可以是 HTTP 409 加 INSUFFICIENT_STOCK；数据库连接超时可以对外是 503 或 504，对内仍保留具体异常与 request_id。

**资源**是需要在适当时机归还或关闭的有限能力，例如文件描述符、数据库连接、网络套接字、锁和临时文件。内存和外部资源必须分开看：垃圾回收语言会在不确定的时间回收**不可达内存**，不能把文件、连接或锁的及时释放交给它；C++ 等采用 RAII 的语言可让析构在作用域结束时执行清理，但仍要设计资源所有者与释放顺序。连接池中的连接若没有归还，流量不大时也许不明显；并发升高后池耗尽，请求便会排队直至超时。

```python
with open("audit.log", "a", encoding="utf-8") as file:
    file.write("user=42 action=login\\n")
# 离开 with 语句块后文件关闭，即使 write 抛出异常
```

不同语言的语法不同，原则相同：获取资源后，应让释放动作与获取紧邻，并保证无论成功还是失败都会执行。自动释放减少遗漏，不能取代对资源所有者、关闭顺序和超时的设计。数据库事务还要区分“归还连接”和“提交或回滚事务”：连接被关闭或归还，并不自动说明本次业务修改应当提交。

## 6. 算法复杂度：先看增长趋势，再测真实成本

**算法复杂度**描述输入规模增长时，运行时间或额外空间如何增长。更严格地说，Big-O 给出输入规模趋于无穷时的**渐近上界**；它必须同时说明 n 的含义和分析口径，例如最坏、平均或摊还情况。它不是一次真实请求耗时的替代品，而是一种先验的风险判断工具。大 O 忽略常数和低阶项，是为了看清当数据从一千条增长到一百万条时，哪种做法会改变数量级。

查询数组第一个元素是 O(1)，遍历 n 个元素求和是 O(n)。若对每个用户都线性扫描全部订单，工作量可能是 O(n²)。把订单预先按 user_id 建索引或映射后，构建索引通常需 O(n)；在常见均匀哈希假设下，每个用户查找的期望时间为 O(1)，总处理趋向 O(n)。哈希表的期望 O(1) 不等于任何条件下严格恒定；哈希冲突、扩容、缓存未命中和数据库 I/O 都会改变实际延迟。

复杂度必须先说明 n 是什么。分页接口中 n 可以是结果条数、表总行数或每个用户的关联记录数；不同定义会导向不同结论。数据库 LIMIT 20 不必然让查询是 O(20)：若没有合适索引，数据库仍可能扫描和排序大量行后才取出 20 条。复杂度分析帮助发现“把全量数据读到应用层再过滤”的危险；执行计划、指标和压测才告诉你实际系统是否真的慢在这里。

空间复杂度同样重要。一次把一千万行 CSV 全读入内存，时间也许是线性的，却可能让进程被系统杀死。流式处理一次只保留当前批次，通常把额外空间从 O(n) 降到 O(1) 或 O(batch size)，代价是不能随意回看已处理的数据。选择数据结构，本质是在时间、空间、实现复杂度和访问模式之间权衡。

不要把“大 O 小的算法一定更快”当结论。n 很小时，O(n) 的简单循环可能比 O(n log n) 的复杂排序更快；网络往返二十毫秒时，把 CPU 从一微秒优化为零点五微秒没有用户可感知的收益。正确顺序是：用复杂度避免明显的规模灾难，用测量找当前瓶颈，只优化确实影响容量、成本或延迟目标的部分。

## 7. 接口与模块：让变化被限制在边界内

**接口**是调用者与实现者之间可见的约定。语言级接口解决模块替换，网络 API 解决跨进程协作；它们不属于同一语言机制，却都必须约定能力与语义。接口不等于函数签名：签名只写参数和返回类型，接口还包含语义，例如字段是否必填、重复请求是否安全、错误码代表什么、调用是否有副作用、版本如何演进。

例如 GET /users/42 的接口至少要说清：42 放在哪里；成功时哪些字段存在；用户不存在是 404 还是空对象；调用者可否缓存；手机号是否绝不能返回。没有这些约定，前后端即使“接口通了”，也会在边缘情况各自做出不兼容假设。稳定接口应围绕消费者真正需要的能力设计，而不是把内部数据库表原样暴露出去。

**模块**把相关实现和私有细节放在一起，只暴露必要接口。认证模块可以暴露 verify_access_token，却不让其他模块直接读取其密钥缓存；订单模块可以使用仓储接口查询订单，不必知道底层是 PostgreSQL 还是测试中的内存实现。这样做不是为了多写几层目录，而是为了控制依赖方向：上层业务依赖抽象，具体数据库驱动依赖抽象并实现它。

抽象也有成本。只有一个查询、没有替换可能时，额外造十个接口只会隐藏流程；当实现确实有变化轴——例如本地文件与对象存储、真实支付与沙箱支付、多种消息队列——接口才特别有价值。判断标准不是“是否使用了设计模式”，而是**变化发生时，修改是否被限制在少数地方**。

## 8. 一个很小但完整的例子

这段伪代码描述“把一件商品加入购物车”，并把本章概念放进同一条执行路径：

```text
addItem(userId, sku, quantity):
    要求：quantity 是 1 到 99 的整数；userId 已通过认证
    product = catalog.findPublicProduct(sku)
    若 product 不存在：返回 PRODUCT_NOT_FOUND
    若 product.stock < quantity：返回 INSUFFICIENT_STOCK
    cart = cartRepository.getOrCreate(userId)
    cart.add(sku, quantity)
    cartRepository.save(cart)
    返回 cart 的公开快照
```

| 在这段代码中 | 它解决的问题 | 不应误解为 |
| --- | --- | --- |
| 类型与校验 | 在入口拒绝不合法数量 | 类型能自动保证库存正确 |
| `catalog` / `cartRepository` 接口 | 隔离数据取得与保存方式 | 必须为每个类都创建接口 |
| 业务错误码 | 让调用方能据此分支处理 | 向客户端暴露内部异常 |
| `cart.add` | 修改购物车这一份业务状态 | 已经完成最终库存扣减 |

userId、sku、quantity 是值或值对象；cart 是可变领域对象；catalog 和 cartRepository 是接口；findPublicProduct 不直接返回数据库行，是为了守住公开字段的边界。库存不足属于可预期业务拒绝，不应被包装成“服务器内部错误”。这里的 product.stock 只用于提示“当前看起来可添加”，不是最终库存预留；真正创建订单时，库存服务或数据库事务必须用条件更新等方式保证“检查与扣减”在并发下仍一致。如果以后发现同一购物车有十万条商品，才需要讨论 cart.add 在数组里查重是线性还是通过映射常数时间定位。概念并非独立背诵，而是在这种小流程中共同约束程序行为。

## 8.1 数据结构与算法设计

算法设计在明确输入、输出与约束后，选择一种能维持正确性的状态组织和推进方式。**数组**把同类元素连续存放，适合按下标随机访问；**链表**用链接换取局部插入和删除的便利，却不能常数时间跳到第 `i` 个元素；**栈**强调后进先出，适合函数调用、撤销和括号匹配；**队列**强调先进先出，适合排队、广度优先搜索和工作分发；**哈希表**用键的哈希值定位桶，平均查找常为 `O(1)`，但会受碰撞、扩容和恶意输入影响；**树**和**堆**则适合维持顺序、范围或最值。它们没有“最好”的排名，只有数据规模、访问模式、更新频率和正确性要求是否匹配。

写算法前先写出**不变量**：它是每次循环开始或结束时都必须仍然为真的条件。二分查找的不变量可以是“若目标存在，它一定仍在闭区间 `[left, right]` 中”；每次比较后排除一个不可能包含目标的半区，区间严格缩小，因此循环会终止。这样解释比背模板更可靠，也能立刻发现常见的 `mid ± 1`、边界初始化和重复元素处理错误。函数的前置条件、循环不变量、终止性和后置条件共同构成一段小程序的正确性论证：输入合法吗，循环中没有破坏什么，为什么不会无限执行，返回值为什么满足承诺。

```python
def first_at_least(items: list[int], target: int) -> int:
    # 返回第一个 >= target 的下标；若不存在则返回 len(items)。
    left, right = 0, len(items)
    while left < right:
        mid = left + (right - left) // 2
        if items[mid] < target:
            left = mid + 1
        else:
            right = mid
    return left
```

这里使用半开区间 `[left, right)`：循环不变量是“答案在这个区间内”，每轮都把区间缩小，`left == right` 时答案唯一确定。`mid = left + (right - left) // 2` 在 Python 中不会溢出，但在固定宽度的 C++、Rust 或 Java 整数类型中是值得养成的写法。真实接口还要处理空列表、排序前提、整数范围和调用方是否允许不存在的结果；算法正确不等于接口契约完整。

常用的算法范式各解决不同结构的问题。**分治**把问题拆成规模更小、结构相同的子问题，再合并结果；归并排序因此稳定地达到 `O(n log n)`，代价是额外空间。**贪心**每步选当前看来最优的局部选择，只有能证明贪心选择性质时才正确，不能因为“看起来合理”就使用。**动态规划**把有重叠子问题的递归状态保存起来，关键是状态定义、转移方程、初值和计算顺序，而不是背 `dp` 数组。**BFS**按距离层次扩展，适合无权图最短路；**DFS**适合遍历、连通性、拓扑排序和回溯；带非负权重的最短路通常需要 Dijkstra 一类算法。后端最常见的收益不是手写这些算法，而是能识别：一次 N+1 查询、无界重试、逐条扫描日志或在列表头部反复插入，是否把原本可索引、批量或队列化的问题写成了随规模失控的算法。

## 8.2 手写题怎样连接到工程：以 LRU 为例

LRU（least recently used）缓存要求容量满时淘汰**最久没有被访问**的项。若只用数组，每次访问都要在线性表中查找并移动元素，`get` 或 `put` 至少有一个会变成 `O(n)`；高频题的要求通常是期望 `O(1)`。组合**哈希表**和**双向链表**即可：哈希表从 key 找到节点，双向链表把最近使用的节点放在表头、最旧节点放在表尾；命中时把节点移到表头，满时删除表尾。这里的核心不是背容器组合，而是维护两条不变量：`positions_` 中的每个迭代器都指向 `items_` 的唯一节点；链表顺序始终从新到旧。

```cpp
#include <cstddef>
#include <list>
#include <optional>
#include <unordered_map>
#include <utility>

class LruCache {
 public:
  explicit LruCache(std::size_t capacity) : capacity_(capacity) {}

  std::optional<int> get(int key) {
    const auto found = positions_.find(key);
    if (found == positions_.end()) return std::nullopt;

    // splice 只移动链表节点；该节点的迭代器仍然有效。
    items_.splice(items_.begin(), items_, found->second);
    return found->second->second;
  }

  void put(int key, int value) {
    if (capacity_ == 0) return;
    if (const auto found = positions_.find(key); found != positions_.end()) {
      found->second->second = value;
      items_.splice(items_.begin(), items_, found->second);
      return;
    }

    if (items_.size() == capacity_) {
      positions_.erase(items_.back().first);
      items_.pop_back();
    }
    items_.emplace_front(key, value);
    positions_[key] = items_.begin();
  }

 private:
  using Entry = std::pair<int, int>;
  std::size_t capacity_;
  std::list<Entry> items_;  // 表头最新，表尾最旧。
  std::unordered_map<int, std::list<Entry>::iterator> positions_;
};
```

`std::unordered_map` 的常见查找是期望 `O(1)`，`std::list::splice` 与删除已知节点也是常数时间，因此上面的两种操作符合题目目标；最坏情况仍会受哈希碰撞影响。这个类缺少线程同步：两个线程同时改 `items_` 或 `positions_` 会破坏不变量。实际服务还必须决定 TTL、容量、淘汰指标、是否允许陈旧值以及锁的粒度；很多场景直接使用经过压测的缓存库或 Redis，比手写共享 LRU 更合适。面试中先给出数据结构、不变量和复杂度，再主动指出并发与失效边界，比只写完代码更能证明理解。

## 9. 易混概念与面试辨析

### 变量、对象和值有什么区别？

变量是名字或绑定，值是数据内容，对象是运行时可被引用和操作的实体；具体语言的实现不同。面试官真正想确认的通常是你是否理解别名和可变性：两个变量指向同一可变对象，任何一个原地修改都会被另一个观察到；在函数内把参数重新绑定到新对象，调用者的变量不会随之重新绑定。只答“变量在栈、对象在堆”既不跨语言准确，也没有解释共享修改为何发生。

### 静态类型和动态类型谁更安全？

二者不是安全与不安全的二选一。静态类型能在运行前拒绝大量形状不匹配，并让重构更可靠；动态类型依靠运行时检查、测试和约定，也能构建可靠系统。真正的边界风险来自不可信输入和业务规则：即使编译器确认 age 是整数，仍要校验年龄范围。回答时要把“类型检查发生的时机”和“业务合法性”分开。

### 值传递和引用传递应该怎样回答？

先问语言的参数传递语义，不要只背“某语言传引用”。Python 官方把它称为**按赋值传参**：形参是新的局部名字，最初绑定到与实参相同的对象。因此原地修改可变对象会被调用者观察到；重新绑定形参不会改变调用者的名字。

```python
def change(items):
    items.append("x")  # 修改共享的列表对象
    items = ["new"]    # 只让局部名字改绑

data = []
change(data)
# data == ["x"]，不是 ["new"]
```

C++ 的 T、T&、T* 是显式不同的参数形式；Rust 还区分移动、共享借用 &T 和可变借用 &mut T。跨语言面试须先说明语言与参数声明。栈、堆、寄存器和逃逸分析是编译器或运行时的实现细节；它们会影响性能和生命周期，却不能替代别名、可变性和作用域的语义解释。

### 异常和错误码该怎么选？

可预期、需要调用方据此分支的业务结果，例如库存不足、验证码失效，适合稳定错误码或 Result 分支；跨越多层且无法就地处理的异常状况，可以借助异常向上交给统一边界处理。关键是保留错误分类和上下文，不能捕获所有异常后统一返回成功或空值。异常不是更高级的 if，错误码也不是把所有失败塞进字符串。

### 时间复杂度 O(n) 就一定优于 O(n log n) 吗？

只在规模足够大、成本模型相近时，增长阶才占主导。O(n) 算法若每一步访问远程数据库，可能远慢于在内存中做 O(n log n) 排序。复杂度先比较随 n 增长的趋势；真实性能还依赖常数、数据分布、缓存、I/O 和并发。

### 平均 O(1) 和最坏 O(1) 有什么区别？

平均或期望 O(1) 表示按输入或哈希分布平均后，单次操作不随 n 增长；最坏 O(1) 则要求任何合法输入都保持常数上界。哈希表查找通常讨论前者，动态数组尾部追加还常讨论“多次追加后的摊还 O(1)”。回答复杂度时应主动说出口径。

### 接口和抽象类或具体实现有什么关系？

接口声明调用者可以依赖的能力与语义；抽象类可在此基础上共享部分状态或默认实现；具体类落实细节。HTTP API 同样是一种接口，即使没有语言级 interface 关键字。把依赖放在接口上，是为了让调用方不绑定某一种数据库、支付渠道或消息队列；若没有变化需求，直接使用具体实现也可能更简单。

## 10. 自测练习与答案

### 练习：为什么不能把“请求参数能够转换为整数”当成“请求合法”？

转换成功只说明表示合法，不说明业务允许。limit 还可以要求大于 0、不得超过服务上限、缺省时采用固定默认值，并决定过大时是拒绝还是截断。若它影响数据库查询，还应避免让客户端以极大数值消耗资源。

### 练习：某函数接收用户列表，为排序直接调用原地排序，调用方后来发现显示顺序被改变。违反了什么契约？

函数产生了未说明的副作用：修改了调用方拥有的可变对象。可以先复制后排序并返回新列表；若性能或语义要求原地排序，应把函数命名为 sort_users_in_place，并在文档中明确写出。哪一种更好取决于调用者是否应观察到这次修改。

### 练习：报表接口对每个用户查询一次订单表，为什么常被称为 N+1 查询问题？

先查询用户一次，再对 n 个用户各发一次订单查询，总共约 n+1 次远程数据库往返；瓶颈不只是循环次数，还是重复 I/O。通常先用一次关联查询或批量按用户 ID 查询，再在内存中分组；之后用执行计划与真实数据量验证索引和结果是否合适。

## 11. 本章小结

后端代码可以从“状态和边界”开始读：变量给运行时数据命名，值表达内容，对象承载可操作状态；类型和校验把不可信输入变成可处理的数据；函数以契约约束成功、失败与副作用；资源必须在所有路径上归还；复杂度先判断增长风险，再由测量确认真实瓶颈；接口和模块把实现细节留在可替换的边界之后。
