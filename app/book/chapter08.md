后端安全不是在接口末尾再加一层“鉴权中间件”，而是先回答几个朴素的问题：谁可以发起请求；服务凭什么相信它；这个身份此刻能做什么；数据在传输、存储和操作时怎样不被不该看到的人获得或篡改；出现异常时怎样发现、止损和复盘。本章讨论的是 Web 后端的基础安全模型。它不能替代针对支付、医疗、车联网等行业的合规与专业评审，却足以帮助你把大多数日常系统从“默认相信输入”改成“明确建立信任”。

## 8.1 从资产和边界开始：威胁建模与最小权限

**威胁模型**是对“要保护什么、谁可能做坏事、经过哪条路径、造成什么后果、用什么控制降低风险”的明确假设。它不是列举骇人的攻击名词。一个在线文档服务的资产包括文档内容、用户账号、访问令牌、管理员操作能力和数据库备份；主体既有普通用户、管理员和运维程序，也有匿名访客、第三方应用、被入侵的账号和出错的内部服务。浏览器到网关、网关到应用、应用到对象存储、CI 到生产环境，都是不同的信任边界。数据每跨过一次边界，接收方就不能仅凭“它来自内部”而默认可信。

画威胁模型时，先写出一次重要操作的流向，再在每个箭头旁问四件事：身份能否伪造，消息会不会被偷窥或篡改，调用者会不会越权，事后能否还原发生过什么。以“下载某份合同”为例，后端不仅要确认请求带了有效登录态，还要判断该用户是否属于这份合同所属的组织；生成对象存储下载链接时还要限制方法、对象和有效期；审计记录要能说清是哪个主体在何时下载了哪个资源。只验证登录态而不检查资源归属，是典型的对象级越权。

**最小权限原则**要求主体只获得完成当前任务所必需的最小能力，并在不再需要时回收。它适用于人、服务账户、数据库用户、云角色和访问令牌。报表服务只需读取聚合表，就不应拥有删除订单的数据库权限；上传接口只应写入某个前缀，而不应获得整个存储桶的管理员权限。最小权限的价值不在于假定每个人都会犯错，而在于把单个凭据泄露或单段代码缺陷的影响限制在较小范围。

权限设计还应考虑**默认拒绝**和**职责分离**。默认拒绝表示：没有明确允许规则时，拒绝操作；不要把“未配置权限”解释成“暂时放行”。职责分离表示高风险动作不应由一个长期凭据独自完成，例如生产密钥的创建与使用、退款审批与实际付款可以由不同角色承担。安全不是把权限切得越细越好：规则过细而无人理解时，同样会形成漏洞。合理做法是按资源、动作和业务风险分层，在代码、数据库和基础设施三个层面共同执行。

## 8.2 认证：先确认“你是谁”

**认证（authentication，常写作 AuthN）**是验证主体所声称身份的过程；它得到的是“这个请求代表用户 A”或“代表服务 B”的结论。用户名只是标识，不是证明。密码、一次性验证码、硬件安全密钥、客户端证书和受保护的私钥，才是可用来证明的认证因子。常见因子分为“你知道的”（密码）、“你持有的”（手机、硬件密钥）和“你本身具备的”（生物特征）；多因素认证要求至少两类相互独立的因子。

密码登录的服务端过程很短：收到用户名和密码后，按用户名找到账户的密码验证值，用专用的密码哈希函数验证候选密码；成功后创建登录态，失败则返回不泄露账户存在与否的通用提示。登录接口还需要限速、异常检测和多因素认证，以抵抗撞库、密码喷洒和暴力猜测。**密码重置不是“再发一次密码”**：应发送一次性、短时、不可预测的重置凭据，服务端保存其哈希值而非明文，成功使用后立即失效；重置端点也要限速、使用通用响应，并对改邮箱、改支付信息等敏感操作要求重新认证。

不要把用户密码、第三方 API Key 和内部服务账号混在同一个认证模型中。用户登录强调交互体验、恢复流程与 MFA；服务到服务的访问通常采用短期工作负载身份、mTLS 或受限访问令牌，不应在配置文件里长期保存一个万能管理员密码。机器账号也应可识别、可撤销、可审计，而不是多人共用的“service”账号。

### 登录态：Cookie、Session 与 JWT

HTTP 本身不记得上一个请求是谁，因此登录后必须在请求间传递某种凭据。

**Cookie**：浏览器保存并按域名、路径等匹配规则自动附带的一小段数据载体；`Secure` 属性才限制它只经 HTTPS 发送。它不是认证方案，也不天然安全。若用 Cookie 承载会话标识，应设置 `Secure`、`HttpOnly`（前端脚本不能读取）和合适的 `SameSite`，优先不设置 `Domain` 以形成 host-only Cookie；确需跨子域共享时再缩小范围。`SameSite=None` 必须同时设置 `Secure`。Cookie 自动携带正是它容易受 CSRF 影响的原因。

**Session**：服务端保存的登录会话状态，例如 `session_id → user_id、过期时间、认证强度`；浏览器通常只保存一个随机且不可预测的 session id。它的优点是可立即撤销、可保存较多状态，缺点是多实例部署需要共享会话存储或粘性会话。Session 不等于 Cookie：前者是状态管理方式，后者是浏览器传递数据的机制；完全可以用 Cookie 传 session id。

**JWT（JSON Web Token）**：一种承载声明的令牌格式；最常见的**签名 JWT（JWS）**以 `header.payload.signature` 三段紧凑形式出现。签名让接收方能验证令牌由可信签发者发出且未被改动；payload 通常只是 Base64URL 编码，任何拿到令牌的人都能读到其中的声明。因此 JWT 不适合放密码、身份证号等敏感数据。JWT 可以减少每次请求查询会话存储的需要，但一旦签发、在过期前通常难以按单个用户即时撤销；这不是“更先进”的 Session，而是在可撤销性、状态一致性和分布式验证之间的取舍。生产系统应验证签名算法、签发者 `iss`、受众 `aud`、过期时间 `exp`、生效时间与密钥轮换信息，且不要接受客户端指定的算法。

简化地说：同站点 Web 应用常把 session id 放在受保护的 Cookie 中；跨服务 API 常使用短期、范围明确的 bearer token；两者都需要过期、轮换、撤销策略和传输保护。选择依据是调用环境和撤销需求，而不是“JWT 无状态所以必然更好”。

### OAuth 2.0 与 OpenID Connect

**OAuth 2.0**解决的是委托授权：资源所有者允许一个客户端在有限范围内访问资源服务器，而不把自己的密码交给客户端。基本角色是资源所有者（通常是用户）、客户端（想访问资源的应用）、授权服务器（认证用户并签发令牌）和资源服务器（保存 API/数据并验证令牌）。授权服务器向客户端发放访问令牌，资源服务器据 scope、受众和令牌状态决定是否处理请求。

例如“用某云盘账号授权一个图片打印应用读取指定相册”中，用户是资源所有者，打印应用是客户端，云盘的身份平台是授权服务器，云盘 API 是资源服务器。用户在授权服务器的页面登录并同意后，客户端取得限定范围的令牌。客户端不该接触用户的云盘密码。对浏览器和移动端等公有客户端，授权码流程应配合 PKCE；回调地址必须精确注册和校验，不能只检查前缀。

PKCE 解决的是授权码被截获后的利用问题；浏览器发起授权前仍应生成并保存不可预测的 `state`，回调时精确匹配它，以绑定“这次回调属于这次发起的登录或授权”。使用 OIDC 时，客户端还必须按发现文档和协议验证 ID Token 的签名、`iss`、`aud`、`exp`，并验证与本次认证请求绑定的 `nonce`；不能仅解码出邮箱或用户名就把用户登录。

OAuth 本身不等于“登录”。若需要让客户端确认用户身份，通常使用 **OpenID Connect（OIDC）**，它在 OAuth 之上定义身份层和 ID Token。访问令牌用于调用资源 API，ID Token 面向客户端说明认证结果；不要拿 ID Token 当作任意资源服务器的通行证，也不要因为令牌里有用户名就跳过资源端的授权检查。

## 8.3 授权：身份确认后，仍要问“能不能做”

**授权（authorization，AuthZ）**是在已知主体身份、资源和上下文后，决定某个动作是否允许的过程。一个通过认证的员工并不自动有权读取所有客户数据。授权判断至少应包含 `主体 + 动作 + 资源 + 上下文`；只检查 URL 里是否出现 `admin`、只隐藏前端按钮，均不是授权。前端只是体验层，真正的拒绝必须发生在服务端、数据访问层或基础设施策略中。

**RBAC（基于角色的访问控制）**通过角色聚合权限。例如 `viewer` 可以读项目，`editor` 可以修改项目，`billing_admin` 可以处理账单。它易于理解、审计和批量授予，适合岗位相对稳定的后台系统。RBAC 的隐患是角色膨胀：当每个例外都造一个新角色，规则会失去可读性。可用“角色只表达稳定职责，例外使用资源归属或临时授权”控制复杂度。

**ABAC（基于属性的访问控制）**以主体属性、资源属性和环境属性写规则，例如“医生可查看同一医疗机构、自己负责的患者，紧急值班时可额外查看但必须记录理由”。它更能表达组织、地域、时间、数据敏感级别等条件，却需要可靠的属性来源、策略语言与测试。ABAC 并非 RBAC 的替代品：实践中常以 RBAC 提供粗粒度岗位权限，再用资源的组织 ID、所有者 ID 和状态做细粒度约束。

**对象级权限**解决“同一个 API 对不同对象权限不同”的问题。接口 `GET /documents/{id}` 的正确问题是“当前主体能否读取 id 对应的这份文档”，而不是“当前主体是否登录”。查询时应将组织或所有者条件带入数据库，例如按 `document_id`、`tenant_id` 和允许成员集合共同筛选；不能先通过 id 取到对象，再仅因对象存在就返回。批量接口、导出接口、文件下载链接和 GraphQL 查询同样需要逐对象或等价的集合授权，不能只保护单个详情接口。

高风险操作还应考虑**重新认证**、双人审批、金额/范围上限和幂等键等业务控制。授权的结果最好可解释：策略拒绝时，系统至少能在受限审计记录中说明命中了哪条规则；但对外响应不应泄露资源是否存在或内部权限结构。

## 8.4 数据保护：密码、哈希、加密和编码不是同一种东西

**哈希**把任意输入映射为固定长度摘要，设计目标是单向和难以碰撞；它不用于还原明文。密码存储必须使用专门的、可调慢的密码哈希函数，如 Argon2id、scrypt、bcrypt 或 PBKDF2，并为每个密码使用随机 salt。salt 不是秘密，它用来避免相同密码得到相同结果、削弱预计算攻击；可选的 pepper 是系统另存的附加秘密，但不能替代安全的哈希算法。不能用普通 SHA-256/MD5 直接存密码，也不能“先加密再保存”，因为密码验证只需比较，不应需要解密。哈希工作因子应随着硬件和风险复审提高，验证使用库提供的安全比较函数。

**加密**是用密钥把明文变成可恢复密文，目标是保密性；有认证的加密模式还可同时发现篡改。它适合需要日后取回的身份证件、外部 API 凭据或备份数据。密钥管理是加密系统的一部分：真正能解密的数据密钥或其上层根密钥必须位于与数据存储分离的访问控制域，例如 KMS；不能把可直接使用的明文密钥和密文一起交给同一低权限读取者。信封加密中，密文旁可以保存**被 KMS 包装的数据密钥**，因为没有 KMS 权限仍无法解开它。使用受管理的 KMS、访问策略、轮换与版本标识，能把“谁能解密”变成可管理的权限问题。加密不自动解决“有权限的服务把数据发错人”，那仍是授权问题。

**编码**只是数据表示转换，如 URL 编码、Base64、UTF-8；它可逆且不需要密钥，因此没有保密性。JWT payload 的 Base64URL 只是编码，这也是“看不懂令牌内容”绝不能当作保密理由的原因。

**TLS**保护客户端与服务器之间一跳传输的机密性、完整性和服务器身份认证。浏览器通过证书链验证所连接域名的服务器身份，握手协商会话密钥，之后用对称加密传输数据。TLS 不是“给数据加密后永久安全”：请求到达负载均衡器后，内部链路、日志、数据库和备份仍需分别保护；也不证明业务请求有权限。生产环境应全站 HTTPS，正确配置证书和自动续期，关闭过时协议/弱套件，并在适用时使用 HSTS。不要为了调试跳过证书校验；那等于放弃服务器身份验证。

## 8.5 Secret 与配置：能运行不等于能安全运行

**配置**是随环境改变但通常不敏感的运行参数，如端口、功能开关、数据库地址、限流阈值；**Secret** 是一旦泄露即可带来访问能力或可解密能力的值，如数据库密码、私钥、OAuth client secret、云访问令牌。二者都可以通过环境变量或配置中心交付，但必须有不同的阅读权限、日志脱敏、变更审计和轮换计划。把 Secret 写进 Git、镜像层、前端包、示例配置或聊天记录，会使其复制到难以完全清除的地方。

较成熟的方式是让工作负载通过平台身份向 Secret 管理服务按需获取短期凭据，而不是把长期密钥注入每个容器。应用只读取它真正需要的 Secret；开发、测试、生产使用不同值和权限；密钥轮换要允许短暂的双版本验证，避免“一改就全站登录失效”。一旦发现泄露，先撤销或轮换该凭据、缩小影响，再清理仓库历史和调查访问记录；删除明文文件本身不等于 Secret 已失效。

## 8.6 不信任输入：校验、参数化、转义与出站控制

来自浏览器的 JSON、URL 参数、文件名、消息队列消息、管理员后台表单，甚至另一个内部服务的字段，都是不可信输入。**输入校验**检查数据是否满足业务允许的结构和范围，例如订单数量必须是 1 到 100 的整数、国家代码必须来自规定集合、上传文件大小和类型受限。优先用允许列表和强类型解析；不要用“删掉几个危险字符”的黑名单代替规则。校验能尽早发现无效请求，却不能单独阻止所有注入。

**SQL 注入**发生在程序把不可信数据拼成 SQL 语法。正确做法是参数化查询/预编译语句，让数据库把输入当作数据而不是指令。表名、排序字段这类不能参数化的位置，应从服务端固定允许列表映射，不能直接接收任意字符串。命令注入、LDAP 注入、NoSQL 注入同理：优先调用不经 shell 解析的 API，用结构化参数传值，并限制进程权限。

**输出转义**发生在数据进入特定解释器之前。例如把用户昵称插回 HTML 时，需要按 HTML 上下文转义；写入 JavaScript、URL、CSS 等不同语境也各有不同规则。它主要防御 XSS 等“把数据当代码执行”的问题。对于 shell，优先根本不经过 shell，使用带参数数组的进程 API；不要把手写的“shell 转义”当作通用防注入方案。校验、过滤、转义的职责不同：校验决定输入是否符合业务；过滤是在确有需求时删除/替换内容；转义让合法数据在目标语境中仍作为数据呈现。不能用 HTML 转义去修 SQL，也不能指望 SQL 参数化替代 HTML 转义。

**SSRF（服务端请求伪造）**指攻击者让服务器代替自己请求本不该访问的地址。常见场景是“输入一个 URL，服务器去抓图片或生成预览”。服务端所在网络往往能访问内部管理接口、云元数据服务和受限数据库，因此后果可能比浏览器直接请求更大。解决方案不是简单禁止字符串 `127.0.0.1`：URL 可经重定向、DNS 解析和不同地址表示绕过。更可靠的是仅允许明确的域名/协议/端口，解析并验证最终目标地址，禁止私有、回环、链路本地与保留地址，限制重定向、请求大小和超时，并让该抓取服务运行在最小网络权限的隔离区。业务若不需要任意 URL 功能，最安全的选择就是不提供它。

文件上传也属于输入。验证内容类型而不是只信扩展名，限制大小、数量和解压后的总量；将原始文件放在非可执行位置，使用随机服务端文件名，必要时进行恶意内容扫描和异步处理。不要把用户上传内容直接放入能被解释执行的路径。

**路径遍历**发生在服务端把用户给出的文件名或路径直接拼入本地路径，例如 `../../etc/passwd` 试图跳出预期目录。不要依靠删除 `..` 字符串；应让用户输入只作为逻辑文件 ID，在服务端映射到固定根目录下的随机文件名，并在规范化后确认目标仍位于允许根目录内。更好的方案是把文件放在对象存储并按对象 ID 访问。

## 8.7 浏览器边界：CORS 不是 CSRF，Cookie 不是万能令牌

**CSRF（跨站请求伪造）**利用浏览器会自动携带目标站 Cookie 的特性：用户已登录银行站点时，恶意站点诱导浏览器向银行发起转账请求，若服务端只看 Cookie 就可能把操作当作用户本人发起。防护应结合请求方法、SameSite Cookie、不可预测的 CSRF token、`Origin`/`Referer` 检查和敏感操作的重新认证。CSRF token 的核心是让攻击站无法读到或构造出与用户会话匹配的值；它不是给所有 API 随便加一个固定 Header。

**CORS（跨源资源共享）**是浏览器执行的同源策略例外机制：服务器用响应头告诉浏览器，哪些来源可以用脚本读取响应、可使用哪些方法和 Header。它解决的是“恶意页面能否读取另一个站点响应”的浏览器访问控制，不会替服务端做身份认证，也不会阻止 curl、移动端或攻击者直接调用 API。若使用带 Cookie 的跨域请求，不能把 `Access-Control-Allow-Origin` 设为 `*` 同时允许凭据；应维护精确可信的 origin 列表。CORS 配错可能泄露可读数据，但即使 CORS 严格，也不能替代 CSRF 防护和服务端授权。

前端把 bearer token 放在可被脚本读取的位置时，应重点防御 XSS；用 HttpOnly Cookie 则减小 token 被脚本直接窃取的面，却要正视 CSRF。这里没有绝对通用答案。无论选择哪种载体，后端都要用短期、范围受限的凭据；以安全模板和上下文转义预防 XSS，并用严格 CSP 等措施降低剩余风险；再对高风险操作设置额外确认。

## 8.8 可追责与可恢复：审计日志、依赖供应链和响应

普通**日志**帮助排障，记录请求耗时、错误堆栈和运行状态；**审计日志**服务于追责与合规，回答“谁在何时从哪里对哪个对象执行了什么动作，结果如何，依据什么权限”。两者可以写入同一平台，却不能混为一谈。审计事件应有稳定事件 ID、时间、主体类型与 ID、请求/关联 ID、资源类型与 ID、动作、结果、来源和必要的策略版本；敏感值如密码、完整令牌、身份证号和银行卡号绝不能写入。审计日志还需限制写入者、设置保留期、防止普通管理员无痕修改，并将关键操作与告警关联。

**软件供应链**包括直接与传递依赖、包仓库、构建脚本、CI 凭据、基础镜像和制品发布渠道。依赖漏洞只是其中一类风险；同名恶意包、被劫持的发布账号、被篡改的构建产物、过宽的 CI Token 都可能把未审查代码送进生产。工程上应提交并维护锁文件，固定可复现的版本，生成 SBOM，持续扫描漏洞与许可证，审查高风险升级，验证包/制品完整性和来源，并让 CI 使用短期、最小权限凭据。SBOM 用于盘点组件和响应漏洞通知，本身不证明制品安全或来源可信；来源证明、签名/校验和受控构建仍是另一层控制。不要在构建脚本中用 `latest` 拉取未知内容，也不要因为“包很流行”就跳过升级评估。

安全事件响应的目标不是立刻写一篇复盘，而是有序地**发现、分级、遏制、根除、恢复、复盘**。发现阶段需要告警和人工报告渠道；分级判断影响资产、范围和持续性；遏制可能是禁用账号、撤销令牌、隔离服务或临时关闭危险功能。根除修补根因并轮换受影响凭据；恢复时验证服务和监控正常；复盘把时间线、事实、决策和改进项写清。保留证据很重要：避免在未记录的情况下重启、覆盖日志或删除可疑资源。对外通知、监管报告和客户沟通应由预先约定的法务、合规和应急流程决定，而不是开发者临场猜测。

## 8.8.1 常见 Web 攻击的成因与控制位置

**注入**的共同根源是把不可信数据解释成代码或查询结构。SQL 参数化把值与 SQL 语法分开，因此 `WHERE email = $1` 能处理含引号的输入；它不能参数化表名、列名、排序方向等语法位置，后者必须用固定白名单选择。命令执行、LDAP、模板与 NoSQL 查询也有相同问题：不要通过字符串拼接构造解释器输入。输入校验能尽早拒绝不符合业务格式的数据，参数化/安全 API 则在解释边界阻断语法逃逸；两者应同时存在。

**XSS**发生在攻击者控制的数据被浏览器作为 HTML、属性、URL 或 JavaScript 执行。输出编码必须匹配具体上下文：HTML 文本、属性值、URL 参数和脚本字符串的规则不同；把数据库中“已经过滤过”的富文本直接注入 DOM 仍不安全。默认自动转义的模板、经过严格审计的富文本清理器以及内容安全策略（CSP）可以降低风险，但 CSP 不是替代正确编码的许可。XSS 一旦成功，可借用户浏览器发起同源请求、读取页面数据或诱导操作；`HttpOnly` Cookie 能防止脚本直接读 Cookie，却不能阻止脚本以该 Cookie 身份发请求。

**CSRF**利用的是浏览器会自动携带 Cookie：攻击站点诱导已登录用户访问一个写入 URL，服务器若只凭 Cookie 判断身份就可能接受。SameSite Cookie、对有副作用请求校验不可猜的 CSRF token、核对 Origin/Referer，以及不要用 GET 做写入共同降低风险。Bearer token 放在 Authorization Header 时通常不会被浏览器跨站自动附带，CSRF 形态不同，但 XSS 与令牌泄露风险仍在。**CORS**只决定浏览器是否允许脚本读取跨源响应，不会阻止攻击者发出请求，不能代替其中任一控制。

**SSRF**让服务端替攻击者请求一个 URL，风险在于服务端可能能访问浏览器无法访问的内网、云元数据或管理接口。不能只检查 URL 字符串是否“看起来像域名”：应采用目的地 allowlist，限制协议、端口、重定向、DNS 解析后的地址范围与响应大小/时间，并在网络层阻止应用到敏感地址段的出站访问。因为 DNS 可能在校验后改变、IPv4/IPv6 表示形式很多，严肃场景应在受限网络代理中执行抓取，而不是让业务进程直接访问用户提供的地址。

## 8.9 高频辨析：把相近概念放回各自的问题

1. **认证与授权**：认证回答“你是谁”；授权回答“你能否对这个资源做这个动作”。登录成功后仍可能被拒绝访问某文档。认证是授权的常见前提，但服务也可以对匿名主体作“只允许读公开资源”的授权判断。

2. **Cookie、Session 与 JWT**：Cookie 是浏览器存取和自动发送数据的载体；Session 是服务端保存状态的机制；JWT 是带声明和签名的令牌格式。Cookie 可装 session id，也可装 JWT；JWT 并不等于登录态，也不天然比 Session 更安全。

3. **JWT 的签名与加密**：常见的三段紧凑 JWT 是 JWS：签名保证来源和完整性，不隐藏 payload；JWE 是加密形式，通常以五段紧凑序列化出现，提供机密性且实现和密钥管理更复杂。看到三个点分隔的 JWT 不能假设内容保密。

4. **哈希、加密与编码**：哈希可用于摘要比对；若攻击者能同时改动数据和摘要，要证明完整性与来源还需 HMAC 或数字签名。加密用于日后恢复明文；编码用于传输/表示兼容。Base64 不是加密，SHA-256 不是密码存储方案，密码哈希也不能用来加密身份证号。

5. **401 与 403**：401 表示缺少或无效的认证凭据，客户端可按协议重新认证；403 表示服务器理解请求但拒绝执行，常因权限不足。为避免泄露资源存在性，某些对象级拒绝可按产品策略返回 404；关键是服务端已做了正确授权，而不是执着于某个状态码。

6. **CORS 与 CSRF**：CORS 管浏览器脚本是否能跨源读取响应；CSRF 防止浏览器借已登录 Cookie 跨站提交有副作用请求。CORS 不会阻止攻击者发请求，CSRF token 也不授予跨域读权限。

7. **校验、过滤与转义**：校验按业务规则接受或拒绝输入；过滤删除不希望出现的内容；转义按输出上下文把数据安全地显示出来。用户评论可通过长度校验，但在 HTML 页面输出前仍需转义。

8. **RBAC 与 ABAC**：RBAC 根据稳定岗位授予权限，易审计；ABAC 根据主体、资源和环境属性判定，表达力更强也更难治理。常见组合是角色提供基础权限，属性限制租户、所有者和状态。

9. **Secret 与配置**：两者都影响运行，但 Secret 泄露会直接增加访问或解密能力，必须最小化暴露、审计和轮换；普通配置也要受控，却通常不需要按密钥级别保护。数据库主机名通常是配置（某些隔离环境中也可能属于敏感基础设施信息），数据库密码则是 Secret。

10. **日志与审计日志**：日志侧重可观测性与排障，允许较高频和技术细节；审计日志侧重责任归属与证据完整性，必须描述主体、动作、资源、结果并避免记录敏感值。把 access token 写进 debug 日志，会同时破坏两者。

## 8.10 练习

1. 某团队把 `GET /api/invoices/{id}` 设为“必须登录”，却没有检查发票所属组织。攻击者猜到另一个组织的 id 后能读取发票。这里认证、授权和对象级权限分别出了什么问题？应把检查放在哪里？

2. 一个单页应用把长效 JWT 存入 `localStorage`，并声称“因为 JWT 有签名，所以 XSS 无法偷走它”。这句话错在哪里？请给出两项优先改进，并说明改用 HttpOnly Cookie 后新增的主要风险。

3. 图片预览服务接受任意 URL，下载后保存到对象存储。设计一组控制，既不把它写成“禁止所有 URL”，也不允许它访问内部管理网段。

4. 为何“把数据库密码 Base64 后提交到仓库”不是保护？若该密码已经泄露到公开仓库，正确的处置顺序是什么？

5. 设计一条“管理员导出用户数据”的审计事件。至少写出八个字段，并指出两类不应记录的内容。

## 8.11 参考答案

1. 登录态验证只完成了认证：请求确实代表某个用户；缺失的是“该用户是否能读这张发票”的授权。对象级权限漏洞来自按 id 直接查询并返回。应在服务端的数据访问/策略层把 `invoice_id` 与主体所属 `tenant_id`、角色或明确授权关系一起作为查询条件；前端隐藏链接没有安全意义。批量导出和下载链接也要复用同一策略。

2. 签名只能防止令牌被篡改，不能阻止注入到页面中的恶意脚本读取 `localStorage` 后外传令牌。优先改进是缩短访问令牌寿命并建立刷新/撤销机制，以及以安全模板和上下文转义预防 XSS、用严格 CSP 等措施降低剩余风险。使用 HttpOnly Cookie 可降低脚本直接读取令牌的风险，但 Cookie 会自动随请求发送，因此必须同时做 CSRF 防护，并配置 `Secure`、`SameSite` 等属性。

3. 将抓取功能独立为低权限服务；只接受 `https` 和明确允许的域名；解析 DNS 后拒绝回环、私有、链路本地和保留地址，并在连接时验证最终地址；限制重定向次数、响应大小、类型与超时；网络策略禁止该服务访问管理面和云元数据地址。记录被拒绝原因时不要回显内部网络细节。

4. Base64 是编码，任何人都可还原；公开仓库历史、镜像和克隆都可能保存该值。先在密钥管理系统撤销或轮换密码，检查该账号权限与访问日志并临时收紧范围；随后清理代码和历史中的明文、补充扫描规则与访问控制。仅删除仓库文件不能阻止已获得旧密码的人继续使用它。

5. 可记录：事件 ID、UTC 时间、操作者主体 ID/类型、认证强度、动作 `user_data_export`、资源范围、审批单或业务理由、策略版本、结果、请求关联 ID、来源 IP 的最小必要表示、导出文件标识与过期时间。不能记录明文密码、完整访问令牌；通常也不应把被导出的完整个人数据复制进审计日志。审计存储需限制写入和读取，并对失败或异常大量导出告警。
