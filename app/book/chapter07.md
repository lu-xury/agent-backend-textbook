一个后端接口收到请求后，并不总该把所有工作做完再返回。创建订单后发邮件、生成账单、转码视频、给搜索索引写入新文档、调用大模型整理长文本，这些工作有的耗时长，有的依赖不稳定的外部系统，有的可以晚几秒完成。若它们全放进请求处理函数，用户会被迫等待，Web 服务器的连接和线程也会被占住；其中一步超时，还会让已经完成的主业务看上去失败。**异步系统**的作用是把“现在必须得到结果的工作”与“可以稍后可靠完成的工作”分开，并把失败、重试、积压和取消变成可以设计、观测和恢复的对象。

异步不是“把函数丢到后台就万事大吉”。一旦工作跨越进程、机器或服务边界，就会出现一个基本事实：发送者、消息中间件和处理者不可能在同一时刻知道彼此是否成功。网络可能在消息写入后、响应返回前断开；消费者可能在调用支付服务成功后、确认消息前崩溃。可靠的异步设计不是假装这些情况不会发生，而是规定每一种不确定状态怎样继续推进，以及重复执行时业务如何保持正确。

本章用“订单支付成功后发送收据并更新积分”为贯穿例子。支付接口必须尽快告诉用户付款是否接受；邮件、积分、分析等后续动作可以交给异步任务。请把队列看成一种**交付协议和流量调节器**，而不只是一个装着 JSON 的容器。

## 7.1 同步调用与异步任务

**同步调用**指调用方在当前控制流中等待被调用方完成，再获得结果或错误。例如 HTTP 请求调用数据库并等到 `COMMIT`，这是同步的；函数在同一线程还是另一线程执行并不改变这一点。同步适合结果是本次业务决策前提的场景：登录时必须验证密码，扣减库存前必须知道库存是否足够，支付结果未确定前不能把订单标为已支付。同步调用的优点是因果关系直接、错误容易返回给用户；代价是端到端延迟由最慢的下游决定，而且调用链越长，失败面越大。

**异步任务**指提交者先记录“这件事应当做”，不等待实际处理结束；工作者在之后取走任务并执行。接口可以返回 `202 Accepted` 和一个任务或订单标识，客户端再查询状态，或由服务端推送结果。异步适合耗时、可批量、可延后、可重试，或不影响主交易是否成立的动作。例如“把商品图片转成三种尺寸”不应占住上传请求；“发送欢迎邮件”失败不应回滚用户注册。反过来，如果用户点击“提现”后系统只把扣款任务塞进队列便立即显示“成功”，却没有定义资金冻结与最终状态，异步只是把错误藏到了以后。

同步和异步经常组合使用。支付服务可在一个短同步事务中写入 `payment=paid` 与一条 `ReceiptRequested` 事件；事务提交后，工作者发送收据。这里“订单已支付”是同步确定的业务事实，“收据已发出”是异步进度。接口不必承诺邮件已到达邮箱，只需准确表达它承诺了什么。

### 高频辨析：同步/异步与阻塞/非阻塞

**同步/异步**描述结果何时交给调用方；**阻塞/非阻塞**描述当前线程在等待时能否继续做别的工作。四种组合都存在。传统数据库查询通常是同步且阻塞的：线程等结果。基于 `await` 的 HTTP 调用通常是**异步 I/O**：调用先取得 future/promise，`await` 使当前协程暂停，运行时可调度其他协程，OS 线程不必被占住。若上层业务在响应返回前不能继续做判断，它仍然在**等待结果**；这与 I/O 是否阻塞线程是两回事。提交到队列后立刻返回是异步的；若生产者因为队列已满而等待可用空间，它又可能在提交这一步阻塞。面试中说“异步就是非阻塞”是不完整的：异步流程的某个环节仍可能阻塞，非阻塞 I/O 也不表示业务已经异步完成。

### 高频辨析：任务与线程

**任务（task/job）**是待完成的业务工作，例如“为订单 9812 发送收据”；它应有稳定标识、输入、状态、尝试次数、截止时间和可观察结果。**线程**是操作系统调度 CPU 的执行单元。一个任务可以由任意一台机器上的任意线程执行；一个线程也会顺序处理许多任务。把任务等同于线程会导致错误的恢复方式：进程重启后线程不存在，但任务若已持久化仍应可取回。进程内线程池适合短小、无需跨进程恢复的并发工作；涉及邮件、支付、文件和跨服务动作时，应使用持久任务存储或消息系统。

## 7.2 队列、生产者、消费者与消息边界

**消息队列**把生产者和消费者解耦。生产者把一条消息发布到某个目的地后，不必知道由哪台机器、何时处理；消费者按自己的速度取消息。队列通常负责暂存、路由、可见性或确认、保留策略等能力。生产者负责构造可理解且可演进的消息，消费者负责按约定处理并在成功后确认。中间件并不会替业务判断“邮件是否真的送达”或“积分是否重复增加”。

消息体应表达稳定的业务事实或命令，而不是把某个进程的内存对象序列化后原样传递。一个命令可写为：

```json
{
  "message_id": "01J...",
  "type": "SendReceipt",
  "version": 1,
  "requested_at": "2026-08-05T06:30:00Z",
  "payload": {"order_id": "9812", "recipient": "a@example.com"}
}
```

这里 `SendReceipt` 是命令，要求消费者完成一件事；`PaymentSucceeded` 这类过去式名称才是陈述既成事实的事件。`message_id` 用于追踪和对同一消息去重，`type` 与 `version` 让消费者能按契约解析，业务数据放在 `payload`。若同一业务动作可能产生多条消息，还要定义稳定的业务幂等键，例如 `idempotency_key` 或 `(event_type, aggregate_id, version)`。不要把密码、完整银行卡号或不必要的个人数据塞进消息；它们可能被保留、备份和被多个消费者读取。对于会频繁改变的大对象，消息放对象 ID 或版本，消费者再按权限读取；但要注意读取时对象可能已变化，必要时传递不可变快照或明确“按当前状态处理”。

生产者真正面对的是“消息是否被可靠接收”。写入调用返回成功以前，进程可能崩溃；返回失败也不必然说明服务端没有收到，因为响应可能丢失。因此生产者要设置合理超时和有限重试，并知道中间件提供的发布确认语义。RabbitMQ 的 publisher confirm 与消费者 ack 分别解决发布侧和消费侧的确认，不能互相替代；Kafka 生产者可通过确认级别、幂等生产和事务配置收紧写入语义。[RabbitMQ 的确认说明](https://www.rabbitmq.com/docs/confirms) 与 [Kafka 的设计文档](https://kafka.apache.org/documentation/#design) 都强调：确认只是某一段链路的证据，不是端到端业务成功的证明。

消费者的基本循环是：收到消息；校验格式和版本；执行可重试的业务动作；把处理结果持久化；最后确认。确认得过早会丢任务：消息刚收到便 ack，进程随后崩溃，系统误以为已处理。确认得过晚会多次执行：实际动作完成后，消费者在 ack 前崩溃，消息稍后重新投递。后者通常比前者安全，因为重复可以由幂等设计消除；这也是很多系统倾向“至少一次”而不是“至多一次”的原因。

### 高频辨析：队列与事件流

日常语言中的“队列”在一个工作队列/消费者组的语义下，往往指一个任务只交给一个工作者，处理成功后就从队列消失；典型用途是发邮件、生成报表、执行 webhook。一个 broker 也可以通过 fanout 或多队列绑定让同一发布被多个订阅者收到，因此关键是路由和消费协议，而非产品名称。**事件流（event log/stream）**更像按追加顺序保存的事实日志，多个消费者组可以各自从自己的位置读取，同一事件可被分析、搜索、计费等多个下游独立消费。Kafka 的 topic 被分为多个有序分区，消费者组对每个分区记录自己的 offset；同一分区在一个消费者组中同一时刻由一个消费者处理。[Kafka 官方介绍](https://kafka.apache.org/documentation/)中称生产者发布 event，消费者订阅和读取 event，正适合这种可回放模型。

二者不是绝对对立。RabbitMQ 也有 Streams，Kafka 也能做工作分发；区别在于你需要的语义。若只想让某一个 worker 执行一次导出任务，工作队列的竞争消费很自然；若新建一个“反欺诈”服务后希望从过去订单事件重新计算，保留可回放的事件流更合适。不要把 Kafka 当作一张可随意更新查询的数据库，也不要把短保留的任务队列当作永久审计日志。

## 7.3 有界队列、背压与限流

队列能吸收短暂尖峰，却不能创造处理能力。设生产速率为 \(\lambda\)，消费者总处理速率为 \(\mu\)。当 \(\lambda > \mu\) 且持续足够久，积压会不断增长，等待时间也会增长；最终磁盘、内存、配额或消息保留时间会成为硬边界。即使平均 \(\lambda < \mu\)，在接近满载时排队等待也会急剧恶化。因而**队列必须有容量、过期和告警策略**；“无限队列”通常只是把 OOM 或磁盘写满推迟到更难恢复的时候。

**背压（backpressure）**是下游处理不过来时，限制上游继续输入或向上游反馈“慢下来”的机制。最简单的形式是有界队列满时拒绝、等待或降级提交；在消息系统中也可限制未确认投递数。降低拉取批量、扩容消费者属于本地并发控制或容量调整，常与背压配合使用，但不等同于背压本身。RabbitMQ 的 manual acknowledgement 加 prefetch 可以按所用客户端和配置限制一个 consumer 或 channel 上尚未确认的投递数量，避免自动确认模式把消费者内存压垮；其队列文档明确指出，自动确认可能使处理速度跟不上的消费者持续增加内存使用。[相关说明](https://www.rabbitmq.com/docs/queues)值得作为配置 prefetch 的出发点。

背压必须配合产品策略。图片缩略图可以延迟，系统显示“处理中”；营销通知可以合并或丢弃过期消息；支付结算不能随便丢，应拒绝新请求、排队并明确预计时间，或将资金状态留在“待处理”。队列深度本身不是唯一指标：还要看最老消息年龄、入队/出队速率、处理时延分位数、失败率、重试量和下游资源利用率。队列深度为零也可能是消费者全部崩溃后生产者被拒绝；深度很大也可能是主动批量处理的正常状态，必须结合趋势解释。

### 高频辨析：背压与限流

**背压**关心接收方的实时承受能力，信号通常沿调用链或队列边界向上游传播；**限流（rate limiting）**按预先设定的额度限制某个主体在一段时间内的请求数或字节数，例如每个用户每分钟 100 次 API 调用。限流主要防滥用和保护公平，背压主要防系统在当前负载下失稳。两者可同时使用：API 网关对用户限流，任务队列按最大并发数调度，消费者再以 prefetch 控制在手任务。Google Cloud Tasks 将队列的最大分发速率和最大并发数作为独立配置，且重试同样受这些上限约束，[官方文档](https://docs.cloud.google.com/tasks/docs/configuring-queues)正体现了“重试也会占用能力”。

## 7.4 投递语义：不要把“恰好一次”当作魔法

投递语义描述某段通信链路在故障时可能给处理者多少次机会，并不直接等同于业务效果。

- **至多一次（at-most-once）**：消息可能丢失，但不会因重投而重复。它常来自自动确认、先提交 offset 或不重试。适合允许偶尔缺失的指标、实时预览等；不适合扣款、履约和关键通知。
- **至少一次（at-least-once）**：系统会在没有成功确认时重投，因此消息可能重复。它要求消费者能处理重复，换来较低的静默丢失风险。大多数业务任务应以此为默认假设。
- **恰好一次（exactly-once）**：在定义好的边界内，某记录的处理效果看起来只发生一次。必须问清边界：是 producer 写入一个 topic 一次，还是 Kafka 读—处理—写回 Kafka 一次，还是“扣款、写数据库、发邮件”这三个外部效果都一次？后一个问题没有一个队列开关可以单独解决。

Kafka 的幂等 producer 可以避免生产者重试在日志中写入重复记录；启用 transactional id 后可将对多个分区的写入纳入 Kafka 事务。Kafka Streams 的 exactly-once 语义也限定为输入位置（offset）、状态存储更新和输出 topic 写入都处在 Kafka 事务边界内。[Kafka 当前设计文档](https://kafka.apache.org/43/design/design/)与 [Streams 说明](https://kafka.apache.org/43/streams/core-concepts/)都把边界说得很明确。消费者若随后向独立 PostgreSQL 写入、调用第三方短信服务，仍可能在“外部操作成功”和“提交 offset”之间崩溃，重复不可避免。

因此面试中更成熟的回答是：我选择至少一次投递，消费者用业务幂等键消除重复；若链路完全在支持事务的流系统边界内，可以使用其 exactly-once processing；跨数据库与外部副作用时，把“恰好一次效果”拆成唯一约束、状态机、Outbox、可查询结果和可补偿动作，而不宣称分布式魔法。**恰好一次通常是组合出来的业务性质，不是 broker 替你完成的承诺。**

### 高频辨析：至少一次/恰好一次

至少一次是“未得到确认就会再送”的传输策略，允许重复；恰好一次是一个更强的、必须说明范围的可观察结果。即使 broker 的某个 topic 中没有重复记录，消费者代码仍可能执行两次。反过来，消息被投递两次，只要积分表对同一业务事件只接受一次写入，用户看到的积分效果可以恰好一次。讨论时先问“谁看见什么效果”，再谈 Kafka、RabbitMQ 或数据库的配置。

## 7.5 确认、重试、死信与消费者幂等

失败不是同一种东西。网络超时、数据库短暂不可用、下游返回 429，通常是**瞬态失败**，可以隔一段时间再试；消息字段缺失、版本不兼容、订单不存在、权限不允许，通常是**永久失败**，原样重试不会变好。分类还要结合业务语义、消息年龄和依赖状态：订单暂时不存在可能是乱序事件，稍后可重试；数据库唯一约束冲突也可能只是重复，应幂等确认而非送入死信。业务处理器应把错误分类，并记录 message id、任务 id、尝试次数、下游错误码和相关订单号。不要用裸 `except: retry()` 把程序 bug、空指针和数据损坏都伪装成“网络抖动”。

重试要有限次，并使用退避和抖动。若一万条消息都因同一个数据库故障立刻重试，会形成重试风暴，使刚恢复的服务再次被打垮。指数退避可令等待大致按 1 秒、2 秒、4 秒、8 秒增长；加入随机抖动可避免所有 worker 同时醒来。还应设置总截止时间：一项“今日 9 点提醒”的任务在三天后成功执行也许比失败更糟。Cloud Tasks 也会对错误退避，并在 429、503 或高错误率时提高退避程度，[其常见问题文档](https://docs.cloud.google.com/tasks/docs/common-pitfalls)说明了这一点。

达到重试上限或发现永久失败时，消息应进入**死信队列（DLQ, dead-letter queue）**，而不是无限循环。DLQ 是隔离和诊断区，保存原消息、失败原因、尝试历史与原始路由；它不是垃圾桶。团队要有查看告警、修复原因、决定丢弃/修改/重新投递的流程。在 RabbitMQ 中，broker 通过 **dead-letter exchange（DLX）** 把死信路由到某个目标队列；消息被拒绝且不重新入队、TTL 到期、队列超限等情形都可触发死信。[DLX 文档](https://www.rabbitmq.com/docs/dlx)也提醒这是一段新的投递链路，目标不可用时仍需考虑可靠性。修复了消费者版本后，回放 DLQ 前应先确认幂等键仍有效，不能用“重放”把历史款项再次扣除。

**幂等消费者**意味着同一业务请求或消息被处理多次，最终可观察状态与处理一次相同。它不是“代码没有副作用”，而是副作用有唯一身份。给积分时，不要写“每收到消息就 `balance += 10`”；可建立 `point_ledger(event_id UNIQUE, user_id, delta)`，在一个数据库事务内插入流水并更新余额。若相同 `event_id` 再来一次，唯一约束冲突，读取既有结果后确认消息即可：

```sql
BEGIN;
WITH inserted AS (
  INSERT INTO point_ledger(event_id, user_id, delta)
  VALUES ($1, $2, 10)
  ON CONFLICT (event_id) DO NOTHING
  RETURNING user_id, delta
)
UPDATE account_point AS p
SET balance = p.balance + i.delta
FROM inserted AS i
WHERE p.user_id = i.user_id;
COMMIT;
```

这里 `INSERT` 因重复事件没有返回行时，随后的 `UPDATE` 也不会执行；实际系统还应检查账户行确实存在，并为异常路径保留审计信息。关键不是 SQL 技巧，而是**去重记录和业务状态必须在同一原子存储边界内**。把已处理 id 先写 Redis、再写数据库，两个步骤之间崩溃仍会产生漏洞；Redis 也许适合短期去重加速，但不是替代长期业务唯一性的凭据。

### 高频辨析：重试/幂等

**重试**是遇到不确定或暂时失败时再执行一次的控制策略；**幂等**是重复执行后不会把业务效果叠加的性质。重试不能制造幂等，幂等也不代表应该无限重试。HTTP `PUT /orders/9812/status` 设置为 `paid` 可以天然接近幂等，但请求带来的“发一封邮件”未必幂等；用 `Idempotency-Key`、唯一业务键、去重流水或 provider 的幂等键才能把它变成可重试操作。一个优秀回答会说明：先让副作用可去重，再对可恢复错误做有上限的重试，永久错误进入人工或自动补偿流程。

### 高频辨析：ack、重试与 DLQ

**ack** 是消费者向 broker 说明“这一投递已完成，可以不再交给我”的确认；它不等于下游用户已经看见邮件。**重试** 是对暂时失败的再次尝试，可能由应用的延迟调度、broker 重投或新的 retry topic 实现；重试时不能 ack 原消息后丢失任务，也不能立即 requeue 形成热循环。**DLQ** 是超过重试预算或确认永久失败后进入的隔离目的地，目的是诊断和处置，不是“再试一次”。先分类错误，再决定延迟重试、DLQ 或成功 ack；无论哪条路径，消费者都要能按业务键去重。

## 7.6 顺序、分区与并行度

“消息有序”必须说明范围。单个消费者顺序处理一个普通队列时，开始顺序可能接近入队顺序，但失败重投、多个消费者、优先级、网络和 broker 实现都会改变观察到的完成顺序。Kafka 的强语义是**单个分区内的追加顺序**，不是整个 topic 的全局总顺序；官方设计文档指出 topic 由一组全序 partition 构成，每个分区在一个消费者组中同一时刻由一个消费者消费。[Kafka 当前设计文档](https://kafka.apache.org/43/design/design/)正是理解并发消费的基础。

分区键决定“哪些记录必须在一起”。订单状态变化 `Created → Paid → Shipped → Cancelled` 应按 `order_id` 分区，使同一订单事件进入同一分区，消费者可顺序处理；按随机 UUID 分区会提高均匀性，却可能让 `Shipped` 先于 `Paid` 到达不同 worker。另一方面，把所有事件放入一个分区虽容易得到全局顺序，却把整个 topic 的最大并行度降为一个消费者。分区的工程选择是：为需要顺序的实体选择稳定键；接受不同实体之间没有全局顺序；处理键分布倾斜和热点用户。

即使同一分区有序，**处理完成顺序**也未必有序。消费者取到 A 后并发提交到线程池，A 的慢外部调用可能让 B 先完成；若要保持状态机顺序，需在该键内串行处理，或用每个键的序列号与期望版本拒绝过期更新。事件还可能乱序抵达：生产者时钟不同、多个来源写同一实体、重试延后，都会让“发生时间”不等于“到达时间”。在可以容忍短暂延迟的分析场景，可设 watermarks 或重排窗口；在订单状态场景，通常更可靠的是数据库状态机只允许合法迁移，例如已取消的订单不能被旧的 `Paid` 事件改回已支付。

### 高频辨析：顺序/全局顺序

**顺序**不是单一开关，至少要问“同一订单内吗、同一分区内吗、还是所有用户之间吗”“指接收、开始处理还是完成副作用的顺序”。全局顺序意味着所有消息竞争同一条串行路径，吞吐和可用性代价高，绝大多数业务并不需要。支付同一订单的事件需要按订单顺序；北京用户和上海用户的独立订单谁先处理通常没有业务意义。以实体键换取局部顺序，是吞吐与正确性之间常见且合理的边界。

## 7.7 延迟任务、定时任务与工作流

**延迟任务**是“在某个未来时刻之后执行一次”的任务，例如下单 30 分钟未支付则关闭订单；**定时任务**按日历或间隔反复触发，例如每天 02:00 汇总昨日账单。二者都涉及时间，但语义不同。延迟任务应保存 UTC 的绝对 `run_at` 和业务条件；消费者真正执行前再次检查订单仍为待支付，防止用户刚付款却被旧任务关闭。定时任务还要保存业务时区与日历规则，并明确夏令时和漏跑补偿：`0 2 * * *` 在有夏令时地区可能出现某天 02:00 不存在或出现两次。服务部署在多台机器上时，不能让每台机器各跑一遍 cron；应使用单一调度器、带租约的 leader，或用数据库唯一键保证一个周期只有一个任务实例。

不要用“sleep 30 分钟”实现延迟任务。进程重启会丢失内存计时器，长时间 sleep 占用 worker，时钟调整也会使行为难以解释。可用具备 `schedule_time` 的托管任务服务，或把 `run_at` 持久化后由调度器扫描并投递；Google Cloud Tasks 支持为 HTTP task 指定未来 `scheduleTime`，也可用显式任务名协助去重，[官方创建指南](https://docs.cloud.google.com/tasks/docs/creating-http-target-tasks)说明了这些边界。RabbitMQ 的 TTL 加死信路由可以做有限的延时模式，但 TTL 到期和死信时机受队列类型及消息在队头的位置影响；精度、重启和大量不同延迟都应按具体版本验证，不宜把它当通用调度数据库。[TTL 官方文档](https://www.rabbitmq.com/docs/ttl)可用于核对所选队列类型的行为。

长流程不能只靠“收到一个任务就从头跑到尾”。例如退款工作流可能经历 `requested → validating → refunding → refunded` 或 `failed/cancelled`。**工作流状态**应存到持久化状态机中，记录当前步骤、输入版本、外部操作的幂等键、下一次唤醒时间和失败原因；worker 每次只推进一个可恢复步骤。取消也不是杀掉线程那么简单：若已提交给支付机构，能否撤销取决于其接口；本地要把状态从 `cancelling` 推进到 `cancelled` 或 `completed`，并阻止尚未开始的下游步骤。对于不可逆动作，应有补偿而不是承诺回滚，例如已经寄出的商品要走退货流程。

### 高频辨析：定时任务/延迟队列

定时任务描述**重复的计划**，通常由 cron 表达式或日历触发；延迟队列描述**一条具体消息何时才可被消费**。每天发一份日报是定时任务；订单 9812 在 30 分钟后自动取消是延迟任务。把前者实现为每天塞一百万条延迟消息会增加管理成本；把后者放进每分钟扫描全订单表的 cron，又会带来扫描压力和时间精度问题。两者都必须有持久状态和幂等处理，因为“调度器是否已经触发”同样会处于不确定状态。

## 7.8 Outbox：数据库提交与消息投递之间的缝隙

设想支付接口做两件事：更新 `payment.status='paid'`，然后向 broker 发布 `PaymentSucceeded`。如果先更新数据库后发消息，进程可能在两者之间崩溃：订单已支付，但收据任务永远没创建。若先发消息后更新数据库，消费者可能看到支付成功事件，却发现数据库仍是待支付，或数据库更新最终回滚。把两个独立系统包进同一个普通事务通常做不到；即使使用分布式两阶段提交，也会提高可用性和运维复杂度，外部邮件与支付 API 更不可能参加。

**Transactional Outbox** 的做法是：在同一个本地数据库事务内，既更新业务数据，也向 `outbox` 表插入待发布事件。事务成功则两者都存在，失败则两者都不存在。独立 relay 按批读取尚未发布的 outbox 行，发布到消息系统，得到发布确认后标记为已发布。relay 在“已发布、未标记”之间崩溃会再次发布，所以消费者仍须幂等。这样消除了“本地业务已提交、但进程在写入待发布意图前崩溃”的窗口；只要 relay 能持续扫描并成功发布，事件最终会离开 outbox。它并不免除 relay、broker、清理策略和监控的可靠性责任。

```sql
BEGIN;
WITH paid AS (
  UPDATE payment
  SET status = 'paid', paid_at = now()
  WHERE id = $1 AND status = 'pending'
  RETURNING id, paid_at
)
INSERT INTO outbox(id, topic, aggregate_id, payload, created_at)
SELECT
  $2,
  'payment.succeeded',
  id,
  jsonb_build_object('payment_id', id, 'paid_at', paid_at),
  now()
FROM paid;
COMMIT;
```

`INSERT` 影响零行表示支付不存在或已不是 `pending`；接口应查询既有支付状态或返回相应业务结果，不能把它当作“又支付成功”。`outbox` 还需要由业务事件唯一键约束，例如 `UNIQUE(topic, aggregate_id, event_type, event_version)`，避免同一状态迁移生成两条事件。真实表还应有事件类型、schema version、分区键、发布状态、锁定者和保留策略。relay 可用 `SELECT ... FOR UPDATE SKIP LOCKED` 让多个实例安全领取批次，或使用数据库变更捕获（CDC）把提交日志转成事件；这只解决领取竞争，事务结束前不应长期持锁，领取后还应通过租约或可恢复的 `locked_at` 状态处理 worker 崩溃。无论轮询还是 CDC，事件 id 都应稳定；发布完成标记只是优化，不是消费者去重的替代。不要在数据库事务里直接等待 broker 或邮件服务响应：那会延长事务、占用连接，并无法保证远端动作与回滚真正原子。

Outbox 带来的是**以可靠 relay 为前提的最终一致性**：主数据库提交后，读模型、搜索索引、积分或邮件会在稍后追上；若积压、DLQ 或 relay 故障使它们没有追上，系统应能发现并修复，而不是假定它会自动完成。系统需要让这种短暂不一致可见且可接受，例如订单页显示“收据发送中”，管理后台可按事件 id 查询投递状态；不能要求用户刷新十次来猜。对真正必须同步维持的不变量，如余额不能低于零，应放在同一数据库事务或受同一强一致协调机制保护，而不是寄希望于队列最终补救。

## 7.9 设计与排障清单

设计一个任务前，先写出它的业务身份和完成定义：谁创建、输入是否包含版本、成功的外部效果是什么、允许多迟完成、允许重试几次、取消后应留下什么状态。然后选择同步或异步边界：若响应不能在没有结果时返回，就不要勉强异步；若工作可恢复且不影响主操作成功，就不要把慢下游绑在请求链上。为每个消息定义 id、类型、版本、分区键和敏感数据规则；为每个消费者定义确认时点、幂等键、异常分类、退避、DLQ 去向和监控指标。

出现积压时，先问“生产是否突然变快，还是消费变慢了”：查看入队与出队速率、最老消息年龄、分区热点、下游数据库延迟、重试量和每个 worker 未确认消息数；不要第一反应就把消费者数翻十倍。

出现重复时，沿着“生产者重试—broker 重投—消费者超时—外部 API 超时—offset/ack 提交”逐段寻找不确定窗口，不要只用日志时间排序推断因果。

出现丢消息报告时，先定位是哪一段缺证据：生产者是否收到 broker 确认、broker 是否持久化、消费者是否过早 ack、是否因 TTL/最大长度/DLQ 路由而过期或丢弃。异步系统的质量，来自对这些边界的明确选择和持续观测。

## 本章练习

1. 用户注册接口同步写入用户表后，要发送欢迎邮件和建立搜索索引。哪些动作应在事务内，哪些动作适合异步？若接口超时，客户端怎样知道注册是否成功？

2. 积分消费者收到 `OrderPaid(order_id=9812)` 后先调用第三方积分 API，第三方返回 200；消费者在提交 ack 前崩溃。消息重投后怎样避免重复积分？请说明仅靠“Kafka 恰好一次”为什么不充分。

3. 一个 RabbitMQ 队列堆积 200 万条缩略图任务。团队计划把 prefetch 从 20 改为 50,000，并把重试间隔改成 0。指出至少三种风险，并给出优先排查的指标。

4. 订单事件按随机 key 发送到 32 个 Kafka 分区，偶尔出现订单先显示“已发货”后又变为“已支付”。如何修改分区和消费者状态更新？为什么不建议把全部事件改到一个分区？

5. “每天凌晨清理过期会话”与“某个会话在 30 分钟后失效”分别应怎样建模？列出时区、多实例和重试三个方面至少各一个注意点。

6. 支付服务先更新数据库、再发送消息，偶发“订单已支付但没有收据”。用 Outbox 重写步骤，并指出 Outbox 仍然会产生什么重复问题。

## 练习参考答案

1. 用户行及其唯一邮箱、注册幂等键等必须在一个短数据库事务内提交；欢迎邮件和搜索索引属于可恢复的后续效果，可由 Outbox 事件异步触发。接口超时不代表事务未提交，客户端应携带注册幂等键并通过同一键查询首次处理结果，不能盲目再次创建用户。若产品承诺“注册成功即收到邮件”，应重新评估承诺，因为邮件供应商并不在本地事务中。

2. 给每次 `OrderPaid` 一个稳定事件 id（可由订单支付记录导出），在本地积分流水或第三方 API 的幂等键中使用它。重投后先发现流水已存在，或第三方按同一键返回既有结果，再安全确认。Kafka 的事务可覆盖特定的读—写 Kafka 链路，不能使第三方 HTTP 调用和 ack/offset 成为一个原子动作；网络在 API 成功响应途中断开时，客户端仍无法知道远端是否已经加分。验收时应重复投递同一事件两次，确认积分流水仍只有一行、余额只增加 10。

3. 巨大 prefetch 会把未确认消息大量压到少数消费者内存，某 worker 崩溃时又造成大批重投；零间隔重试会对故障下游形成重试风暴，并让永久坏消息占满吞吐；盲目扩容还可能把数据库或对象存储推过容量。先看入队与完成速率、最老消息年龄、每类错误比例、重试次数、消费者未确认数、下游延迟与资源利用率，再决定是否限流、修复慢操作、按分区扩容或隔离坏任务。

4. 用 `order_id` 作为 partition key，让同一订单的状态事件进入同一分区；消费者在该键上顺序执行，数据库状态机以版本号或合法迁移拒绝过期事件。一个全局分区会把所有订单串行化，吞吐上限和故障影响都集中到一条路径；无关订单并不需要彼此排序。

5. 前者是定时任务：保存调度定义和每个周期的执行记录，保证多实例只领取一次；后者是带 `run_at` 的延迟任务，执行前再次检查会话没有被续期。时区上要用明确的业务时区并处理夏令时；多实例上用 leader、租约或唯一周期键；重试上要使清理操作幂等，且记录上次成功水位，避免宕机后悄悄漏跑。

6. 事务内更新支付状态并插入唯一的 outbox 事件；relay 读取事件、发布、收到 broker 确认后记录已发布。relay 可能在发布成功、标记前崩溃，因此同一事件仍会发布多次；下游收据服务必须按事件或订单收据键幂等。Outbox 保证本地状态和“待投递意图”原子一致，不保证邮件供应商绝不收到两次请求。验收时可模拟 relay 在收到发布确认后崩溃，并确认收据服务最终只发送一封邮件。
